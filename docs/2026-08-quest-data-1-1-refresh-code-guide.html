PR #50 · Code guide

The quest that keeps your progress after the game renames it

Patch 1.1 renamed ninety-one quests and gave eight titles to a different quest. The pipeline that rebuilds the app database identified a quest by its wiki page address. A refresh would therefore detach recorded progress from all ninety-one. On the eight it would attach that progress to the wrong quest. This change makes identity follow the game's own identifier. Four labs let you operate the resolver, the collision order, the name key and the prerequisite collapse.

This is phase 3 of the EFT 1.1 roadmap, code half only. Two decision documents carry the design. docs/decisions/feature-quest-data-1-1-refresh.md holds the product decision, and feature-quest-data-1-1-refresh.spec.md holds the technical design. The research behind both is docs/assessments/2026-08-quest-data-1-1-refresh-grounds.md. This PR publishes no data. It prepares the pipeline, so that the regeneration in PR B runs against reviewed code.

The whole change

The pipeline reads the game rules from a live source again. Quest identity now follows the game's own identifier, so a rename keeps the player's progress. Seven guards stop a run that would publish wrong data.

01

What a quest is keyed by

A quest has two keys, and the recorded progress of the player hangs off both of them. Every decision in this change follows from that fact, so read this chapter first.

The published database gives each quest a row key in Quests.Id. The key is base64 of the wiki page address of the quest. Until this change the pipeline computed that key again from the current page title on every run.

The app has a second key. No published database ever carried a NormalizedName column, so both the released build and main compute one from the quest name in SQL.

TarkovHelper/Services/QuestDbService.csLoadBaseQuestsAsync, the column-absent path
LOWER(REPLACE(REPLACE(REPLACE(Name, ' ', '-'), '''', ''), '.', '')) AS NormalizedName

Recorded progress is a row in the database of the user: QuestProgress(ProfileId, Id, NormalizedName, Status). A write files the row under the Id of the quest and stores the name key beside it. A load keys each row by normalizedName ?? id, so a row written before the name key existed answers to the row key alone.

A read therefore asks both keys, always.

TarkovHelper/Services/QuestProgressService.csIsRecordedAs
private static bool IsRecordedAs(ProgressSnapshot snapshot, TarkovTask task, QuestStatus status)
    => RecordedUnder(snapshot, ProgressKeyOf(task), status)
       || RecordedUnder(snapshot, task.NormalizedName, status);

Now put the two facts together. The row key came from the page title, and the name key came from the quest name. A patch that renames the page moves both keys at once. The recorded row then matches neither key, and the completion of the player disappears from the screen.

The rule to carry through the guide

A quest keeps the progress of the player only if it keeps at least one of its two keys. This change keeps both.

02

The pipeline stopped reading the game

The refresh had one source for the game rules, and that source went down in July. Two older defects had already emptied the fields the app needs most.

The app describes a game that no longer exists. Patch 1.1 landed on 2026-08-03. Quests it removed are still listed, quests it added are missing, and dissolved chains still show quests as locked. The Kappa gauge counts 248 quests where the game now requires 13.

The pipeline could not correct any of that. Its only source of game rules was the tarkov.dev GraphQL endpoint, which has answered HTTP 422 since about 2026-07-22. The queries it sent would not have helped in any case.

the only task query the pipeline ever sentbefore this change
{ tasks(lang: en) { id tarkovDataId name normalizedName wikiLink trader { name } } }
// No minimum level. No Kappa flag. No loyalty. No prerequisites. No faction.

Two older defects made the state worse. The first defect is an empty cache. A fetch could receive a valid HTTP 200 that carried an error body. It wrote that body to the cache as an empty set, and the refresh reported success.

The January 2026 regeneration ran that way. Since then BsgId, the identifier the game itself uses, is NULL on all 488 quests and all 4014 items. Two features read that column and both have been dead for seven months. Log sync matches no quest event, and hideout item requirements resolve 0 of 317 rows.

The second defect is silence. A failed export batch was counted and ignored. An empty wiki cache returned success with zero quests, and a missing item cache let the run continue. Chapter 8 covers the guards that close each path.

Why the empty cache matters more than it looks

An empty cache does not fail. It publishes. The identifiers it dropped are the same identifiers the rename carry-over in chapter 3 depends on. One silent failure in January set the trap that patch 1.1 sprang.

The replacement source is the JSON API at json.tarkov.dev, which the tarkov.dev front end itself reads. TarkovDevJsonClient fetches four endpoints with their locale files, and it refuses an empty or malformed answer.

TarkovDBEditor/Services/TarkovDevJsonClient.csFetchTasksAsync, abbreviated
var payload = Deserialize<JsonEnvelope<JsonTasksData>>(group.Bodies[0], TasksPath);
var rawTasks = payload?.Data?.Tasks;
if (rawTasks == null || rawTasks.Count == 0)
{
    // Never write an empty cache: see the class remarks.
    throw new InvalidOperationException(
        $"{_baseUrl}{TasksPath} returned no tasks. Refusing to overwrite the cache with an empty set.");
}

foreach (var (id, task) in rawTasks)
{
    if (string.IsNullOrEmpty(task?.Id))
        throw new InvalidOperationException($"{TasksPath}: task '{id}' has no id.");
    if (string.IsNullOrEmpty(task.WikiLink))
        throw new InvalidOperationException($"{TasksPath}: task '{task.Id}' has no wikiLink.");
    // ... maps the task into the cache model
}

The client carries the fields the old query omitted: minPlayerLevel, kappaRequired, factionName, taskRequirements and the per-trader traderRequirements. It reads Korean and Japanese names from the locale files beside each endpoint. It sends the stored ETag, so a repeat run costs one 304 answer for each file.

03

Ninety-one renames and eight reused titles

This is the defect the change exists for. A refresh done the old way loses progress on ninety-one quests, and moves progress onto the wrong quest on eight of them.

Patch 1.1 de-numbered the multi-part chains. Measured against the 488 published quests: 91 are renames to a page that still exists, 35 were removed from the game, and 1 is a punctuation redirect.

Eight titles are worse than a rename. The Sew it Good, Punisher and Tarkov Shooter parts were renumbered, so a title that named one quest now names another one.

Published rowIts game recordIts 1.1 page
Sew it Good - Part 45ae4497b86f7744cf402ed00Sew it Good - Part 2
Sew it Good - Part 35ae4496986f774459e77beb6Sew it Good - Part 4
A Shooter Born in Heaven5c0bde0986f77479cf22c2f8Shooter Born in Heaven

Read the first two rows together. A page-keyed refresh mints the row key for "Sew it Good - Part 4" from that title, exactly as it did before. The completion of the old Part 4 is filed under that same key. So the completion shows against a quest the player has never done.

The answer is to follow the identifier of the game instead. QuestIdentityResolver matches each wiki page to a task, and then looks up the previous row that holds the same BsgId. Where it finds one, the quest keeps the key of that row and its name key under the new title.

TarkovDBEditor/Services/QuestIdentityResolver.csResolve, the identity step
var carried = task == null ? null : previous.ByBsgId(task.Id);

resolution.Quests.Add(new ResolvedQuest
{
    Title = page.Title,
    WikiPageLink = WikiQuestIdentity.PageLinkFor(page.Title),
    Id = carried?.Id ?? WikiQuestIdentity.IdFor(page.Title),
    // A previous database without the NormalizedName column (every publish
    // before this one) still pins the value both builds computed for that row
    // themselves, which is what their stored progress is keyed by.
    NormalizedName = carried == null
        ? QuestNormalizedName.SqlForm(page.Title)
        : carried.NormalizedName ?? QuestNormalizedName.SqlForm(carried.Name),
    Task = task,
    FactionPairShared = factionPairShared,
    PreviousName = carried?.Name,
});

The carry-over is a property of the data, not of new app code. That matters, because every install in the field runs the July release. Data reaches those builds within minutes, and an app update cannot.

The carry-over has one precondition. It reads BsgId from the previous database, and chapter 2 says that column is NULL on every row. BsgIdBackfillService copies the identifiers back from the December 2025 snapshot, which holds 473 of the 488. One rename has no identifier to copy, and the runbook sets that one by hand.

04

One page, several game records

Ten wiki titles are the link target of two or three tasks. A page has to take one of them, and which one it takes decides whose log events match.

A quest row holds one BsgId. Ten pages have more than one candidate, for two different reasons. Some quests exist as a BEAR record and a USEC record behind one page. Others exist as an old record and a re-created record.

The first draft took the lowest identifier. That rule is not evidence, and on The Tarkov Shooter - Part 5 it takes the dead record. Part 6 lists the other record as its prerequisite, so the dead record also drops the only prerequisite Part 6 has.

ChooseAmong replaces the guess with a fixed order of evidence. The order is reproducible, and the refresh report prints every candidate with the rule that decided.

TarkovDBEditor/Services/QuestIdentityResolver.csChooseAmong
if (candidates.Count == 1)
    return (candidates[0], CollisionRule.Single);

// 1. A BEAR/USEC pair behind one page: the page serves both factions, as the four
//    published rows for Drip-Out and Textile do today.
if (candidates.Count == 2 && IsFactionPair(candidates[0], candidates[1]))
    return (LowestId(candidates), CollisionRule.FactionPair);

// 2. The record the rest of the game data believes in: some other task requires it.
var requiredByAnother = candidates.Where(c => index.IsRequiredByAnotherTask(c.Id)).ToList();
if (requiredByAnother.Count > 0)
    return (LowestId(requiredByAnother), CollisionRule.RequiredByAnotherTask);

// 3. The record the user's own log events have already been matching.
var previousId = previous.ByPageTitle(title)?.BsgId;
var previouslyHeld = candidates.FirstOrDefault(c =>
    string.Equals(c.Id, previousId, StringComparison.OrdinalIgnoreCase));
if (previouslyHeld != null)
    return (previouslyHeld, CollisionRule.PreviousRow);

// 4. Nothing to go on: the record the game created most recently.
return (NewestId(candidates), CollisionRule.NewestId);

Step 1 also sets FactionPairShared, which keeps Faction NULL on the row. That matters more than it looks. The released build compares the faction string for equality, so a row that takes the BEAR side hides the quest from every USEC player.

Step 4 needs the creation time of a record. The first eight hex digits of a game identifier are a Unix timestamp, so the newest record is a sort. An identifier that is not in that shape sorts oldest, and therefore never wins the tie-break by accident.

TarkovDBEditor/Services/QuestIdentityResolver.csCreationTimeOf
internal static long CreationTimeOf(TarkovDevQuestCacheItem task)
{
    if (task.Id.Length < 8)
        return long.MinValue;

    return long.TryParse(task.Id.AsSpan(0, 8), NumberStyles.HexNumber, CultureInfo.InvariantCulture, out var seconds)
        ? seconds
        : long.MinValue;
}

A task is claimed by one page only. The three match passes run in order of strength: the page address against wikiLink, then the page title against the slug of the task, then the committed alias list. Pages are sorted by title before the passes, so two pages that compete for one task always resolve the same way.

05

The key the app computes for itself

The schema grows by two additive pieces. One of them is a column whose spelling decides whether recorded progress is found at all.

Chapter 1 showed the app computing a name key in SQL because no column holds one. This change adds the column, and every build switches to it the moment it exists. That is the hazard. The stored progress of the player is keyed by the value the SQL expression produced, so the column has to produce the same value.

The editor already had a name normalizer, and it writes the tarkov.dev spelling: sew-it-good-part-4 where the app computes sew-it-good---part-4. The two forms differ on 228 of the 488 published quests.

The one change that is invisible to the drift guard

A column of tarkov.dev spellings is additive. DataFormatDriftTests reports it as widened, and the publish goes out. In the field it un-keys the recorded progress of 228 quests in every build at once.

QuestNormalizedName.SqlForm is therefore a port of the SQL expression, and not of the editor normalizer. It lowers A to Z only, because that is all SQLite does. The bundled e_sqlite3 is built without ICU, so LOWER leaves every non-ASCII letter alone.

TarkovDBEditor/Services/QuestNormalizedName.csSqlForm
var result = new StringBuilder(name.Length);
foreach (var c in name)
{
    switch (c)
    {
        case ' ':
            result.Append('-');
            break;
        case '\'':
        case '.':
            break;
        default:
            result.Append(c is >= 'A' and <= 'Z' ? (char)(c + ('a' - 'A')) : c);
            break;
    }
}

The typographic apostrophe U+2019 in "What’s on the Flash Drive?" survives this function. It survives the SQL expression too, because REPLACE only ever looks for the ASCII apostrophe U+0027. The port is correct exactly where it looks wrong.

One invariant holds the two keys together: NormalizedName == SqlForm(TitleOf(Id)), where TitleOf decodes the page title the row key was minted from. It holds for a renamed row as well, because both sides then describe the original title. Chapter 8 shows the guard that checks it on every row before a write.

The second piece: loyalty per trader

The roadmap expected each loyalty requirement to name the trader who gives the quest, and chose a single column. The 1.1 data disagrees. Besides Collector, four ordinary quests require loyalty with a trader other than their giver, and one of them names five traders.

A single column would have dropped those gates in silence, so QuestTraderRequirements is a child table that mirrors HideoutTraderRequirements. Nothing on screen changes in this phase. Builds in the field ignore the table, and phase 4 reads it.

06

What ships is what both sources have

The wiki lists quests the app has never shown, and the game data lists quests the game removed. A quest ships when both sources have it, with one exception the wiki itself writes.

The wiki quest category now holds 47 pages for the questline of the separate Arena game, plus pages kept for removed quests. The JSON API still lists 35 quests the game removed. Neither source alone answers the question of what exists today.

So a page becomes a quest when the crawl found it in the quest category, no excluded category holds it, and a task matched it. Requiring both sources needs no hand-maintained list of exceptions.

One exception is needed. The JSON API carries no record for the eighteen KORD BREACH quests of the current season, in any game mode. Those pages come in on the word of the wiki alone, recognised by the requirement line the pages themselves carry.

TarkovDBEditor/Services/WikiQuestService.csExtractIsSeasonal, abbreviated
var reqMatch = Regex.Match(content, @"==\s*Requirements\s*==\s*(.*?)(?===|\z)", RegexOptions.Singleline | RegexOptions.IgnoreCase);
if (!reqMatch.Success)
    return false;

foreach (Match bullet in Regex.Matches(
    reqMatch.Groups[1].Value,
    @"^\*+\s*Must be playing in the\s*\[\[([^\]|]+)",
    RegexOptions.IgnoreCase | RegexOptions.Multiline))
{
    var target = bullet.Groups[1].Value.Trim();
    if (target.StartsWith("Seasons#", StringComparison.OrdinalIgnoreCase)
        || target.Equals("PvP Season", StringComparison.OrdinalIgnoreCase))
    {
        return true;
    }
}

return false;

The reader is deliberately narrow. It reads the link target of a requirement bullet, and not the words around it. A page that mentions a season in prose is not imported without a game record.

A narrow reader has a failure mode: the wiki changes the wording, no page matches, and eighteen quests leave the app in silence. MentionsSeasonalMode is the loose counterpart. When pages mention a seasonal mode and none of them matches the strict reader, the run fails and names the reason.

A seasonal quest carries no BsgId until the API adds a record, so log sync cannot mark it. When the API catches up, the page matches by its address, the row key does not move, and a data-only publish fills the gap.

The one hand-maintained list

Three prestige tasks point their wikiLink at Neuanfang, a German title with no page, and no normalization maps "New Beginning (Prestige 2)" to new-beginning-2. Without help those three published quests would leave the app.

quest-match-overrides.json bridges them. Each entry names the upstream report it waits on, so the list is a workaround and not a second source of truth. The refresh report flags an entry whose page matches without it, which is how an entry gets retired.

Prestige 5 and Prestige 6 have no record at all, and no seasonal marker. They leave the app until the API carries them. Recorded progress on them stays in the data of the user and reappears when they return.

07

One prerequisite, two statuses

Prerequisites now come from the game data. Fourteen of them name more than one satisfying status, and a requirement row can hold only one.

The wiki chain is no longer usable. Patch 1.1 dissolved most chains, and the wiki lists more prerequisites than the game on 111 quests and fewer on 60. The API list is the game list, so the pipeline takes it.

The API has no OR groups. Fifteen quests had one in the published data, and they collapse to the AND list of the game. The report shows each one before and after.

Then live 1.1 data produced a failure the spec did not anticipate. Fourteen prerequisites name two statuses: ten name active or complete, and four name complete or failed. The row key is the triple (quest, prerequisite, group), so one row for each status collides on the primary key.

TarkovDBEditor/Services/RefreshDataService.csMapRequirementStatuses
public static string MapRequirementStatuses(IReadOnlyList<string> statuses, string questTitle)
{
    // An entry with no status at all means the ordinary "must be completed".
    if (statuses.Count == 0)
        return "Complete";

    var types = statuses.Select(s => MapRequirementStatus(s, questTitle)).ToList();

    if (types.Contains("Accept")) return "Accept";
    if (types.Contains("Complete")) return "Complete";
    return "Fail";
}

The most permissive type wins. That choice is not arbitrary. The released build treats Accept as satisfied by an active prerequisite and by a completed one. So "active or complete" collapses onto Accept with nothing lost.

"Complete or failed" has no single equivalent, and it takes Complete. A player who failed the prerequisite may take the quest in the game, and the app keeps it locked. Four quests are affected, the report lists them, and the PR asks a reviewer to confirm the trade.

The other direction is worse

An unknown requirement type is never satisfied by QuestProgressService.IsStatusSatisfied, so it locks the quest for ever. A quest shown a little early is the smaller harm, and DeduplicateRequirements resolves duplicate rows the same way.

Collector is computed, and now it can shrink

The prerequisite list of Collector is the Kappa set, derived from the flags rather than curated. It used to be written after the transaction, which meant the code could only insert. A quest that lost its Kappa flag kept its Collector row for ever, and the published data carries one such leftover.

The rows are now built in memory, and they go through the same table-global diff as every other requirement. A quest that leaves the Kappa set now leaves the list of Collector with it. The Kappa count falls from 248 to 13.

The API also gives Collector five prerequisites of its own, and all five are already in the Kappa set. Taking both would write the same row twice, so the builder skips Collector on the same name test the synthesis matches on.

08

Nothing publishes quietly

Every guard here describes a way this pipeline has already failed in silence. A crossed threshold is a source problem, and never something to publish.

Seven guards stop a run before it writes. Three of them are presence tests. An empty wiki cache fails the run. An empty or missing task cache fails it, and so does an empty or missing trader cache. Each message names the menu command that fixes it. An export batch that failed now aggregates and throws after the loop, instead of being counted and ignored.

Three more are thresholds. Each threshold is a constant with a comment that names the spec.

TarkovDBEditor/Services/RefreshDataService.csRefreshGuards
/// Above this share of previous quests without an external ID, the carry-over
/// cannot work: every renamed quest would be minted a fresh row key while its page
/// still matched, so all 91 of them would lose their recorded progress. The
/// match-rate guard does not catch this, because the pages do still match.
public const double MaxPreviousQuestsWithoutBsgId = 0.10;

/// Above this share of previously published quests losing their game record, the
/// task set is wrong (an outage serving a partial file, a game mode with fewer
/// tasks), not the game.
public const double MaxLostMatches = 0.05;

/// Above this share of imported quests without a trader, the trader cache is wrong.
public const double MaxTradersMissing = 0.05;

/// How far the task cache may lag the wiki crawl before the pair stops describing
/// one moment in the game.
public static readonly TimeSpan MaxTaskCacheLag = TimeSpan.FromDays(7);

The first constant is the guard the whole carry-over rests on. Lab A shows why the match-rate guard cannot cover it. A run from a database whose identifiers are still NULL matches every page. Nothing looks wrong, and every renamed quest gets a fresh row key.

The seventh guard is the seasonal marker of chapter 6. Pages that mention a seasonal mode with no page marked seasonal means the wording moved upstream.

The last gate before a write

AssertPublishConstraints checks the value vocabularies and the NULL rules the released build depends on. Each item on its list is a way an additive publish can still break a build that is already installed.

  • The requirement type is one of Complete, Accept and Fail. An unknown type is never satisfied, which locks the quest for ever.
  • The faction is NULL, Bear or Usec. The released build compares the string for equality, so any other value hides the quest.
  • The name key equals SqlForm(TitleOf(Id)) on every row, is never empty, and is unique. Progress recorded against a row that fails this test is not found.
  • The trader is present on all but a small share of rows, and no two quests share a row key.

The exception collects every problem and names the offending rows, rather than throwing on the first one. An operator who must fix a source wants the whole list.

The report a regeneration is reviewed against

About every quest row changes in this refresh, and no one can review that in a database browser. tools/DataDiff is a console project in the solution that compares the published database against the candidate and writes markdown.

It joins quests by BsgId first and by row key second. A rename therefore reads as a rename, and not as one removal with one addition. It calls out the titles that changed owner and the prerequisite edges added and removed. It also lists the objective lists whose shape changed, the icon coverage and the NULL rates. It replaces CheckDb, an untouched Hello World scaffold, and its comparison core has its own tests.

This PR also gives the pipeline its first tests, about 120 of them across six suites. Before this change no service in the editor other than the publish service had one.
