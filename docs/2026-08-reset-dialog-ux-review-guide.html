PR #41 · Code guide, part 5

A wipe you have to mean

Parts 3 and 4 made the profile reset structurally airtight: one transaction, one barrier, one fence, every wait bounded. This pass reviewed the dialog a player actually touches and fixed the three gaps that survived: a keyboard with no safe default, a target name that blends into its sentence, and colors the app's theme does not know about. Two labs let you drive the keyboard model and the run renderer yourself.

Part 5 of the profile series, stacked on PR #41 after the PR #42 hardening merged into it. Part 3 covers the reset's design, part 4 its deep review. Companion to docs/decisions/feature-complete-profile-reset.md (R1, R2, R5).

The whole change in one sentence

Three UX fixes make the reset dialog safe by default and its target unmistakable: keyboard focus starts on Cancel and follows the state swap so Enter and Space can never wipe anything by reflex, the profile name is rendered as the emphasized word of the sentence and spelled out on the confirm button itself, and the dialog's warning and error colors come from the app theme instead of near-miss literals.

01

The dialog after the hardening

A UX review asks a different question than a deep review: not "where does this fail?" but "what does a player experience, key by key and glance by glance?" Three findings survived that question.

By the time this pass ran, ProfileResetDialog was already a hardened piece of machinery. It names the captured target profile (PRD R1), enumerates every category the reset removes (R2), reports failure with the all-or-nothing guarantee (R5), refuses to close mid-run but only up to CloseRefusalLimit, and even its raid warning had learned not to cry wolf (ShouldWarnAboutRaid gates on IsMonitoring). The PR #42 hardening also gave both of its dismiss buttons IsCancel, so Escape already declined the confirmation and dismissed the result.

What remained were experience gaps, the kind a green test suite has no opinion about:

  • The keyboard had no default. The dialog opened with nothing focused, so Enter and Space did nothing, and the first Tab press was a guess. After a reset, focus was left behind with the collapsed confirm panel.
  • The target name blended in. PRD R1's whole point is that a player with three profiles can see which one is at risk, but the name sat mid-sentence in the same small semibold as every word around it, and the confirm button said only "Reset This Profile".
  • The colors bypassed the theme. The raid warning hardcoded an orange one shade off the app's WarningColor, and the error detail hardcoded the exact value of ErrorBrush.

Three commits fix these in order: focus, naming, colors. Each is small; the reasoning behind each is the part worth reviewing, and that is what this guide walks.

02

A dialog opened blind

WindowStyle="None" buys the dialog its look and costs it every built-in keyboard behavior. Escape had been wired back by hand; nothing had wired back focus.

A borderless WPF window starts with keyboard focus on the window itself, not on any control. Every keystroke a player sends lands nowhere: Enter does nothing, Space does nothing, and the first Tab jumps to whatever happens to be the first focusable element in the visual tree. For most dialogs that is an annoyance. For a dialog whose accept button permanently deletes a profile, it is also a lost opportunity, because focus placement is the one keyboard decision a destructive dialog gets to make in its favor.

The second half of the defect

The result state made it worse. ShowResult collapses the confirm panel and shows the result panel, but collapsing an element does not move keyboard focus: focus stayed behind with the now-collapsed, disabled confirm buttons. A keyboard user who had Tabbed to a button, run the reset, and then pressed Enter to dismiss the outcome got nothing. Only Escape (via Close's IsCancel) or another blind Tab worked.

There is also a decision hiding in what the dialog does not wire. QuestCompleteConfirmDialog, the app's other borderless confirmation, sets IsDefault on its confirm button so Enter confirms from anywhere. Symmetry would suggest doing the same here. Symmetry would be wrong: completing a quest is one click to undo, a profile wipe is not, and IsDefault turns Enter into a global accept regardless of what holds focus. The reset dialog must keep the asymmetry: Escape dismisses from anywhere, Enter acts only on what is focused.

03

Focus as the keyboard default

With no IsDefault, whatever holds focus IS the Enter key's meaning. The fix is two lines that decide that meaning deliberately, in both states.

The confirm state's fix is declarative. The window claims its initial focus in XAML, and the choice of element is the entire point: Cancel, so that a reflexive Enter or Space declines.

TarkovHelper/Windows/ProfileResetDialog.xamlconfirm state
        ResizeMode="NoResize"
        SizeToContent="WidthAndHeight"
-        ShowInTaskbar="False">
+        ShowInTaskbar="False"
+        FocusManager.FocusedElement="{Binding ElementName=BtnCancelReset}">

The result state's fix is one call at the state swap. Focus follows the panels, so the button the player now needs is the button the keyboard now holds.

TarkovHelper/Windows/ProfileResetDialog.xaml.csShowResult
 ConfirmPanel.Visibility = Visibility.Collapsed;
 ResultPanel.Visibility = Visibility.Visible;

+// Focus follows the state swap, so Enter/Space dismiss the result without a Tab
+// first; Escape already reaches Close through its own IsCancel flag.
+BtnCloseReset.Focus();

 TxtResetResult.Text = ResultHeadline(_loc, outcome, _target);

The finished keyboard model reads as a table of intent. Escape always means "get me out safely": it declines the confirmation or dismisses the result, both no-ops on data. Enter and Space act on the focused element, and focus only ever starts on safe elements. The single destructive action, the confirm button, is reachable exclusively by deliberate navigation: a Tab (or a mouse click) followed by an activation. No single keystroke wipes a profile from the dialog's opening state.

Why both IsCancel flags can stay true

Cancel and Close both carry IsCancel for the dialog's whole life. That is unambiguous because the two panels swap Visibility: a collapsed button is not an eligible Escape target, so exactly one IsCancel button is ever hittable. An earlier draft of this pass moved the flag by hand at the state swap; the shipped design keeps the flags static and lets visibility disambiguate, which is one less thing to keep in sync.

04

The load-bearing word

PRD R1 exists so a player with several profiles always knows which one is at risk. The dialog named the profile; nothing made the name visible.

The target line read "This will permanently remove everything the PvP Season profile owns:", set in FontSizeSmall with the whole line semibold. Typographically, "PvP Season" was indistinguishable from "everything" or "permanently". The one word the sentence exists to deliver had no more weight than its function words.

Why this matters more since PvP Season

The seasonal profile turned reset from a rare recovery action into the routine way a season starts. Routine actions build muscle memory, and muscle memory stops reading body text. A player who resets "as usual" while the app has auto-switched profiles under them is exactly the accident R1 anticipates, and the only defense at click time was a button reading "Reset This Profile", where "This" is a reference the player must resolve by re-reading the context they have stopped reading.

The fix names the target twice, at the two moments that matter: once in the sentence, where the name becomes the visually emphasized word, and once on the confirm button, so the last thing the player clicks carries the name itself.

05

Naming the target twice

The button is a format string; the sentence is three text runs. The interesting part is the constraint that shaped the runs: an e2e assertion on the line's exact text that must keep passing.

The button change is a rename with a slot. ProfileResetConfirmButton becomes ProfileResetConfirmButtonFormat: "Reset {0}" in English, "{0} 초기화" in Korean, "{0}をリセット" in Japanese. The e2e now asserts the rendered content ("Reset PvP Season") against the captured target, and the localization completeness tests track the renamed key.

TarkovHelper/Windows/ProfileResetDialog.xaml.csconstructor
-BtnConfirmReset.Content = _loc.ProfileResetConfirmButton;
+BtnConfirmReset.Content =
+    string.Format(_loc.ProfileResetConfirmButtonFormat, _loc.ProfileName(target));

The sentence is the subtler half. The existing e2e test finds the target line by its exact UIA Name, which for a TextBlock is its Text. A TextBlock built from plain Runs flattens them into exactly the concatenated string, so the name can be restyled without the text changing, and the assertion keeps holding without being touched. That flattening guarantee is why the implementation uses three plain runs and nothing fancier.

TarkovHelper/Windows/ProfileResetDialog.xaml.csSetTargetLine
private void SetTargetLine(string format, string profileName)
{
    var slot = format.IndexOf("{0}", StringComparison.Ordinal);
    if (slot < 0)
    {
        // A translation that lost its slot degrades to the unstyled sentence rather
        // than crashing; the localization tests guard the slot's presence.
        TxtResetTarget.Text = format;
        return;
    }

    TxtResetTarget.Inlines.Clear();
    if (slot > 0)
        TxtResetTarget.Inlines.Add(new Run(format[..slot]));
    TxtResetTarget.Inlines.Add(new Run(profileName)
    {
        FontWeight = FontWeights.Bold,
        Foreground = (Brush)FindResource("ErrorBrush")
    });
    var suffix = format[(slot + "{0}".Length)..];
    if (suffix.Length > 0)
        TxtResetTarget.Inlines.Add(new Run(suffix));
}

Two boundary decisions live in those few lines. The Korean and Japanese formats begin with "{0}", so slot == 0 and the prefix run is skipped rather than added empty. And the slot < 0 branch is a deliberate degradation: it can only run if a future translation edit loses the slot, which Format_keys_keep_their_argument_slot already fails the build for; if that guard is somehow bypassed, the player gets an unstyled but correct sentence instead of an exception inside a destructive dialog.

06

Two oranges, one red

App.xaml defines WarningColor #ff9800 and ErrorBrush #ef5350. The dialog shipped with #FFA726 and #EF5350. One of those literals is worse than the other.

TarkovHelper/Windows/ProfileResetDialog.xamlraid warning + error detail
-<Border x:Name="RaidWarningBorder" Background="#44FFA726" CornerRadius="4" ...>
-    <TextBlock x:Name="TxtRaidWarning" ... Foreground="#FFA726" .../>
+<Border x:Name="RaidWarningBorder" CornerRadius="4" ...>
+    <!-- The app-wide warning color at ~27% opacity (the 0x44 alpha the old
+         hardcoded value used), so the tint tracks WarningColor. -->
+    <Border.Background>
+        <SolidColorBrush Color="{StaticResource WarningColor}" Opacity="0.27"/>
+    </Border.Background>
+    <TextBlock x:Name="TxtRaidWarning" ... Foreground="{StaticResource WarningBrush}" .../>
 ...
-<TextBlock x:Name="TxtResetError" ... Foreground="#EF5350" .../>
+<TextBlock x:Name="TxtResetError" ... Foreground="{StaticResource ErrorBrush}" .../>

The error detail's #EF5350 duplicated ErrorBrush exactly: latently wrong (a future palette change silently strands it) but correct today, and even findable by searching for the token's value. The raid warning's #FFA726 is the worse defect: it is already a color the palette does not contain, close enough to pass any review glance, far enough to make the dialog subtly off-brand, and no search for #ff9800 will ever surface it. Near-miss literals are how themes rot.

The one non-obvious move is the tint. The old background was #44FFA726, the warning orange at alpha 0x44. There is no "WarningBrush at 27%" resource, so the fix builds the brush locally from the shared WarningColor with Opacity="0.27" (0x44 / 0xFF): the alpha the designer chose survives, and the hue now tracks the palette.

07

What stayed as it was

Three review candidates were deliberately not shipped. A reviewer should be able to see the reasoning, not just the absence.

  • No IsDefault on the confirm button. Covered in chapter 02: Enter must never be a global accept in a dialog whose accept is irreversible. The XAML comment records the asymmetry so a future "consistency" cleanup does not undo it.
  • No type-the-name-to-confirm friction. PvP Season made reset a routine season-start action. The shipped friction, a Danger Zone button plus an explicit named confirmation, matches that frequency; typing the profile name every season would punish the common case to guard against an accident the named button now guards better.
  • The raid warning still evaluates once, at open. A player who opens the dialog and then queues into a raid before confirming sees no warning. PRD R8 makes the warning advisory (warn, never block), the window between open and confirm is seconds, and the part 4 hardening already fixed the warning's real defect (stale raid state crying wolf). Re-checking at confirm time remains a candidate for a future pass.
