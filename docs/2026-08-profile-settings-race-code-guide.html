PR #43 · Code guide, part 6

The settings that belonged to nobody

Three of the four services that reload on a profile switch had grown a transition guard. The fourth held the numbers a player edits by hand: level, scav reputation, faction, prestige, DSP count, editions. It refilled them one key at a time, asking "which profile is selected?" eight separate times, and wrote a player's correction into whichever profile the answer happened to be. Three labs let you drive the tear, the revision gate, and the write attribution yourself.

Part 6 of the profile series. Part 1 covers write attribution for progress data, part 3 the complete profile reset, part 5 the reset dialog UX. Companion to docs/decisions/fix-profile-settings-race.md (R1, R2, R5) and docs/decisions/fix-profile-settings-race.spec.md. It closes SPA-2 of docs/assessments/2026-08-seasonal-profile-amplified-issues.md, the last of the four services that finding named.

The whole change in one sentence

The eight profile-scoped settings become one immutable snapshot that carries the profile it belongs to and the transition it was loaded for, built from a single bulk query and published only while its revision is still the latest, so a reload can no longer tear across two profiles or publish an older profile's values last, and an edit is stored in the profile whose value was on screen instead of the one the switch just selected.

01

The guard three services had

A profile switch is announced, not awaited. Two of them can be in flight at once, from two different threads, and the subscriber that handles them has to be able to tell which one it is serving.

ProfileService keeps the selection and a monotonic transition counter as one unit under a static gate. CurrentTransition hands out the pair atomically, and ProfileChangedEventArgs carries Profile, ProfileChanged and Revision. The revision counts every raise, including a provenance-only re-confirmation, so no two loads ever serve the same number.

The event is raised outside that lock, deliberately: handlers run synchronously and take locks of their own, so holding the gate across the raise would be a lock-ordering hazard. The cost is the thing this whole guide is about. Two near-simultaneous transitions, one from the dispatcher when the player clicks and one from the EFT log watcher's thread pool, can deliver their events to a given subscriber in either order.

TarkovHelper/Services/ProfileService.csunchanged by this PR
public (AppProfile Profile, long Revision) CurrentTransition
{
    get { lock (_gate) return (_activeProfile, _transitionRevision); }
}

Five subscribers listen. QuestProgressService, HideoutProgressService and ItemInventoryService share one shape, grown over parts 1 and 3 of this series:

  1. the handler takes the event's own Profile and Revision, never a fresh lookup;
  2. ClaimRevision lifts the latest-known revision to this one;
  3. the store read happens off to the side, touching no cache;
  4. the revision is re-checked after the read;
  5. a stale result is discarded rather than published.

Publication is atomic per service. QuestProgressService swaps an immutable ProgressSnapshot that embeds its own ProfileId and Revision; the other two swap a mutable cache together with a _loadedProfileId string under a lock. ProfileReloadRaceTests and ProgressSnapshotTests pin it.

The fifth subscriber is MainWindow, which only repaints a header. The fourth is where the data was.

02

The unguarded fourth

SettingsService threw away both halves of the event and rebuilt its cache by asking a global question eight times in a row.

TarkovHelper/Services/SettingsService.csbefore
private void OnActiveProfileChanged(object? sender, ProfileChangedEventArgs e)
{
    ReloadProfileSettingsAndNotify();   // e.Profile and e.Revision both discarded
}

private void LoadProfileSettings()
{
    _playerLevel = int.TryParse(GetProfileSetting(KeyPlayerLevel), out var level) ? level : null;
    _scavRep = double.TryParse(GetProfileSetting(KeyScavRep), out var scavRep) ? scavRep : null;
    // ... six more, one per key ...
}

private string? GetProfileSetting(string key)
    => _userDataDb.GetProfileSetting(ProfileService.Instance.ActiveProfileId, key);

Read that last line against the loop above it. Every one of the eight reads resolves ActiveProfileId again, at its own call time, and UserDataDbService.GetProfileSetting opens a fresh SQLite connection per call. One reload is eight sequential connection open, query, close cycles, and the selection is free to move between any two of them.

Failure shape one: the tear

A transition landing between read k and read k+1 leaves keys 1 to k holding profile A's values and keys k+1 to 8 holding profile B's. There is no field naming which profile the cache holds, so nothing in the service can detect the state, and nothing clears it. It stands until the next transition, however long that is.

The eight values are not decorative. Level, scav reputation, faction, prestige, editions and the DSP count are what QuestProgressService.GetStatus consults to decide whether a quest is Active, Locked, LevelLocked or Unavailable, and what ItemsPage filters on. While the mixture stands, the lists are filtered by two profiles at once.

03

The older transition publishes last

Suppose the tear were fixed by a single query and nothing else. The second failure shape survives untouched, and it is the one a bulk read cannot reach.

Because the event is raised outside the publisher's lock, the handler for the older transition can run last and therefore publish last. Every value it publishes belongs to one profile, so there is no mixture to spot; the cache simply holds the previous profile's complete set under the newer profile's name. From inside the service the state is indistinguishable from a correct load, and it heals on exactly the same schedule as the tear, which is to say never.

Why a bulk query alone was rejected

Replacing the eight reads with one query removes the tear and leaves the inversion. That is the spec's own reasoning for taking the snapshot shape rather than the smaller diff: the guard has to be about which transition this load serves, not about how many round trips it takes.

The revision exists precisely for this. Each reload claims the revision it serves, re-checks it after the read, and publishes only on an exact match. Both halves are worth reading closely, because the comparisons are narrower than they look:

TarkovHelper/Services/SettingsService.csafter
private void ClaimRevision(long revision)
{
    while (true)
    {
        var current = Interlocked.Read(ref _latestRevision);
        if (revision <= current) return;            // an equal revision does NOT re-claim
        if (Interlocked.CompareExchange(ref _latestRevision, revision, current) == current) return;
    }
}

// ... inside the reload, after the store read ...
if (Interlocked.Read(ref _latestRevision) != revision)
{
    _log.Debug($"Discarding stale settings load for {profileId} (revision {revision})");
    return;
}

The publish check is !=, not <. It asks one question: "is the revision I claimed still the latest anyone claimed?" A load can only fail it by being overtaken, because its own claim already raised the counter to at least its own number. Stating it as an equality makes the invariant the code is really asserting visible at the site.

04

The correction that overwrites

A wrong number on screen is a display bug. A wrong number the player then corrects is a data loss, and it is silent on both ends.

Here is the sequence the PRD is built around. The settings on screen are a mixture, or a stale complete set. The player notices that their level says 32 when it should say 22, and fixes it. The setter runs:

TarkovHelper/Services/SettingsService.csbefore
private void SaveProfileSetting(string key, string value)
    => _userDataDb.SetProfileSetting(ProfileService.Instance.ActiveProfileId, key, value);

The write goes to the profile that is selected, which in the collision window is not the profile whose number was on screen. The player has just taken a value they read off profile A, decided it was wrong, and overwritten profile B's correct value with their correction. Nothing warns them, and afterwards the edit is indistinguishable from a deliberate one, which is why fix-profile-settings-race.md also declines to repair historical damage: there is nothing to key a repair on.

The doctrine was already written down

ProfileAttributionSourceTests allowlisted exactly four selection reads in this file, and its own failure message states the rule the codebase had adopted everywhere else: the partition must arrive as a parameter or on the snapshot the change was derived from. The Non-Goals of docs/decisions/feature-complete-profile-reset.spec.md named this gap explicitly and deferred it as SPA-1 territory, with the question "what would give the cache an identity worth guarding?" left open. This change is the answer, and three of those four allowlist entries are deleted by it.

So the read defect and the write defect are one defect wearing two hats: the cache had no identity of its own, so both the loader and the writer had to ask a global question, and both got an answer that was true at some moment other than the one they needed it for.

05

The snapshot

One immutable value carrying the eight settings, the profile they belong to, and the transition they were loaded for. The shape ProgressSnapshot already proved in part 1.

TarkovHelper/Services/Settings/ProfileSettingsSnapshot.csnew
internal sealed record ProfileSettingsSnapshot(
    string ProfileId,
    long Revision,
    int? PlayerLevel,
    double? ScavRep,
    bool? ShowLevelLockedQuests,
    int? DspDecodeCount,
    string? PlayerFaction,
    bool? HasEodEdition,
    bool? HasUnheardEdition,
    int? PrestigeLevel)
{
    internal static ProfileSettingsSnapshot Defaults(string profileId, long revision)
        => new(profileId, revision, null, null, null, null, null, null, null, null);

    internal int PlayerLevelOrDefault => PlayerLevel ?? SettingsService.DefaultPlayerLevel;
    // ... six more OrDefault members ...
}

The eight nullable fields in SettingsService collapse into one volatile reference to this record. Nullable is load-bearing: null means "this profile has no row for that key", which is what makes the property answer its default. That "null means default" rule used to live in each of the eight getters and would now have needed a second copy wherever the changed events are raised from a snapshot, so it moved onto the record as the OrDefault members and has exactly one home.

PlayerFaction deliberately has no OrDefault. Null there is a real value, "no faction chosen", not a missing one.

The load

UserDataDbService gains a synchronous LoadProfileSettings that reads one profile's rows in a single query. It replaces an async twin that had existed with zero callers, rather than sitting beside it as a second copy. Synchronous, because the caller must have the values when it returns: the property getters answer from them mid-startup, and the reset hook runs as a plain Action.

TarkovHelper/Services/SettingsService.csafter
private void ReloadForProfile(string profileId, long revision, bool notify)
{
    ClaimRevision(revision);

    // Null means the read failed, which is also what _lastLoadFailed records: one query
    // per reload, so there is no half-read state to represent.
    Dictionary<string, string>? values = null;
    try { values = _userDataDb.LoadProfileSettings(profileId); }
    catch (Exception ex) { _log.Error($"Failed to load profile settings for {profileId}: {ex.Message}"); }

    if (Interlocked.Read(ref _latestRevision) != revision) { /* discard */ return; }

    _lastLoadFailed = values == null;

    var snapshot = values == null
        ? ProfileSettingsSnapshot.Defaults(profileId, revision)
        : SnapshotOf(profileId, revision, values);
    ProfileSettings = snapshot;

    if (notify) RaiseProfileSettingsChanged(snapshot);
}

Three details in that block earn their place. The failure path publishes the new profile's defaults rather than keeping the previous values, because keeping them would be the original defect with better manners: one profile's level and editions displayed under another profile's name (PRD R5). The flag is set before the publish so a throwing subscriber cannot leave it stale. And the seven changed events are raised from the captured snapshot rather than re-read per event, so a publish landing mid-fan-out cannot make one event carry a value from a different profile.

A cost the spec states plainly

Failure granularity coarsens. Eight reads used to fail one at a time, nulling one field each; one query means a read failure defaults all eight. In practice the store fails per connection rather than per key, so the eight failed together anyway, and per-key parse failures keep their per-key fallback. That last part is pinned by An_unparsable_row_falls_back_to_its_default_and_leaves_its_neighbours_alone.

06

Writes follow the snapshot

Once the cache has an identity, the write has a destination that does not depend on what happened between the player reading a number and changing it.

TarkovHelper/Services/SettingsService.csafter
private bool UpdateProfileSetting(
    Func<ProfileSettingsSnapshot, ProfileSettingsSnapshot?> update, string key, string value)
{
    // Captured before the derivation, and the only profile named below: the value the
    // player just corrected was read off THIS snapshot.
    var origin = ProfileSettings;

    var next = update(origin);
    if (next == null) return false;          // value already current: no write, no event

    var published = TryPublish(origin, next, update);

    SaveProfileSetting(origin.ProfileId, key, value);
    return published;
}

TryPublish is a compare-and-swap loop in the shape of QuestProgressService.Mutate. If another publisher wins the swap, the update is re-derived against whatever is now live and retried. If what is now live names a different profile, re-application stops: grafting one profile's edited value onto another profile's snapshot is the defect itself, in miniature.

The write below the loop runs either way, and that asymmetry is deliberate rather than sloppy. A reload that overtook this edit read the store before this write, so the row being written is still the row the player was editing; it will be there when that profile is next loaded. Dropping the write as well would discard a correction the player made on purpose. What is dropped is only the in-memory graft, and with it the changed event, because announcing the new value would push it at pages currently showing a different profile.

The guards that had to be preserved exactly

Each of the eight setters had its own "value differs" test, and two of them are sharper than they look. Both survive verbatim in the new lambdas:

  • ScavRep compares against the effective value (s.ScavRepOrDefault), so setting an unstored profile's scav rep to the default still writes nothing, exactly as before.
  • HasEodEdition compares against the nullable value (s.HasEodEdition == value). An unstored edition is not the same as a stored false, so the player's first "no, I do not own it" is still written and announced. Comparing the OrDefault value here would have swallowed it, and no test would have noticed.

The reset hook joins its siblings

HandleProfileReset was the only reset hook that compared the reset target against the ambient selection, and its own doc comment gave the honest reason: the selection was the cache's identity, so there was nothing else to compare with. With a snapshot there is.

TarkovHelper/Services/SettingsService.csbefore / after
if (!string.Equals(profileId, ProfileService.Instance.ActiveProfileId, StringComparison.Ordinal))
    return;
ReloadProfileSettingsAndNotify();

var current = ProfileSettings;
if (!string.Equals(profileId, current.ProfileId, StringComparison.Ordinal))
    return;
// The snapshot's own revision, not a fresh one: a reset announces no transition.
ReloadForProfile(profileId, current.Revision, notify: true);

Passing the snapshot's own revision is what makes an intervening transition win: if one landed while the hook was reading, the guard inside discards this publish, which is correct because that transition's reload also reads post-reset rows. The hook stays synchronous, because ProfileResetService.RunRefreshHooks calls it as a plain Action and expects the cache current when it returns.

07

Healing, and what stayed as it was

Two states can survive a guard, and one event keeps arriving on its own. The rest of the surface is deliberately untouched.

A guard that discards a losing reload can leave the snapshot naming a profile the selection no longer shows, and a failed read leaves the player looking at level 15 and no editions. Both used to be curable only by switching profile by hand. EFT re-logs the session mode every time the player opens the profile screen, which arrives as a provenance-only re-confirmation, and that is the one event that keeps coming without the player doing anything. So it is where the self-healing lives:

TarkovHelper/Services/SettingsService.csafter
if (!e.ProfileChanged && !_lastLoadFailed &&
    string.Equals(ProfileSettings.ProfileId, profileId, StringComparison.Ordinal))
    return;

ReloadForProfile(profileId, e.Revision, notify: true);

All three conditions have to hold for the skip, which is why this is not a plain if (!e.ProfileChanged) return;. The same shape guards QuestProgressService.OnActiveProfileChanged. The skip is also the one fan-out reduction the change makes on purpose: a re-confirmation that needs no healing no longer re-reads identical rows to raise seven events and refresh three pages. Three tests hold the truth table down: A_re_confirmation_that_needs_no_healing_does_not_reload, A_re_confirmation_heals_a_snapshot_left_naming_another_profile, and A_failed_load_publishes_the_new_profiles_defaults_and_heals_on_a_re_confirmation.

What stayed as it was

  • The public surface. Eight properties, seven changed events, HandleProfileReset. No page or consumer is edited by this PR.
  • All seven events fire on every published reload, in the same order, whether or not the value differs. Raising only real changes would make pages refresh less often, which is a UI-timing change tangled into a correctness fix, and ProfileResetHooksTests pins the full sequence as the reset contract.
  • The reload stays synchronous. The three progress services reload fire-and-forget; this one cannot, because its getters must answer coherently mid-startup and the reset hook needs the cache current when it returns. The guard does not depend on asynchrony: it exists because two handler threads interleave.
  • ClaimRevision is duplicated a fourth time, deliberately. Extracting it would edit three already-guarded services for no behaviour change. THR-1 in docs/assessments/2026-08-code-health.md is the cache unification that would absorb it, and the spec records the direction under which this copy becomes a pure move.
  • ShowLevelLockedQuests rides along unchanged. It is stored, cached and saved, and read by nothing outside this service and the legacy JSON migration. Deleting a stored user setting is a product decision, not a concurrency fix, so it stays as the eighth snapshot field.
  • The selector's own display lag, and historical damage. The highlight is painted from a queued callback and can briefly show the losing side of two switches; no stored data is at stake and it stays out. A value an earlier collision caused a player to overwrite cannot be told from a deliberate edit, so nothing is reconstructed.

The enforcement moved with the code

ProfileAttributionSourceTests fails on leftover allowlist entries as well as on new selection reads, so deleting the code forced the list to shrink in the same commit. What remains for this file is two entries: the constructor's subscription, and one CurrentTransition read in LoadSettings, which is the single load with no ActiveProfileChanged to learn its profile from. ProfileResetHooksTests now seeds a snapshot instead of eight private fields, and seeds it for a synthetic profile id that the ambient selection can never equal, so the hook's new identity source is the only thing those tests can be passing on.
