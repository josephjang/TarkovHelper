PR #55 · Code guide

The requirement the app shipped and never read

Patch 1.1 made trader loyalty the main thing that decides if a quest can be taken. The refresh in PR #50 published that requirement for 94 quests. The app did not read it, so it showed those quests as available. This change reads it.

This is phase 4 of the 1.1 adaptation. The data it reads arrived in docs/2026-08-quest-data-1-1-refresh-code-guide.html, which is the earlier chapter of the same story. The decisions here are recorded in docs/decisions/feature-quest-loyalty-gating.md and in its specification docs/decisions/feature-quest-loyalty-gating.spec.md.

The whole change

A quest that needs a trader loyalty level now shows as locked until the player enters that level. The player enters it once for each trader, in the profile drawer.

01

What 1.1 did to unlocking

The patch moved quests off chains and onto trader levels. The refresh published that, and nothing read it.

Before patch 1.1 a quest opened because you finished the quest before it. The chains were long, and the app modelled them well. The patch dissolved most of those chains. It put the freed quests behind a trader loyalty level instead.

The 1.1 refresh published that fact. The table is QuestTraderRequirements. It holds 107 rows over 94 quests, and it names seven traders. The levels run from 2 to 4, and no row asks for level 1.

The refresh published it so that this phase would need nothing from the pipeline. That held. There is no schema change here, no editor change, and no data publish. Every row this change reads is already in the database of every install.

02

A gate that was always met

The defect. 94 quests carried a requirement, and the answer was always yes.

QuestProgressService.GetStatus reads six things about the player. It reads the editions, the prestige level, the faction, the DSP decode count, the player level and the Scav karma. It did not read loyalty, because there was nothing to read it from.

So every loyalty requirement was met. The effect is not the same for every quest, and the two groups are worth separating.

27 of the 94 have no other gate that a new profile fails. They have no prerequisite, and their minimum level is at or below the default of 15. A new profile therefore saw 27 quests as available on the first day. The game locks each one behind loyalty level 2.

The other 67 have a prerequisite or a higher level. They did not show at once. They showed the moment that other gate cleared, which is still wrong. It is also harder to notice, because it looks like the chain working.

The five nobody would guess

15 rows over 5 quests name a trader other than the one who gives the quest. Chemical - Part 3 is Skier's quest and it needs Jaeger at 2. Reading the gate off the giver sends the player to raise Skier, which unlocks nothing. The row on screen shows the giver, so the app must say the other name.

03

Where the gate goes

One more check in the status walk, after level and after karma, and no new status.

The walk has an order, and the order decides what the row badge says. The editions, the prestige and the faction answer Unavailable. The DSP count and the prerequisites answer Locked. The player level and the Scav karma answer LevelLocked. Loyalty joins the third group, last.

Last, and not first. Loyalty levels themselves need player levels in the game, because Prapor 3 needs level 21. A quest short of both is usually waiting on the level first. An earlier check would also change the badge on quests that have no loyalty requirement at all, and this phase must not do that.

The status stays LevelLocked and gains no member of its own. The status chips have a fixed vocabulary, their counts are computed from it, and the selected chip is written to the store. A new member moves all three, for a difference the badge already makes.

+               // level 21 in the game), so a quest short of both is usually waiting on level
+               // first, and running this earlier would change the badge on quests that have

+               if (!IsTraderLoyaltyRequirementMet(task, settings))
+               {
+                   gate = QuestGate.TraderLoyalty;
+                   return QuestStatus.LevelLocked;
+               }

                return QuestStatus.Active;

The check reads every row, and not any row. A quest that names three traders is taken only when all three stand where it asks. A trader with no entry reads as level 1, which is where the game starts every trader. So a new profile fails a level 2 row and meets a level 1 row.

The badge needs a rule of its own, because one status now covers three different requirements. The obvious rule is to ask the same three questions again, in the same order, and name the first one that fails. That is a second copy of the walk's order, with nothing holding the two together. Reorder the walk and every test still passes while the badge sends the player to the wrong requirement.

So the walk says which gate stopped it. GetStatus takes an out QuestGate, sets it at the step that returns, and QuestRequirementBadge.For is a switch over the answer. The precedence exists once, in the engine. The badge only knows how to spell a gate.

For loyalty it names the trader only when the trader is not the giver. 89 of the 94 quests name their own trader, and the row already shows that trader. So LL2 is complete on those rows, and stays as narrow as Lv.15. The five that name somebody else get the name, as Jaeger LL2.

TarkovHelper/Pages/QuestRequirementBadge.csFor
internal static string? For(
    QuestGate gate,
    TarkovTask task,
    ProfileSettingsSnapshot settings,
    Func<QuestTraderRequirement, string> traderDisplayName)
{
    switch (gate)
    {
        case QuestGate.PlayerLevel:
            return $"Lv.{task.RequiredLevel}";

        case QuestGate.ScavKarma:
            return $"Rep {task.RequiredScavKarma:0.#}";

        case QuestGate.TraderLoyalty:
        {
            var loyalty = QuestProgressService.FirstUnmetTraderLoyalty(task, settings);
            if (loyalty == null) return null;

            // The trader's name only when it is NOT the quest's own.
            return QuestProgressService.IsGivenBy(task, loyalty)
                ? $"LL{loyalty.Level}"
                : $"{traderDisplayName(loyalty)} LL{loyalty.Level}";
        }

        // ... and the Unavailable gates, spelled the same way: RequiredEdition as
        // "EOD" or "Unheard", ExcludedEdition as "Edition", PrestigeLevel as
        // "P.{n}", Faction as "BEAR" or "USEC" ...

        default:
            return null;
    }
}

A null is not a blank badge. StatusText wraps this and falls back to the status word. So Active, Done, Failed and Locked read as themselves. A gate with no value to show still says Level or N/A.

Every pane passes the gate the same GetStatus call reported. The list row, the detail pane, the prerequisite rows and the alternative-quest rows therefore cannot disagree. Before this, four of seven call sites passed no task and read the literal Level.

04

One row for each trader

Where the entered levels are kept, why they are keyed by trader id, and why the profile reset needed no change.

The entered levels are profile data. They belong beside the player level, the Scav Rep and the prestige level. Those live in the ProfileSettings table, one row for each key, partitioned by profile.

Loyalty is the first value there that is not one row. It is one row for each trader, under a common prefix. The key is app.traderLoyalty. and the tarkov.dev trader id.

The alternative was one row holding a map of every trader. Per trader rows need no serialization format. They cost one write for each edit, on the write path every other value already uses. They come back through the same bulk read, and a person can read them in the table.

The key is the trader id and not the trader name. The requirement rows carry the id, the gate compares by id, and a nickname can change upstream. The API already renders Mr. Kerman and Radio station. The name is looked up for display through the Traders table, which the drawer needs anyway for Korean and Japanese.

The reset did not change at all

A complete profile reset deletes every ProfileSettings row whose key is not on an allowlist. The allowlist holds the two edition keys, because the editions describe what the account owns. Deletion is the default, so a prefix of new keys is wiped without the reset learning anything. That is the whole reason the reset code is not in this change.

The read path is where the rows become a value. Every bounded setting is clamped there, and loyalty is clamped there too, to the range 1 to 4. The setters have always clamped, so no row the app wrote can be out of range. A row can still be out of range, because ProfileSettings is a plain SQLite table that a person can edit by hand.

TarkovHelper/Services/Settings/ProfileSettingsSnapshot.csReadTraderLoyalty
private static TraderLoyaltyLevels ReadTraderLoyalty(IReadOnlyDictionary<string, string> values)
{
    var entries = new List<KeyValuePair<string, int>>();

    foreach (var (key, stored) in values)
    {
        if (!key.StartsWith(SettingsService.TraderLoyaltyKeyPrefix, StringComparison.Ordinal))
            continue;

        var traderId = key[SettingsService.TraderLoyaltyKeyPrefix.Length..];
        // A row keyed on the bare prefix names no trader, so it is dropped.
        if (traderId.Length == 0) continue;
        if (!int.TryParse(stored, out var level)) continue;

        entries.Add(new KeyValuePair<string, int>(
            traderId,
            Math.Clamp(
                level,
                SettingsService.MinTraderLoyaltyLevel,
                SettingsService.MaxTraderLoyaltyLevel)));
    }

    return entries.Count == 0 ? TraderLoyaltyLevels.Empty : TraderLoyaltyLevels.From(entries);
}

A row for a trader the current data gates nothing on is kept. It costs nothing, because no gate reads it. It is also the mechanism the drawer depends on: the publish that starts gating on that trader finds the entry already there.

05

A map the record can compare

Why the ninth value is a small type of its own, and not a dictionary.

ProfileSettingsSnapshot is a record. Its value equality is what the setter contract asserts. Each of the nine setters is driven, and the test compares the whole snapshot with the one it expects. That single comparison says the setter changed its own field, and left the other eight alone.

A Dictionary member breaks that comparison quietly. A record compares a reference member by reference. Two snapshots holding equal maps in different instances would read as different. Two snapshots sharing one instance would read as equal, whatever the map holds. Every assertion of that kind would then pass for the wrong reason. ImmutableSortedDictionary compares by reference as well.

So the map is a small type that owns its own comparison. TraderLoyaltyLevels holds a sorted map, compares by structure, and hashes by structure. That keeps the record honest with no change to the record.

The type earns a second thing. With returns the same instance when the level does not change. The setter's guard is therefore a reference check, and re- setting a level a profile already holds skips both the publish and the write. That is the same no-op guard the eight scalar settings get from comparing two integers.

TarkovHelper/Services/Settings/TraderLoyaltyLevels.csWith
internal TraderLoyaltyLevels With(string? traderId, int level)
{
    if (string.IsNullOrEmpty(traderId)) return this;
    // The same instance for an unchanged level: the setter's no-op guard is a
    // reference check, so this identity is what skips the publish and the write.
    if (_levels.TryGetValue(traderId, out var current) && current == level) return this;

    var next = new SortedDictionary<string, int>(_levels, IdComparer) { [traderId] = level };
    return new TraderLoyaltyLevels(next);
}
06

The roster comes from the data

Which traders the drawer offers, and the one number the app still hard codes.

The drawer shows one input for every trader that at least one loaded requirement row names. That is seven traders today. The list is computed from the rows during the quest load, inside the same swap that publishes the quests. So no reader sees new quests beside an old roster.

A fixed list of the seven was rejected. The day the API publishes loyalty for the seasonal quests, or Ref gains a gated quest, a fixed list needs an app release to grow. Until that release the gate would lock quests behind a trader the player cannot enter, which is the worst state of the three. With the roster in the data, a data publish alone grows the drawer.

All sixteen traders was rejected as nine inputs that nobody uses. Fence is not in the roster either. Fence standing is the Scav Rep input, which the roadmap decided.

The order is the game's order, and it is hard coded. TraderDbService.DisplayRank holds it, because the Traders table carries no sort column and alphabetical order puts Jaeger before Prapor. A trader the order does not name sorts last, and is still shown. The order decides display only.

Four is a constant, and a test keeps it honest

Every trader with loyalty levels has exactly four, and the game has never had a fifth. Publishing a per trader maximum needs a pipeline change and a data publish, to carry a number that has not moved. The gate itself never needs the bound, because it compares integers. Only the input needs it. A content test over the published database fails when a requirement asks for more than four. That is on the publish PR, and long before a player sees it.

The quest loader keeps such a row rather than dropping it. Dropping it would open a quest the game still gates. It logs a warning instead, saying the app's ceiling has fallen behind the game's.

07

The value that announces nothing

The one place the specification was wrong, found while the drawer was built.

A profile switch reloads the settings and announces them. RaiseProfileSettingsChanged sends one event for each of the seven single-key values the drawer renders, and the drawer repaints one control on each event. That works because each of those seven is sent on every publish, whether the profile has a row for that value or not. A profile with no stored level still sends PlayerLevelChanged, carrying the default. There is an eighth single-key value, ShowLevelLockedQuests. It announces nothing and is wired to no control, so the drawer never had to hear about it.

Loyalty cannot do that. It is a family of rows, so the fan-out sends one event for each stored entry. The specification chose this, and it is right for what it is: a reload has no idea which traders the loaded data even gates on, and a trader with no row answers the default without being told.

But it leaves a hole, and the hole is the common case. A profile that has entered no loyalty announces no loyalty event at all. A drawer listening only to that event would therefore keep the previous profile's levels on screen, under the new profile's name. A complete profile reset produces the same state, because it deletes every one of those rows.

What that shows the player

The quest list is right and the drawer is wrong, at the same time. The list reads the snapshot, so it locks the quests again. The drawer still shows Prapor at 4. The player reads a drawer that says the levels are entered, beside a list that says they are not.

The fix is one more announcement, sent once for each published fan-out and never for a single edit. ProfileSettingsReloaded carries nothing. It says that a whole snapshot was published. A reader that must repaint from the snapshot then has a signal that arrives whatever the snapshot holds.

It is sent last, and under the same liveness guard as the value events. A fan-out for a snapshot the cache has already moved past announces nothing, and this signal is part of that nothing. Otherwise a reader would repaint from a snapshot that is no longer the live one.

TarkovHelper/Services/SettingsService.csRaiseProfileSettingsChanged
        Announce(() => PrestigeLevelChanged?.Invoke(this, snapshot.PrestigeLevelOrDefault));

+       // One announce per STORED entry, not one per trader in the drawer's roster: a
+       // trader with no row answers the default without being told.
+       foreach (var (traderId, level) in snapshot.TraderLoyalty.Entries)
+       {
+           Announce(() => TraderLoyaltyChanged?.Invoke(this, new TraderLoyaltyChange(traderId, level)));
+       }

+       // Last, and under the same guard: a reader that has to repaint from the snapshot
+       // rather than from a value it was handed needs one signal that arrives whatever
+       // the snapshot holds.
+       Announce(() => ProfileSettingsReloaded?.Invoke(this, EventArgs.Empty));

        void Announce(Action raise)
        {
            // The question is re-asked before EVERY event, because each handler can block
            // the raising thread for as long as the dispatcher takes to run it.
            if (!ReferenceEquals(Volatile.Read(ref _profileSettings), snapshot)) return;
            raise();
        }

The drawer hears both signals, and repaints once for the pair. A seven trader profile switch sends seven TraderLoyaltyChanged events, and then ProfileSettingsReloaded. Every one of the eight repaints the whole drawer from the same snapshot. So both handlers book one shared RefreshCoalescer instead, the same collapse the quest list uses. The burst arrives in full, and the drawer is painted from the snapshot once.

The quest list needs none of this. It subscribes to the per trader event for the single edit, and PlayerLevelChanged already books its collected refresh on every publish. Only the drawer must read the snapshot, because only the drawer draws a control for a trader that may have no row.

08

Two bounds the patch outgrew

The audit the roadmap gave this phase, and the test that replaces the next one.

The drawer's inputs carry hard coded bounds, and the data they are judged against is published separately. The two drift, and nothing watched them. The audit was judged against the upstream game data and the wiki on 7 September 2026.

Two bounds moved. The prestige input stopped at 5, and patch 1.1 added prestige 5 and 6. There are six prestige entries upstream and six New Beginning quests on the wiki. So the maximum is now 6.

Fence reputation can fall to -7 in the game, and the Scav Rep input stopped at -6. The reputation bands start at -7. So the floor is now -7.0.

The rest are confirmed unchanged. The level cap is still 79, because the upstream level table has seventy-nine entries. The DSP decode count stays 0 to 3. The edition values the data carries are the ones the app already reads.

Widening a constant is the whole change for each. The read clamp, the setters, the legacy import and the drawer all read them, and nothing stored moves. A build that predates this clamps a stored -7.0 to -6.0 when it reads it. It does not rewrite the row, so the value returns on the next upgrade.

The audit is now a test run

ProfileBoundsCoverDataTests reads the published database. It asserts that every minimum level, prestige requirement, Scav karma, decode count and edition value is one its input can be set to. The edition case asks the gate itself, and not a copy of its strings, because that gate fails open: an edition it does not recognise shows its quests to every player. The next patch's audit is a test run.

The published data cannot pin the two bounds that moved. It carries no prestige requirement above 3 and no karma requirement below -3. Both bounds describe the player's own character, and not a demand that a quest makes. Those two are pinned as values, in SettingsSetterContractTests, so moving a constant back fails.
