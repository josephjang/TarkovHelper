PR #60 · Code guide

One Kappa number, and a page that says what holds Collector

Part 1 of the Kappa and Collector guides, and the last phase of the EFT 1.1 roadmap. It continues the trader loyalty guides (docs/2026-09-quest-loyalty-gating-code-guide.html and its deep review), and it rests on the data that arrived in docs/2026-08-quest-data-1-1-refresh-code-guide.html.

The decisions are in docs/decisions/feature-kappa-collector-1-1.md and its spec, which this PR appends to. No data is published. Every value the page shows is in the database every install already has.

The whole change

The Collector page now shows Collector's status, every unlock condition with its value, and the Kappa count. Every Kappa count in the app is one number with one label, counted inside a render pass. Two wrong labels are gone, and two dead methods with them.

01

What 1.1 already published

The data and the gate were in place before this phase. What was missing was on the screen.

Patch 1.1 cut the Kappa set from 248 flagged quests to thirteen. Collector is one of the thirteen. The other twelve are its prerequisites. The data refresh, phase 3 of the roadmap, published Collector's row as the game has it: player level 42, Scav karma 3, seven traders at loyalty level 4, and twelve prerequisite rows.

The loyalty phase, phase 4, made the gate uniform. Collector is gated on all of those conditions by the same walk every other quest goes through. On a fresh profile the walk answers, in order: Locked, then Lv.42, then Rep 3, then Prapor LL4, then Active. The status engine did not change in this phase.

The app shows what the data says, as the refresh decided for every disagreement.

02

Two labels and a silent page

The numbers were right. The words around them were wrong, and one page said nothing.

Collector's detail pane counted the thirteen flagged quests and wrote "Prerequisites: (x/13 completed)" over them. Collector has twelve prerequisites. The thirteenth quest is Collector itself. Under the old data, with 248 flagged quests, nobody noticed. At thirteen, a player who had done all twelve read "12/13" and went looking for the one they had missed.

The Collector page had the mirror problem. With its option off, its stats line ended "Kappa Quests Only" while it listed Collector's own items and nobody else's. Under 1.1 "Kappa quests" names the thirteen, a set the page never lists. The option itself read "Include Pre-Quest".

And the page said nothing about Collector. It listed the hand-over items and their counts, 43 of Collector's 44 published rows. A player who had finished the twelve kept ticking items off there, while the quest tab one click away said Prapor LL4. The loyalty phase recorded that gap as an accepted risk until this phase.

The count that read live singletons

The quest tab draws its rows, its chips and its detail pane from one captured RenderPass. So a profile switch cannot mix two profiles on one screen. The Kappa gauge beside the chips did not. It re-ran a status walk per flagged quest against the live singletons. During a switch the gauge could describe one profile while the chips next to it described another.

03

One count, inside the pass

The flag decides membership. The caller decides "done", against its own pass.

GetCollectorProgress became GetKappaProgress, and its predicate takes the task instead of the task's name. The body did not change: the game's flag is the membership rule, Collector included, and the percentage is an integer. What changed is who answers "done". The caller answers it against the render pass it drew everything else from.

TarkovHelper/Services/QuestGraphService.csGetKappaProgress
+   private IEnumerable<TarkovTask> KappaQuests()
+       => _tasks!.Where(t => t.ReqKappa && !string.IsNullOrEmpty(t.NormalizedName));

-   public (int Completed, int Total, int Percentage) GetCollectorProgress(Func<string, bool> isQuestCompleted)
+   public (int Completed, int Total, int Percentage) GetKappaProgress(Func<TarkovTask, bool> isDone)
    {
        EnsureInitialized();
+       var kappaQuests = KappaQuests().ToList();
+       var completedCount = kappaQuests.Count(isDone);
        var total = kappaQuests.Count;
        var percentage = total > 0 ? (completedCount * 100 / total) : 0;
        return (completedCount, total, percentage);
    }

Three surfaces call it, and each answers the predicate from its own pass. The detail pane counts within the pass that built the rest of the pane. The list button captures one pass at the click, for its header and for its rows. The gauge is the one that differs, and the spec's wording had to be read against the code.

The gauge counts within the pass the rows were built from

The spec said the gauge counts "from the pass ApplyFilters already captured". ApplyFilters captures no pass. The two methods that do build the row statuses, LoadQuests and RefreshQuestStatuses, capture through one seam, CaptureRowPass, which remembers the pass in _rowPass. The gauge counts inside that remembered pass, through the same pass.KappaProgress() reading the detail pane and the list window ask for. So it is one reading of one profile, and the gauge has no done-source of its own. This is TD8 in the spec.

Counting the statuses cached on the row view models was tried first and rejected. It answered for the flagged quests that happen to have a row, not for the flagged set. And an ApplyFilters that ran before the first LoadQuests read an empty row list as "none done". That profile had done some of the thirteen. KappaGaugeSourceTests pins both.

RenderPass moved out of the quest page into a file of its own, with a static Capture. Three pages capture one now: the quest page, the Collector page and the Items page.

The Items page is the third, and it joined at the review. Its item list and its detail pane each read a live status per quest, against two snapshots that background work republishes together. A publish landing mid-walk left the list mixing two profiles, and the pane naming quests the listed rows had not counted. The page captures one pass per load now, in _listPass, and both halves answer from it (ItemsPageRenderPassTests, TD22).

The pass answers the readings, so no page can forget the guard

The implementation left each surface to spell its own reads over the pass: a private StatusIn(pass, task), and a private KappaProgressIn/KappaQuestsIn pair carrying the IsInitialized check. That came to four copies of the Kappa pair across two pages. Nothing stopped a fifth from forgetting the check. A forgotten check paints "0/0" over a graph that is not built yet, which is the one thing the check exists for.

The reads live on the pass now: StatusOf, IsDone, and the nullable KappaProgress() and KappaQuests() with the guard inside them. Null means "no reading", and never a zero. The graph they are answered from is a private field, set at the capture. A surface holding a pass cannot reach past it for a live one.

That also made the pass a sealed class rather than the readonly record struct it started as. With two services in it, the pass is a read context and not a value. Equality over service references would mean nothing, and default(RenderPass) stops being spellable. This is TD17 in the spec, and RenderPassStatusGuardTests now names the only files under Pages/ allowed to ask the service for a status. A new page that reads one live fails a test instead of passing review.

04

A panel with no rule of its own

The badge, the lines and the count already existed as pure functions. The panel composes them.

The loyalty phase left two helpers that this phase needed exactly. QuestRequirementBadge.StatusText formats the gate the walk reported. RequirementLineViewModel.BuildFor builds one line per condition, in the badge's own order, with a met or unmet colour. Both are pure functions of the task and one settings snapshot.

CollectorUnlockViewModel.BuildFor composes them with the count. It contains no comparison of its own. Which condition holds Collector is the engine's answer, carried in the gate. The badge and the first unmet line agree because both derive from it. A Collector-specific "met" rule would have been the second copy of the gate rule the loyalty phase removed. That is TD1.

Non-nullable in and out, with one exception on purpose. "The loaded data has no Collector quest" is the page's case, not the builder's. RebuildUnlockPanel collapses the panel and returns before it asks for a view model. So there is always a panel to build. The nullable return the builder carried was a second guard behind that one, and unreachable. The page discarded it with a ! anyway.

The count is the exception, and it is an option rather than two ints. Null is what pass.KappaProgress() answers when the graph is not built. The panel then writes no count, and hides the button that would open an empty list. "0 of 0" is a reading the page does not have, and it would read as "nothing is flagged" (TD17).

The page captures one pass per load and hands it to three consumers: the item aggregation, the detail panel's quest sources, and the panel. So the list and the panel above it describe one profile.

The two near-identical "quests in scope" computations became one CollectorScope.QuestsInScope, with the same three exclusions as before: Done, Failed and Unavailable. It takes the status as a delegate, which the page answers from its pass. So the rule cannot reach past that pass for a live reading.

That scope answer is walked once per load, not once per selection. The load keeps it in a ListScope record, with the pass and the "include prerequisites" option. The quest sources and the stats line's scope word read that stored scope. Neither reads the live checkbox again (TD13).

Rules the unit suite could not run

Five rules decide what this list holds: the quests in scope, their listed rows, the currency items, the totals, and the aggregate they fill. All five were private members of a WPF control, and nothing ran them. The page cannot be constructed in the unit suite, because its markup resolves App.xaml's brushes and its field initializers open the databases. What covered them was indirect: a guard reading the page's own source, and e2e flows that assert a rendered list.

They read no service and touch no control, so they moved to Services/CollectorScope.cs, with the per-item aggregate they fill to Models/CollectorQuestItemAggregate.cs. The page keeps what is genuinely its own: ListScope, CaptureListScope, which is the one place the checkbox is read, FindCollector, and two one-line wrappers that supply its own inputs. Behaviour did not change, which is why the twenty cases of CollectorScopeTests could be written against it: they are the first to run these rules at all. That is TD18.

Shown, never counted

The seven loyalty levels, the karma and the level are values the player typed into the drawer. They are shown as met or unmet, and they never enter the Kappa number. A 21-item gauge was rejected: a click in the drawer would move a "progress" bar, and a player who prestiges would watch Kappa progress go backwards without failing a quest. That is PD1. And the panel sits above the item list, not instead of it (PD3).

05

Four events, one rebuild

The page subscribes to what can change the panel, and collapses a burst into one repaint.

The quest page consumes eight settings events. The Collector page consumes four: the player level, the Scav Rep, a trader loyalty change, and the profile settings reload. The five it skips are the two edition events, the prestige level, the DSP decode count and the faction. That is TD4.

The reason is not that the page ignores those values. The item list reads three of them transitively. Its scope drops a quest whose status is Unavailable, and that is what an unmet edition, prestige or faction gate produces. It reads them for every quest in the scope, and not only for Collector.

What keeps the list insensitive is the published data: no quest in Collector's prerequisite closure carries one of those gates. The DSP count cannot matter either way, since its gate reads Locked, and Locked stays in scope.

So the decision rests on a data fact, and the review gave that fact a guard: PublishedDataContentTests.The_quests_Collector_depends_on_carry_no_edition_prestige_or_faction_gate. It walks the closure in the published file and asserts that no row in it is gated. When that case fails, this page needs those five events, and its settings refresh has to reload the items rather than the panel alone.

The reload is not redundant with the other three. A profile that has entered no loyalty levels raises no loyalty event at all. The reload closes the burst it belongs to, so it joins the same coalesced refresh rather than booking one of its own.

A published profile announces the level, the rep, one loyalty event per stored entry, and then the reload. For a seven-trader profile that is 1 + 1 + 7 + 1 = ten events this page listens to, over one snapshot. RefreshCoalescer turns that burst into one rebuild. The first request books a refresh on the dispatcher at background priority, and the rest of the burst joins it. The pending flag is cleared before the refresh runs, so a change landing during it books a second pass.

Why the subscription test reads the source

The spec asked for the page constructed on an STA thread. The page cannot be constructed in the unit suite: its markup resolves App.xaml's brushes, and its constructor reaches six singletons that open the databases. So CollectorPageSubscriptionTests reads the source, the way MainWindowTeardownTests does.

It pins which four events are subscribed. It pins that each handler is a one-liner over the coalescer. It pins that one load captures one pass, and threads it to the scope and to the panel. "Every status comes from a pass" outgrew this page and is a guard over the whole Pages/ directory now (RenderPassStatusGuardTests, TD17). The burst rule itself is RefreshCoalescerTests. That is TD11.

The window and the brushes

Three small moves, so two pages can share what one page owned.

The Kappa quest list was a window built inline in a click handler on the quest page. The Collector page opens the same list, so the window moved to KappaQuestListWindow with one static entry point. It takes the owner, the rows and the strings source, and nothing else. Each button hands it its own pass, so the list is the same list from either place (TD5).

TarkovHelper/Pages/Components/KappaQuestListWindow.csShow
+   internal static void Show(
+       Window? owner, IReadOnlyList<(TarkovTask Quest, bool IsDone)> quests,

The count and the name resolver are gone on purpose. The header's pair is counted from the rows the window was handed (HeaderText). Each row's name comes from loc.GetQuestName. So no caller can hand the window a number or a name from another list. And neither click handler walks the flagged quests a second time for one.

A null owner is allowed, for a caller with no window, and the window then centres on the screen. WPF's CenterOwner is not owner-null tolerant, and leaves an ownerless window where the OS cascades it. KappaWindowListTests pins the header, the names, the placement rule, and the count neither page asks for again.

The six status brushes moved out of the quest page into QuestStatusBrushes. The Collector page's badge now reads the same six, rather than a copy that could drift a shade. They are frozen at construction. A frozen brush may be read from any thread. So the first page to touch the class does not tie the brushes to its own dispatcher. QuestStatusBrushesTests pins one distinct frozen brush per status and the Gray fallback (TD10).

The condition lines have two colours of their own. Both builders took them as a metBrush/unmetBrush pair, spelled at each call site. That is how two pages came to name one resource key twice. They travel together now, as RequirementLineBrushes with a FromResources(owner) that reads the theme's text colour and the badge's own locked orange.

It is read from an element, rather than kept beside the frozen brushes, and that is on purpose. "TextPrimaryBrush" is an App.xaml resource, so resolving it needs a live element and a dispatcher. The builders still take the pair as an argument. A test can then hand in two sentinels, and assert which one a line got.

08

What the walk's comment hid

A whole dead file, one wrong comment, and the defect the comment had covered.

GetKappaPath and GetKappaItems had no caller since the todo that added them. They are named after the "Kappa Path" achievement, which patch 1.1 retired; players who complete Collector now earn "Dawn of a New Era". The Collector page's option already lists the items across the twelve quests. Keeping them "in case" was rejected: a planner is a new change with its own proposal (TD6).

The review found three more dead members on one chain. ItemRequirementService.GetItemsForQuestPath has no caller at all. It was the only caller of QuestGraphService.GetOptimalPath, which was the only caller of the private TopologicalSort. The spec had recorded TopologicalSort as staying, on a count of direct references. Following the chain end to end shows every one of those references to be dead too, so all three go.

Widening the sweep one step further took the rest of that file with them. Nothing in the solution names ItemRequirementService outside its own 352 lines: no code, no XAML, no nameof, no source guard that reads a file by path, and nothing in tools/DataDiff. Nothing constructs the singleton or calls its Initialize. Its four result types have no user either, so no remaining member needs them.

The file is deleted whole rather than two members of it, and the build and the green suite are what validate that. No test asserts a deleted type is absent, because that assertion holds whatever the code does.

Deleting them meant reading the prerequisite walk they used. Its last line carried a comment: Add the task itself only if it's a prerequisite (not the target). The code under it adds the task unconditionally. The target quest has always been the last entry of that walk. The comment was corrected, and every caller was read.

At the review the contract moved into the name (TD16). The walk is two members now. GetPrerequisiteClosure answers the closure, and the target is its last entry. GetAllPrerequisites answers what its name promises, which is the same walk without the target. Each caller reads the member it meant, so no call site has to compensate.

The caller that trusted the comment

A "quest started" log event plans a batch completion over that walk. The plan's own comment says the started quest stays Active and only its prerequisites are recorded. The batch planner marks every entry it is given Done, and the walk it was handed ended with the started quest. So every quest the live log sync saw a player start was recorded as finished. The main window routes every event type through this path, and nothing had covered the Started path.

That first fix dropped the target here, with a Where clause over the answer. The review replaced the clause with the rename, so the call site asks for the prerequisites and gets them. Graph is the seam the tests set, and it defaults to the singleton. PrerequisiteWalkTests pins both members, and Lab D below drives the two consumers that need opposite answers.

The denominator that stopped at startup

Reading the Kappa count end to end turned up a second defect off this theme. The count is read from QuestGraphService. That service and QuestProgressService are the only two caches that do not reload themselves on a data publish. They are handed their tasks once, at startup. So an hourly publish left every quest surface and the Kappa denominator on the previous publish until restart, beside a freshly reloaded item table.

MainWindow's QuestDbService.DataRefreshed handler owns the republish now. It calls QuestProgressService.PublishTasks(tasks) and QuestGraphService.Instance.Initialize(tasks) before it rebuilds the loyalty roster from them. PublishTasks is a new split out of Initialize, and it indexes the tasks and nothing else. A publish changes which quests exist, never which rows the player recorded. The rows are keyed by id and normalized name, not by task instance, so re-reading progress here would block the dispatcher for no gain.

An empty reload is a failed load, and keeps the task set that is on screen. Hideout modules stay out on purpose, and that gap is recorded where the publish channel is designed. That is TD19, pinned by PublishTasksTests and by a source guard over the handler's order.

What this leaves open

The manual check at the 600 pixel minimum window found the panel wrapping onto three rows with nothing clipped. The badge showed in the app's own orange. It also found the list showing 43 items, of Collector's 44 published rows.

The row for the LM KC-130 model aircraft carries no item id. QuestDbService.LoadQuestRequiredItemsAsync drops such a row at load, since it cannot be matched to the Items table. So it never reaches the aggregation, and is invisible rather than listed by name. That is a data gap for a data publish, unchanged by this phase, and the spec's Context says so.
