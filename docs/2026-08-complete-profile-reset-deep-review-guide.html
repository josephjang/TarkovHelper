PR #42 · Code guide, part 4

The gaps in an airtight reset

PR #41 shipped a reset built on structural guarantees: a transaction that cannot half-run, a barrier no write can bypass, a fence no sync can cross. The deep review asked one question of every guarantee: what happens at its edge? This guide walks the defects that question found, and the fixes, with three labs where you drive the failure and then the repair.

Part 4 of the profile series. Part 1 covered attribution, part 2 its deep review, part 3 the complete reset this review targets. The fixes land in PR #42, stacked on the PR #41 branch. Companion to docs/decisions/feature-complete-profile-reset.spec.md.

The whole change in one sentence

Every guarantee PR #41 made was real, but its mechanisms had unexamined edges: the barrier helper ran SQLite on the very threads it existed to protect, its drain could wait forever behind a dialog that refuses to close, the debounced flush hid pending writes from the reset that must discard them, and the first-run migration could race itself into a blank screen; PR #42 bounds, orders and serializes those edges, makes the failure states honest, and pins all of it with 63 new tests.

01

The review, in numbers

The diff under review was already green: 537 tests, clean build, spec and PRD merged alongside. A deep review of green code hunts what tests do not see: edges, waits, races, and sentences that are not quite true.

The review ran nine finder angles over the PR #41 diff (line-by-line triage, removals, design, altitude, ripple, language footguns, efficiency, duplication, conventions), deduplicated their candidates, and then verified every survivor against the code: no finding was fixed on plausibility alone, and no finding was dropped without a written reason. Everything first deferred was re-audited adversarially; three questions only the author could answer were asked and answered, and the answers are recorded in chapter 08.

Every candidate ends in exactly one of three states: confirmed and fixed (with a test that failed before the fix where one was expressible), refuted with a concrete proof (a call chain, a probe, a disproved premise), or escalated as a decision with options and a recommendation. The angle that was skipped, wrongly

The triage skipped the WRAPPERS angle because the diff adds no classic wrapper type. The skip was literally correct and still wrong: the angle's question is "does the wrapper forward everything its callers rely on?", and TrackedUserDataWrites is exactly such a claim. Its doc said the ordering guarantee was structural with "no call-site discipline to erode"; in fact SettingsService.SaveProfileSetting writes a profile-owned table without ever passing through it. A later sweep recovered the finding, and the doc now names the exception instead of denying it. Nothing resurrects through that path today, but a comment that overstates a guarantee is a defect in its own right: the next engineer builds on what the comment promises, not on what the code does.

02

The offload that vanished

The severest finding was created by the barrier itself. Wrapping four writes in the new helper deleted the Task.Run they used to live in, and nothing said that offload was an invariant.

Before PR #41, the fire-and-forget saves in QuestProgressService and EftRaidEventService ran inside Task.Run. PR #41 replaced those call sites with TrackedUserDataWrites.Run(...) to gain the reset barrier, and the offload went with the deleted lines:

three eras of one call sitewhere the offload lives
// Before PR #41: the offload is the only thing keeping SQLite off this
// thread. Nothing names it as an invariant.
_ = Task.Run(() => SaveProgressBatchAsync(changes));

// PR #41 as merged: barrier gained, offload silently lost. RegisterAsync
// returns WITHOUT YIELDING when no reset is running, and Microsoft.Data.Sqlite's
// *Async methods run synchronously, so the whole open-and-write executes on the
// caller: the WPF dispatcher for ResetQuest's click handler, and the log-poll
// thread inside lock (_readLock) for raid saves.
_ = TrackedUserDataWrites.Run(profileId, () => SaveProgressBatchAsync(changes));

// PR #42: the offload is restored INSIDE the helper, once, for every caller.
public static async Task RunLoggingFailures(string profileId, string description, Func<Task> op)
{
    try
    {
        await RunTracked<object?>(profileId, async () =>
        {
            await Task.Run(op).ConfigureAwait(false);  // op runs on the pool, never the caller
            return null;
        }).ConfigureAwait(false);
    }
    catch (Exception ex)
    {
        _log.Error($"Tracked user-data write for {profileId} failed: {description}", ex);
    }
}

"Async" does not mean "on another thread": an async method runs synchronously on its caller until its first genuine yield, and neither the no-barrier fast path nor Sqlite's I/O ever yields. The suite stayed green throughout because tests assert what is written, not where the writing thread came from. The fix puts the offload where the barrier already is, inside the helper, so every current and future call site inherits both; the propagating twin (RunPropagatingFailures) deliberately does not offload, because its callers are already async and awaiting the result, and an extra hop would only reorder their continuations. A_fire_and_forget_write_does_not_run_on_the_callers_thread now pins the property the deleted lines used to provide for free.

The removals lesson

For every line a diff deletes or replaces, name the invariant it enforced and point at where the new code re-establishes it. Here the invariant was unnamed, so the substitution looked like pure win: same write, plus a barrier. The review's REMOVALS angle exists precisely because the most dangerous deletion is the one that looks like a refactor.

03

Nothing bounded the wait

The reset drained in-flight writes with an unbounded await, behind a modal dialog whose whole job is to refuse dismissal while the reset runs. Two correct designs, composed into a trap.

Each piece was defensible alone. The drain awaits every registered write, because proceeding past one is how rows get resurrected. The dialog refuses to close mid-run (its OnClosing cancels the close), because closing would take the outcome message with it, and the Close button, Alt+F4 and Application.Current.Shutdown() all route through OnClosing. Compose them with one write that never completes, a wedged connection, an antivirus hold, and the result is a modal that nothing on the machine can dismiss, over a MainWindow that ShowDialog() has disabled. Task Manager becomes the only exit.

The fix bounds every wait in the chain, and the order of the timeout handling is the part worth reading twice:

TrackedUserDataWrites.BeginResetAsyncthe drain, bounded
try
{
    await Task.WhenAll(inFlight).WaitAsync(Remaining()).ConfigureAwait(false);
}
catch (TimeoutException)
{
    // The barrier is already up at this point. Lower it before reporting the
    // failure, or every later write for this profile would wait on a barrier
    // nobody will release.
    await new ResetHandle(state, barrier).DisposeAsync().ConfigureAwait(false);
    throw new TimeoutException(
        $"Timed out after {timeout} draining {inFlight.Count} in-flight write(s) for {profileId}. " +
        "Nothing was removed.");
}
  • The drain gets 30 seconds (DefaultDrainTimeout). A tracked write is a handful of short SQLite statements; a wait anywhere near the bound means wedged, not slow.
  • The store transaction gets its own 30 seconds (ProfileResetService.StoreTimeout), and MaxDuration publishes the sum so the UI can size its own bound against it.
  • The dialog keeps a backstop: CloseRefusalLimit = MaxDuration + 15 s. If even the bounded path wedges, the window starts accepting close again; losing one outcome message beats a modal nothing can dismiss. If the reset then finishes after the force-close, the outcome goes to the log rather than a dead window.

04

Writes the discard could not see

The reset discards the target's pending debounced saves before deleting. The flush that persists those saves began by making them invisible to everything, including the reset.

ItemInventoryService debounces edits through a 500 ms timer into _pendingSaves, a map of item name to the profile that owned the edit. As merged, the flush's first move was to snapshot the map and clear it, then walk the snapshot and register each entry's tracked write one by one. Between the clear and an entry's own registration, that entry existed only in a local list inside the flush: not in the map, where DiscardPendingSaves could sweep it, and not registered, where the barrier's drain could wait for it. A reset arriving in that window deleted the rows, then watched the invisible entries write them back.

The fix inverts the bookkeeping: nothing is cleared up front, and each entry is claimed from inside its own tracked write, after that write has passed the barrier:

ItemInventoryService.SavePendingItemsAsyncthe claim, abbreviated
await TrackedUserDataWrites.RunLoggingFailures(profileId, $"item inventory {itemName}",
    async () =>
    {
        lock (_lock)
        {
            // The claim, made only now that the barrier has been passed and this
            // write is registered against it. A reset that got in first removed the
            // entry: writing it back would be the resurrection the barrier exists
            // to stop. A re-dirty under a different profile belongs to that
            // profile's own pending write.
            if (!_pendingSaves.TryGetValue(itemName, out var pending)
                || !string.Equals(pending, profileId, StringComparison.Ordinal))
            {
                return;
            }
            _pendingSaves.Remove(itemName);
            // ... snapshot the quantities under the same lock ...
        }
        await _userDataDb.SaveItemInventoryAsync(itemName, firQty, nonFirQty, profileId);
    });

The invariant, stated once

At every instant, a pending entry is visible to exactly one authority: the map (where a reset's discard can sweep it) or the barrier (where the drain waits it out). There is no third place. The old flush created a third place and kept entries there across whole SQLite round-trips.

05

First launch, twice

The RaidHistory owner column arrives by migration, and the migration ran behind a guard that was neither volatile nor synchronized. The first launch after upgrading is exactly when several threads race init.

UserDataDbService.InitializeAsync guarded its work with a plain if (_isInitialized) return;. Five entry points can trigger init concurrently on startup, and PR #41 made the ALTER TABLE for RaidHistory.AppProfileId the first non-idempotent DDL in the sequence: CREATE TABLE IF NOT EXISTS shrugs at a second run, but a second ALTER TABLE ADD COLUMN is an error by design. The loser of the race threw duplicate column name, and the exception surfaced in the worst imaginable disguise: QuestProgressService.ReloadForProfileAsync catches init failures, logs them, and publishes an empty quest map. On the first launch after upgrading, the player's every quest showed un-completed while the database sat intact underneath.

UserDataDbService (PR #42)serialized init, idempotent migration
public async Task InitializeAsync()
{
    if (Volatile.Read(ref _isInitialized)) return;   // fast path only
    await _initLock.WaitAsync().ConfigureAwait(false);
    try
    {
        if (Volatile.Read(ref _isInitialized)) return;   // the decision, under the lock
        // ... open, CreateTablesAsync (includes the migration) ...
        Volatile.Write(ref _isInitialized, true);
    }
    finally { _initLock.Release(); }
}

// The migration: pragma check first, and the race window that remains (another
// PROCESS can add the column between check and ALTER) is re-checked rather than
// pattern-matched on the message:
catch (SqliteException ex) when (ex.SqliteErrorCode == SqliteGenericError)
{
    if (!await HasRaidHistoryOwnerColumnAsync(connection).ConfigureAwait(false)) throw;
    _log.Info($"RaidHistory.AppProfileId was added concurrently: {ex.Message}");
}

Two details carry the design. The semaphore serializes threads inside one process, but SQLite files are shared with other processes too, so the ALTER must additionally treat "someone else already added it" as arrival rather than failure; the shared error code forces a re-check instead of a message match, and anything else with the same code (no such table) still throws. And every await in the init chain gained ConfigureAwait(false), because the synchronous entry points block on this task, and resuming on a captured UI context while that thread waits is a deadlock.

06

Failure, told truthfully

Part 3's dialog earned its keep by saying something true on failure: nothing was removed. The review found the paths where that sentence, or the diagnostics behind it, went wrong.

The rollback that ate the cause

ResetProfileAsync caught, called RollbackAsync(), and re-threw with a bare throw;. Correct, except that a rollback on a broken connection usually throws too, and an exception thrown inside a catch replaces the one being re-thrown. The dialog then reported the rollback's complaint instead of the actual cause, the disk-full or locked-database that a player could act on. RollbackSafelyAsync now swallows and logs the rollback's own failure so the original survives (the data is equally safe either way: a transaction never committed rolls back when the connection dies). The same fix went to the three pre-existing rollback sites in the file, and A_rollback_that_cannot_run_is_swallowed_so_the_original_failure_survives proves it against a real file.

Failed and Abandoned are different sentences

Bounding the store wait (chapter 03) created a third outcome, and the review caught it rendering under the wrong headline. A drain timeout happens before the transaction ever starts: "nothing was removed" is provably true, and the outcome is Failed. A store timeout abandons the wait, not the work: the transaction may still commit or roll back on its own, so the one claim the dialog must not make is the one it cannot prove. That outcome is Abandoned, with its own localized text in all three languages.

ProfileResetOutcome is now a record with a private constructor and three factories: Succeeded(), Failed(message) (the detail is required, because a blank line under a failure headline explains nothing), and Abandoned(). A success carrying an error, a failure carrying none, or a timeout claiming nothing was removed are not bugs to catch in review anymore; they are states that cannot be constructed. The_abandoned_headline_does_not_claim_that_nothing_was_removed pins the text itself.

One hook's failure is one hook's failure

After the commit, four HandleProfileReset hooks bring memory in line with the store. As merged, all four ran inside one try/catch, and each hook raises its change event synchronously into UI subscribers the reset does not own. One throwing subscriber therefore skipped every later hook: three pages kept showing pre-reset data over a wiped database, while the dialog reported success. The success report was correct, and stays: the transaction committed, and a stale page (repaired by the next profile switch or restart) is not a failed reset. The fix is blast radius, not verdict: each hook runs in its own catch, and Every_hook_runs_even_when_every_hook_throws is exactly what it sounds like.

Smaller truths

  • The mid-raid warning could cry wolf. It read CurrentRaid?.State raw, and StopMonitoring never clears the last raid, so a leftover from a stopped watcher warned about a raid that ended hours ago. Now gated on IsMonitoring, the same rule the header status bar already applied.
  • Escape now cancels. The borderless dialog had no IsCancel anywhere, so Escape did nothing on a destructive confirmation. Cancel and Close carry IsCancel="True"; Confirm deliberately has no IsDefault, so Enter cannot wipe a profile.
  • Failure logs name the row again. Six context-carrying messages had collapsed into one that named only the profile. The helpers now take a description ("item inventory salewa", "batch of 3 rows"), because a failed write reverts silently on the next load, and the profile id alone does not say what reverted.
07

One rule, one seam

The design findings: a boundary rule spelled three ways, an orchestration sequence with no unit coverage, and a migration that logged only in the build where nobody would ever read it.

The fence gets one spelling

Part 3's watermark rule ("not after the reset moment") appeared as e.Timestamp <= resetAt.Value and its complement on adjacent lines of LogSyncService, which must stay exact inverses or the sync summary's count and the kept events stop partitioning the input, and as a third spelling in QuestProgressService's live fence. All three now call one predicate:

ResetFence.csPRD R6, in one place
internal static class ResetFence
{
    public static bool IsFencedOut(DateTime eventTimestamp, DateTime? resetAt)
        => resetAt.HasValue && eventTimestamp <= resetAt.Value;
}

The count and the filter are now literally one expression and its negation. ResetFenceTests pins the boundary from both sides (exactly at the watermark: fenced; one tick later: applies) and the partition property itself; flipping <= to < fails two of its four facts. This was one of the three escalated decisions: the fuller option, threading the timestamp into the batch write path, was declined because that path was proven unreachable and the extension forces an unresolved question about which timestamp cascade-derived rows would inherit.

The sequence becomes testable

The barrier-discard-store-hooks-release order is the load-bearing guarantee of the whole feature, and as merged it had zero unit coverage: only [E2EFact]s, which need an interactive desktop, exercised it. The re-audit rejected a DI rewrite (the repo's architecture is Instance singletons; swapping "remember to add a hook" for "remember to register a service" forecloses nothing) in favour of the idiom the repo already uses twice: an internal ResetCollaborators record of four delegates, with ProductionCollaborators as its only production value. Thirty-odd tests in ProfileResetOrchestrationTests now drive the sequence against recorders, and a source-fitness test, Every_service_that_declares_a_reset_hook_is_called_by_the_reset_service, scans the source so a fifth HandleProfileReset added without wiring fails the build. The transaction body was likewise split into four named steps, so "the watermark is written after the settings delete" is visible at the call site instead of 37 lines into a 65-line method, and moving it fails three store tests.

Conventions with consequences

  • Debug.WriteLine is [Conditional("DEBUG")]: all twenty calls in UserDataDbService compiled to nothing in Release, so the migration ran silently in the one build where a support thread would need its trace. All converted to the repo's Log.For<T>().
  • The e2e harness stopped hand-copying DDL. Its seeded database duplicated the production schema by hand and relied on CREATE TABLE IF NOT EXISTS silently adopting whatever it made. It now builds the file through the real store, with RaidHistory.AppProfileId as the drift canary; the six new harness tests all failed against the hand-copied schema.
  • A test hook left the production singleton (BeforeResetCommitAsync moved to an internal overload parameter), and the throw-vs-null drift between two settings readers ended in one ReadSingleValue helper.
08

What survived the review

Thirteen findings were refuted rather than fixed, and three questions went to the author. Both lists teach as much as the fixes do.

Refutation is a proof, not a shrug

Three examples of the standard the review held itself to:

  • Disproved by probe. A plausible DST bug in the watermark's round-trip (local DateTime.Now serialized with offset, read back with RoundtripKind) was tested directly: a January and a July value both round-tripped bit-identical in one process, because the parse uses the embedded offset and the UTC-to-local step is instant-aware. The finding died on evidence, not on argument.
  • Disproved by call chain. "A stale confirmation dialog could write through after a sync" assumed apply-after-confirm; the chain is inverted, MainWindow applies before reporting, so there is no confirm gate to write through.
  • Disproved by reachability. A real deadlock shape in HideoutProgressService (blocking write meets raised barrier) requires a UI path to fire during the barrier's lifetime; its only two callers live on a page inside MainWindow, which ShowDialog() disables for the whole window, and no overlay or hotkey path reaches them.

The three author decisions

  • SaveSingleModule stays blocking. The dispatcher-blocking hideout write is a documented defect (THR-4 in the code-health assessment), and the review still recommended considering leave-as-is, because the block is currently what serializes rapid writes to the same module: every non-blocking variant lets two quick clicks race their upserts, and the persisted level can land one below what the UI shows. Decision: leave it; the ordered-and-non-blocking answer is the pending-map pattern, as its own change.
  • The refresh hooks keep hard-coding "post-reset state is empty". Three hooks blank their caches, which duplicates the transaction's delete list in memory. No defect today, the transaction provably deletes every row of those tables for the profile; the reload alternative needs an inverse profile map and a revision-semantics decision the reset path otherwise never touches. Decision: leave it, documented at each site.
  • The fence consolidation stops at the predicate. Chapter 07's ResetFence extraction was chosen over threading the timestamp through the batch write path, defense-in-depth on a proven-unreachable path.

Why record declined options at all

The eventual THR-4 effort inherits the ordering argument instead of rediscovering it in production; the next reader of the hooks knows the coupling is chosen, not overlooked. A decision that is not recorded is indistinguishable from an accident.
