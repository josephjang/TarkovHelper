PR #49 · Code guide

The download that ran every hour and never arrived

PR #48 gave the app a versioned data channel. A deep review of it found 43 defects, and every one of them shares a shape. The update loop keeps running and never makes progress, or the publisher writes a channel the app refuses and then calls that channel healthy. Nothing surfaces in either case. Four labs let you operate the file swap, the check result, the publisher verdict, and the schema guard.

This is the deep-review guide for PR #48, whose own code guide is 2026-08-versioned-data-channel-code-guide.html. That guide builds the channel from nothing. Chapter 1 here is the short recap, enough to judge the rest. Two decision documents carry the design. docs/decisions/feature-versioned-data-channel.md holds the product decision, and feature-versioned-data-channel.spec.md holds the technical design. This change rewrites parts of that spec, and it updates the reference document docs/database-update-mechanism.md.

The whole change

The client can now finish an install, and it refuses what it cannot carry. The publisher now refuses to write a channel the app rejects. The title bar says when an app update is the only way back to current data. The schema guard stays red until a person adopts what it proposed.

01

The channel this change hardens

PR #48 replaced one text file with a versioned channel, and its own code guide builds that design from nothing. This is the short version, and it names the four parts every defect here lives between.

Every install of the app used to poll two files on raw main: TarkovHelper/Assets/db_version.txt and tarkov_data.db. Any difference in the version token started a full download. Nothing checked what arrived.

That mechanism cannot be taught a new rule. Builds already in the field hardcode those two addresses. A publish that older builds cannot read would reach every one of them within minutes.

The channel answers that with four parts. Read them as a set, because the defects in this change sit in the gaps between them.

  • A data format version. An integer that names the reader contract for the database. It covers the SQLite schema, the meaning of each field, and the range of values a field may hold. It rises only when an older build would read new data and show the user something wrong.
  • Versioned endpoints. One data/v<N>/ directory per data format version. A build polls the directory of the format it reads. One csproj property picks that format, the bundled seed database, and the polled addresses together. The old Assets pair stays as format 1's second address, kept byte-identical forever.
  • A manifest. data/v<N>/manifest.json names the version this endpoint serves, and the digest and the size of the database beside it. The database also stamps the same format number into SQLite's user_version, so the payload states its own contract.
  • An index. data/index.json names the data format version the project publishes right now. A build compares that against its own pin and learns it was left behind. Superseded directories are never rewritten, so a freeze is never a step a person can forget.
data/v1/manifest.json and data/index.jsonas committed
{
  "schemaVersion": 1,
  "dataFormatVersion": 1,
  "version": "1.0.10",
  "database": {
    "file": "tarkov_data.db",
    "digest": "sha256:1fdb928c9e1c7912a491244bfd1b4dc5607aaa7c6dd6b4ec0eda5986e91313c7",
    "size": 6889472
  }
}

{ "schemaVersion": 1, "currentDataFormatVersion": 1 }

One check runs at startup and then once an hour. It reads the index, reads the manifest, compares the manifest version against a local bookmark, and downloads the database when the two differ. The publisher is a separate program: TarkovDBEditor's DataPublishService compares its build output against the repository and writes the endpoint.

02

One failure shape

The review did not find one bad line. It found the same accident 43 times, in two halves of the same mechanism.

A silent update channel has a specific hazard. Nobody watches it. The user never asked for a download and never sees one. So a channel that stops working looks exactly like a channel with nothing to send.

Every finding in this change is a path that failed quietly rather than loudly. They divide into two halves.

The client half

The check runs, does work, and ends where it started. The bookmark never advances, so the next check repeats it. One install downloaded the whole 6.9 MB payload every hour, forever, and the log line blamed the download.

The publisher half

The tool writes a channel the app refuses, and then reports that channel as healthy with the Publish button disabled. The operator sees nothing to do while CI is red and every install has stopped updating.

The two halves meet at one rule. The client and the publisher must agree about what a valid channel is. Where the client refuses a document, the publisher has to refuse to write it. Where the publisher writes a document, the client has to accept it.

Chapters 3 to 5 take the client half, and chapter 6 takes the publisher half. Chapter 7 shows where this change moved the boundary between them. Chapter 8 covers the guard that was supposed to catch all of this.

03

The swap that could not finish

The last step of an install replaces one file with another. Three separate defects lived in it, and each one made every later update on that install fail in the same way.

The download lands in tarkov_data.db.tmp. The size and the digest are checked, the data format stamp is read, and then the temp file has to become the working database. Windows makes that step harder than it looks. A reader can hold the file open, and a file can carry the read-only attribute.

The code before this change moved the working database to tarkov_data.db.bak, then moved the temp file into place, then deleted the backup. Read that sequence for what it does to a read-only database.

TarkovHelper/Services/DatabaseUpdateService.csbefore
var backupPath = _databasePath + ".bak";
if (File.Exists(_databasePath))
{
    SqliteConnection.ClearAllPools();
    await Task.Delay(100);

    if (File.Exists(backupPath))
    {
        File.Delete(backupPath);          // throws on a read-only backup
    }

    const int maxRetries = 3;
    for (int retry = 0; retry < maxRetries; retry++)
    {
        try
        {
            File.Move(_databasePath, backupPath);   // the attribute travels with it
            break;
        }
        catch (IOException) when (retry < maxRetries - 1) { /* wait and retry */ }
    }
}

File.Move(tempPath, _databasePath);
// ... and this delete is inside the try that reports the whole download
if (File.Exists(backupPath)) File.Delete(backupPath);

Windows moves a read-only file without complaint. It refuses to delete one. So the two moves succeed, the backup inherits the attribute, and the final delete throws UnauthorizedAccessException.

That throw reaches the outer catch of the download, which returns false. The new bytes are already on disk. The check reports a failed download anyway, so the bookmark stays where it was.

The install is now wedged in a second way. A read-only backup sits beside the database, and the next check deletes it first. That delete throws before anything else runs. Every hour, forever, the install downloads 6.9 MB and fails at step one.

TarkovHelper/Services/DatabaseUpdateService.csafter, abbreviated
internal async Task SwapIntoPlaceAsync(string tempPath)
{
    if (!File.Exists(_databasePath))
    {
        File.Move(tempPath, _databasePath);   // first install: nothing to back up
        return;
    }

    SqliteConnection.ClearAllPools();
    await Task.Delay(100);

    var backupPath = _databasePath + ".bak";
    TryDelete(backupPath);        // clears the attribute, and logs rather than throwing
    ClearReadOnly(_databasePath);

    const int maxRetries = 3;
    for (int retry = 0; ; retry++)
    {
        try
        {
            File.Replace(tempPath, _databasePath, backupPath, ignoreMetadataErrors: true);
            break;
        }
        // UnauthorizedAccessException as well as IOException: it is not an IOException
        // (its base is SystemException), so a filter naming only IOException lets the
        // denied-access swap escape on the first attempt without ever retrying.
        catch (Exception ex) when (ex is IOException or UnauthorizedAccessException
                                   && retry < maxRetries - 1)
        { /* drain the pool, wait, retry */ }
    }

    TryDelete(backupPath);   // housekeeping, and it cannot fail the install
}

Three changes, and each answers a different failure.

  • One call, not two moves. File.Replace is atomic on NTFS and writes the backup itself. At every instant the database path holds either the old file or the new one. The pair of moves left a window where it held neither. A failure in that window left the install with no database, and nothing reads the backup back.
  • The attribute is cleared first. File.Replace refuses a read-only destination, and Windows refuses to delete a read-only backup. Either one alone wedges every future update, so both are cleared before the loop, and the clearing is logged because the attribute was somebody's intent.
  • The retry filter names both exceptions. UnauthorizedAccessException derives from SystemException, not from IOException. A filter naming only IOException lets the denied swap escape on the first attempt without ever retrying.

The backup delete also moved out of the path that reports the download. The new bytes are in place by then, so the install has succeeded. Removing the backup is housekeeping, and housekeeping must not be able to report the whole download as failed.

04

What the bookmark promises

A local file holding one token decides whether an install downloads 6.9 MB. Four defects came from trusting that token, or from trusting the document that names it.

The bookmark is Assets/db_version.txt. The client writes the manifest version into it after an install, and reads it back as the first non-blank line of the file. The publisher reads its own copy the same way.

That read makes a promise about what a token may contain. A token holding a line break survives the write and comes back truncated. It then compares unequal to the published version on every launch, and the install downloads the whole database every hour for its life.

TarkovHelper/Services/DataChannel.csnew, abbreviated
internal static bool IsBareVersionToken(string? version)
{
    if (string.IsNullOrWhiteSpace(version)) return false;

    foreach (var c in version)
    {
        var allowed = (c >= 'a' && c <= 'z')
            || (c >= 'A' && c <= 'Z')
            || (c >= '0' && c <= '9')
            || c is '.' or '-' or '_' or '+';

        if (!allowed) return false;
    }

    return true;
}

This is an allowlist rather than a test for line breaks. A separator nobody thought of cannot walk around an allowlist. The permitted set is semver's own version grammar with the underscore added, which covers every shape this channel or a CalVer successor can publish.

IsBarePayloadName guards the other free-text field for a related reason. The manifest names the file to fetch, and that name is pasted onto the endpoint URL. URI normalization resolves a .. segment against the base before the request goes out. An unchecked name can therefore point the download at another format's directory, while the manifest still looks internally consistent.

Both tokens are trimmed before they are judged, the same way the digest is. A stray space in a document somebody edited by hand is a formatting slip, not a different value. Refusing the whole manifest over one would stop every install updating.

The bookmark is not evidence that a file exists

The freshness test used to trust the token alone. It records which version was installed. It does not record that the file it names is still on disk.

TarkovHelper/Services/DatabaseUpdateService.csRunCheckAsync
if (LocalVersion == manifest.Version)
if (LocalVersion == manifest.Version && File.Exists(_databasePath))
{
    return Result(true, false, "Database is up to date");
}

An antivirus quarantine, a half-finished copy or a manual delete leaves the bookmark intact with no database under it. The old test reported "up to date" about a file that was not there, and the install never repaired itself.

Two documents, two answers to the same question

The manifest and the index both carry a schemaVersion, which describes the shape of the JSON document itself. This build reads shape 1. The two documents answer a newer shape in opposite directions, and that asymmetry is deliberate.

A manifest above this bound is refused outright. Declining an install is always safe, and a publish that put an unreadable shape at this address is an operator error the next publish fixes.

An index above the bound is still read for one field. Refusing it would cost a stranded build the only notice it will ever get. The index most likely changes shape at the publish that bumps the data format. That is exactly the publish that strands the builds reading this code.

TarkovHelper/Services/DataChannel.csParseIndex, after
var index = JsonSerializer.Deserialize<Index>(content, JsonOptions);
if (index is not { SchemaVersion: >= 1, CurrentDataFormatVersion: >= 1 })
{
    return null;
}

if (index.SchemaVersion > MAX_SUPPORTED_SCHEMA_VERSION)
{
    _log.Warning(
        $"Channel index declares schema version {index.SchemaVersion}, above the "
        + $"{MAX_SUPPORTED_SCHEMA_VERSION} this build understands. Reading only the "
        + "data format version it publishes, which every index schema carries.");
}

return index;

The promise this rests on

currentDataFormatVersion keeps its name and its meaning in every future index schema. Builds in the field derive their stranded notice from it and can never be taught a replacement. A schema that renames or drops it degrades to the old behaviour rather than lying. The field then reads 0, and the document is refused. Only repurposing it under the same name could mislead, and that is what this promise forbids.

05

A listener is not a participant

Both update services announce what they are doing. A subscriber that throws was able to cancel the work, hide its result, and wedge the service for the life of the process.

UpdateService checks for app updates and raises two events. It raises UpdateCheckStarted before the network call and UpdateCheckCompleted after it. The title-bar pill subscribes to both.

That subscriber formats localized strings and resolves WPF brushes. It can throw. A control being torn down during shutdown is the realistic case.

Look at where the two raises sat. The started raise was outside the try. The success raise was inside the try that classifies failures.

TarkovHelper/Services/UpdateService.csbefore
_isChecking = true;
UpdateCheckStarted?.Invoke(this, EventArgs.Empty);   // outside the try

try
{
    var response = await _httpClient.GetStringAsync(UpdateXmlUrl);
    // ... parse, and set _availableUpdate ...

    _lastCheckTime = DateTime.Now;
    _lastCheckError = null;
    UpdateCheckCompleted?.Invoke(this, new UpdateCheckEventArgs(_availableUpdate, null));
    return _availableUpdate;
}
catch (Exception ex)
{
    _lastCheckTime = DateTime.Now;
    _lastCheckError = ex;                    // the SUBSCRIBER's exception lands here
    UpdateCheckCompleted?.Invoke(this, new UpdateCheckEventArgs(null, ex));
    return null;
}
finally
{
    _isChecking = false;
}

Follow one check that really did find an update. The completion raise reports it, the pill subscriber throws, and control enters the catch. The catch records the subscriber's exception as the error of the check.

Then it raises completion a second time, carrying no update and that error. The second raise reaches the same subscriber, which throws again, and this time nothing catches it.

GetStatusKind puts Failed ahead of UpdateAvailable. So the update that really had been found disappeared from the UI behind an error the network never produced.

TarkovHelper/Services/UpdateService.csafter, abbreviated
if (Interlocked.CompareExchange(ref _isChecking, Checking, Idle) != Idle)
{
    // The only exit that raises nothing: no check began here.
    return _availableUpdate;
}

UpdateInfo? found;
Exception? error;

try
{
    try
    {
        RaiseStarted();                  // contained
        // ... fetch, parse, set _availableUpdate ...
        found = _availableUpdate;
        error = null;
    }
    catch (Exception ex)
    {
        found = null;
        error = ex;
    }

    _lastCheckTime = DateTime.Now;
    _lastCheckError = error;

    // Outside the catch above, not merely inside a try: a completion subscriber
    // that throws must not be classified as a failed check.
    RaiseCompleted(new UpdateCheckEventArgs(found, error));
}
finally
{
    Interlocked.Exchange(ref _isChecking, Idle);
}

return found;

Four properties come out of that shape, and each answers a real failure.

  • One exit raises completion once. The result is decided before the raise, so a throwing subscriber has nothing left to rewrite.
  • Both raises are contained. A listener exists to be told what happened. One that throws must not cancel the work it was merely being notified of. The started raise gets the same treatment for symmetry, and because an uncontained throw there left _isChecking set forever.
  • The flag is claimed atomically. The hourly timer and the Settings button can arrive together, and a read then a write let both start a check.
  • The raises happen while the flag is held. A subscriber that calls back in is answered "already in progress", rather than nesting a second check inside the first one's own notification.

DatabaseUpdateService received the same shape, and one thing more. Every database service subscribes to its DatabaseUpdated event and reloads from it. That raise walks the invocation list and contains each subscriber on its own.

One try around the whole raise would let a single handler that throws skip every service after it in the list. Half the app would keep reading the old data, with nothing to retry it until the next publish.

Why this had to be structural

Both callers drop what they get. The database check runs from an async void timer callback, where an escaped exception ends the process. The timer starts the app check and forgets it. App.xaml.cs hooks no handler for an unobserved task, so an escaped exception there vanishes with no log line.

06

What the publisher may write

TarkovDBEditor compares its build output against the repository and reports what a publish would change. It could report a channel as healthy that every install refuses.

The comparison is the operator's only view of the channel. It drives the Publish button, the change count, and the confirm dialog. A comparison that reports nothing to publish means the operator closes the window.

CI still guards the committed repository, so a bad channel does turn the build red. But a red build the tool cannot clear is worse than no check. There is no way out of the editor, and hand-copying files is the only repair.

The review found five gates that were absent or wrong. Each one is a rule the client enforces and the publisher did not.

Two absent tokens compare equal

The manifest version and db_version.txt have to agree. The check compared them and stopped there. With both absent, two nulls compared equal and the endpoint read as healthy.

The app's own reader rejects a manifest with no version outright. So the tool reported health for the one state in which every install stops updating.

TarkovDBEditor/Services/DataPublishService.csCheckManifestAsync, after
if (result.ManifestVersion == null)
{
    // Checked for presence rather than only against db_version.txt: two absent
    // tokens compare equal, and the app's own reader rejects a manifest with no
    // version outright.
    result.ManifestDriftReason = $"{shown} records no version, so clients cannot read it";
    return;
}

if (!IsPublishableVersionToken(result.ManifestVersion))
{
    // Checked before the two tokens are compared, because a db_version.txt
    // holding the same unreadable token compares equal.
    result.ManifestDriftReason =
        $"{shown} records version {result.ManifestVersion}, which no client can read";
    return;
}

if (!string.Equals(result.ManifestVersion, result.CurrentVersion, StringComparison.Ordinal))
{
    // ... the two documents disagree ...
}

IsPublishableVersionToken is the same allowlist as the app's DataChannel.IsBareVersionToken. The two projects do not reference each other, so the copies must change together. A test named A_token_the_editor_publishes_is_a_token_the_app_can_read fails if they drift apart.

The publish refuses a bad token before it writes anything, rather than only reporting one it finds. Free text like 1.0 beta used to reach the manifest, and the app returns null for that whole document.

Stamping ran only on the copy path

Every published database carries its data format in SQLite's user_version. The client refuses a payload that carries none, on the stated grounds that every publish writes one.

The stamp was written only when there was build output to copy from. A publish with no build output left the endpoint database unstamped, which breaks the invariant the client states verbatim.

One rule changed under the client too

The guide for PR #48 shows an unstamped payload installing. A stamp of 0 read as "this file makes no claim", and the client let it through. This change refuses it, and the spec now says why. Every publish stamps the database before it hashes it, so a payload that arrives unstamped did not come from a publish. It is also the payload most likely to carry no digest, so accepting it installs a file that nothing verified.

TarkovDBEditor/Services/DataPublishService.csPublishDatabaseAsync, after
var sourceExists = File.Exists(sourceDbPath);
if (sourceExists && comparison.DbWillPublish)
{
    // Stamp here, not during the comparison: this is the last moment before the
    // bytes are read, and both endpoints receive the one stamped file.
    var stampFailure = await StampDataFormatAsync(sourceDbPath, comparison.LiveDataFormatVersion);
    if (stampFailure != null) return Fail(result, stampFailure);

    // ... copy to the endpoint, and to the Assets mirror while format 1 is live ...
}
else if (!sourceExists)
{
    // No build output, so the endpoint copy is the database this publish
    // describes: it is the one that has to be stamped, and the one the mirror
    // is repaired from.
    var stampFailure = await StampDataFormatAsync(channelDbPath, comparison.LiveDataFormatVersion);
    if (stampFailure != null) return Fail(result, stampFailure);

    if (comparison.MirrorsToAssets)
    {
        await CopyFileWithShareAsync(channelDbPath, Path.Combine(_targetBasePath, DatabaseFileName));
    }
}

The mirror judgment was skipped, in both directions

Format 1 has two addresses. data/v1/ is where new builds poll, and TarkovHelper/Assets/ is the address builds in the field hardcode. The two must serve identical bytes, forever.

The comparison judged the mirror inside the branch that needs a source database. With no build output it returned early, and MirrorInSync kept its default of true. A real drift went unreported.

Both files being compared belong to the repository, so the missing build output does not make the pair unjudgeable. A publish repairs the mirror from the endpoint copy, which is why a drift found this way is always something the tool can clear.

What the operator would have shipped

The publish still wrote the channel token into the mirror's db_version.txt. A fresh install seeds itself from Assets. It would start bookmarked as up to date on a database it never received, and it would never download again.

The index had no detector at all

data/index.json is the one channel document above the endpoints. It is how a build learns that nothing further is coming for it. Nothing in the comparison looked at it.

CheckIndexAsync compares the parsed fields rather than the rendered bytes. The file is committed with CRLF, and this repository has no .gitattributes. A byte comparison would therefore call a healthy index drifted on whichever machine checked out the other line ending.

Republishing bytes that hold the same rows

The database changing its bytes is not the same as its data changing. SQLite records a commit in the file header, and it can move pages. An editor session that leaves the rows as it found them still writes a byte-different database.

The comparison compares bytes, so it says changed. A version token bumped for that makes every install download a multi-megabyte file it already has, because a client decides on the token alone.

The window now offers "Keep current version" for that case. It is offered only when the database really is being replaced and the endpoint has a token to keep, which CanKeepPublishedVersion states in one line.

07

Where the wire ends

Four boundaries moved. Each one puts a decision beside the thing it has to agree with, so the two cannot be edited apart.

The protocol leaves the service

DatabaseUpdateService held the endpoint URLs, the document records, the parsers, and the whole install procedure. The wire half now lives in DataChannel: where the endpoints are, and what the documents they serve may say.

The two drift for different reasons. The protocol changes when the published documents change. The client changes when the install procedure changes. Every rule about a document now sits beside the parser that enforces it.

DataFormatVersion deliberately stayed on the service. It identifies the build rather than the wire, and most of its readers ask it that way: which seed the repository ships, which pin the csproj carries, which baseline the drift guard compares. DataChannel reads it in exactly one place, to name the endpoint such a build polls.

The wording and the urgency travel together

The title-bar pill has two meanings now. An ordinary update keeps the reassuring green install pill. A build whose data channel has been superseded gets an amber pill that says so. Installing is the only thing that restarts its game data updates.

That choice used to be made in two files. MainWindow decided the colour, and the localization file held the words.

TarkovHelper/HeaderUpdatePill.csnew
public static HeaderUpdatePillText For(LocalizationService loc, string version, bool isSuperseded)
{
    ArgumentNullException.ThrowIfNull(loc);

    return isSuperseded
        ? new HeaderUpdatePillText(
            loc.HeaderUpdateForDataLabel,
            string.Format(loc.HeaderUpdateForDataTooltipFormat, version),
            HeaderUpdatePillTone.Warning)
        : new HeaderUpdatePillText(
            string.Format(loc.HeaderUpdateAvailableFormat, version),
            string.Format(loc.HeaderVersionTooltipInstall, version),
            HeaderUpdatePillTone.Success);
}

The tone is semantic rather than a brush, so MainWindow only renders the result. A new pill state cannot ship escalated words in the reassuring green.

The XAML lost the pill's Background, Foreground and AutomationProperties.Name. The code behind assigns all three on every path that shows the button. A value declared there would never be observed, and editing it would do nothing. UpdateStatusTests guards both halves of that asymmetry, including that the Settings twin still declares its own colours.

The accessible name is now the visible label, and the sentence moved to HelpText. WCAG 2.5.3 requires the accessible name to contain the visible words, so speech input can activate the pill by reading it aloud.

Background raises reach the UI without blocking it

Four handlers in MainWindow answer events raised on background threads. Three watch log monitoring, and one answers the database check. They used a blocking Dispatcher.Invoke or a bare InvokeAsync.

TarkovHelper/UiDispatch.csnew
public static bool Post(Dispatcher dispatcher, Action action)
{
    ArgumentNullException.ThrowIfNull(dispatcher);
    ArgumentNullException.ThrowIfNull(action);

    // Shutdown started (but not finished) still counts as gone: the queue accepts
    // the operation and then never runs it, so the work is dropped either way.
    if (dispatcher.HasShutdownStarted || dispatcher.HasShutdownFinished)
        return false;

    try
    {
        dispatcher.BeginInvoke(action);
        return true;
    }
    catch (InvalidOperationException) when (dispatcher.HasShutdownStarted || dispatcher.HasShutdownFinished)
    {
        // Shutdown began between the check above and the post.
        return false;
    }
}

Two hazards justify it. A blocking dispatch from a foreign thread throws TaskCanceledException once the dispatcher shuts down, and that throw escapes an async void callback unhandled. And a window unsubscribes its handlers when it closes, but a raise already past its delegate read still arrives.

Only that teardown race is swallowed, and only while the dispatcher confirms it is shutting down. Every other failure propagates.

Each posted body contains its own failures, because it runs later on the dispatcher. An exception escaping it reaches DispatcherUnhandledException, which App.xaml.cs leaves unhandled, and that ends the process. A failed repaint of the version chip must not do that.

The handlers that deliberately stay blocking

The settings handlers must not post. SettingsService pairs its raise with the apply under a snapshot identity guard, and posting would split the two. The rule is about which thread raised the event, not about which handler looks slow.

The publish method fits on a screen

PublishAsync folds from 204 lines to 114. The database step and the endpoint documents became named methods, and a Fail helper records a refusal as one statement rather than three.

CompareFilesAsync now returns a FileGroupComparison instead of writing three counts through Action<int> callbacks. Twelve count fields become four values, and no caller can pair one group's file list with another group's counts.

08

A guard that cleared itself

The one test that protects the promise the whole channel rests on had the same defect as the code it guards. It ran, it reported, and it left nothing behind.

Within one data format version, the published database only ever grows. Additions are safe because readers feature-detect. A removed table, a removed column or a retyped column breaks every build already reading that schema. Those builds cannot be fixed after the fact.

DataFormatDriftTests compares the published database against a committed baseline file. The baseline has to be a ratchet rather than a snapshot taken once. A column a publish adds is invisible to the guard until the baseline records it. Without a widening step, the next publish could drop that same column, and the comparison would find nothing missing.

The widening step wrote the new baseline into the tracked baseline file, and then failed the run. Read what the second run then does.

The guard that only ever failed once

The second run read the file the first run wrote. It found the schema unchanged and went green, against a baseline nobody had reviewed or committed. A non-additive change therefore failed once and passed from then on. Running the tests also modified a tracked file as a side effect.

TarkovHelper.Tests/DataFormatBaseline.csRatchet, after
internal static DataFormatBaselineReport Ratchet(string baselinePath, DataFormatSchema current)
{
    var proposedPath = ProposedPathFor(baselinePath);

    if (!File.Exists(baselinePath))
    {
        Write(proposedPath, current);
        return new DataFormatBaselineReport(DataFormatBaselineOutcome.Bootstrapped, [], []);
    }

    var baseline = Load(baselinePath);
    if (baseline is null)
    {
        return new DataFormatBaselineReport(DataFormatBaselineOutcome.Unreadable, [], []);
    }

    var (breaks, additions) = Compare(baseline, current);
    if (breaks.Count > 0)
    {
        // A stale proposal from an earlier addition is left alone: the run is red
        // either way, and it may still be the schema the maintainer meant to adopt.
        return new DataFormatBaselineReport(DataFormatBaselineOutcome.Broken, breaks, additions);
    }

    if (additions.Count > 0)
    {
        // Proposed rather than applied, because only a committed baseline guards anything.
        Write(proposedPath, current);
        return new DataFormatBaselineReport(DataFormatBaselineOutcome.Widened, breaks, additions);
    }

    if (File.Exists(proposedPath)) File.Delete(proposedPath);
    return new DataFormatBaselineReport(DataFormatBaselineOutcome.Unchanged, breaks, additions);
}

The proposal now lands beside the baseline as a .proposed.json sibling, left untracked on purpose. It is the artifact a maintainer reads and adopts, and adopting it is a rename. The guard stays red until somebody does that.

A break proposes nothing at all. A removal must not be able to launder itself by arriving beside an addition.

Six of the existing cases had been passing because of the bug, and they are tightened here. The failure message for every outcome now says which file to review, where to move it, and that re-running without moving it stays red.

Two more test defects, from the same family

The three channel suites had each grown a private copy of the same fixture helpers, and the copies had drifted. Two digest helpers returned lowercase hex while the third returned uppercase. The two byte comparers disagreed about what they print when they fail, which is the half of that assertion a reader depends on. One copy each of TestDigest, TestFiles and TestSqlite replaces them.

The test project also restated its own seed path and copied the 6.9 MB database into its output. The path it restated was the frozen pre-channel mirror, which stops being republished the moment the live data format leaves 1. The fixtures would then describe format 1 data while driving an app that ships a newer format.

TestSeed.DatabasePath is now the single spelling, and it reads the app's own bundled seed where the build already puts it. SeedDatabaseTests pins the seed to the pinned data format, and guards the csproj coupling itself.
