PR #38 · Code guide, part 2

A green suite that proved nothing

Part 1 explained why attribution has to travel with the data. This is what happened when that design met a real log file, a real store, and a real thread pool. The design held. The implementation shipped a dozen defects that defeated the attribution it exists to provide, and one of them explains why none of the others failed a test.

Everything here is commit c31ee51, which landed after part 1 was written. If you read the code guide and stopped, you have reviewed roughly half of this PR.

01

Why nothing failed

Start here, because it is the reason the rest exists. One test double disagreed with production about a single question, and that disagreement made most of this chapter list invisible.

The store has a key policy. When UserDataDbService.LoadQuestProgressAsync reads a partition back, it keys each row by normalizedName ?? id, taken from the row. So a quest that carries a name comes back name-keyed, and only a legacy row with no name comes back id-keyed.

ProgressStoreFake, the double every unit test writes through, keyed rows by the raw Id it was handed. Both are internally consistent. Neither is wrong on its own terms. But they answer differently, so a test that saved a row and read it back got a dictionary shaped in a way production never produces, and every assertion written against that shape held for the wrong reason.

The class of bug, not the instance

A test double is a claim about the collaborator it replaces. When the claim is wrong, the suite does not get weaker in a way you can see: it stays green, gets faster, and keeps agreeing with itself. Every defect in chapter 4 lived in the gap between those two key policies, and no amount of additional testing through the fake would have found them.

The fix is on both sides, and the durable half is the second one. The fake now keys the way the store does, and a new test pins the production policy directly so the two cannot drift apart again: ProgressStoreFakeTests.The_real_store_still_reads_by_name_first_and_deletes_by_either_spelling. That test asserts nothing about the fake. Its whole job is to fail when UserDataDbService changes and the double does not.

02

The timeline stopped reading

A bound that was correct for the live path was inherited by the sync path, where it means something completely different.

EftLogPatterns.FrameCompletedLines caps one read at MaxReadChunkBytes, which is 4 MB. That bound is right and part 1 explained why: the live watcher must not allocate a whole multi-megabyte log because a file changed. Whatever is left over is picked up on the next poll.

SessionModeTimeline.ReadNewEntries called it once. For the live path that is fine, because there is always a next Refresh. For the sync path there is not: a sync builds one timeline per session folder, reads it, and throws it away. Anything past the first 4 MB was never in the timeline at all.

What that produces

Not a crash, and not an empty answer. Resolve still finds the last transition at or before the event, so it answers with whichever mode was current 4 MB into the file. A seasonal wipe's completions file into PvE, and the summary reports a confident PvE count. The mechanism built to stop guessing produces a guess and labels it as evidence.

Services/Eft/SessionModeTimeline.csReadNewEntries
- if (stream.Length <= position) return false;
- var (lines, nextPosition) = EftLogPatterns.FrameCompletedLines(stream, position);
- _positions[file] = nextPosition;
+ while (position < stream.Length)
+ {
+     var (lines, nextPosition) = EftLogPatterns.FrameCompletedLines(stream, position);
+
+     // No forward progress means the remainder is an incomplete final line (or an
+     // unreadable one). Leave it for the next Refresh instead of spinning on it.
+     if (nextPosition <= position) break;
+
+     position = nextPosition;
+
+     // Persisted per chunk rather than once at the end: whatever this chunk appends is
+     // already in _entries, so an exception on a later chunk must not leave a resume
+     // offset that re-reads and duplicates it.
+     _positions[file] = position;
+     ...
+ }

Three things in that loop are load-bearing and each one is worth a moment in review. The nextPosition <= position break is the termination proof: without it, a trailing partial line makes the loop spin forever on the same offset. The per-chunk offset write is a crash-consistency argument, not an optimisation: entries are appended as they are parsed, so an IOException on chunk seven must not leave an offset that re-reads chunks one through six. And appended is declared outside the try, so a read that dies part way through still reports what it managed, and Refresh still re-sorts for it.

Truncation, which the same change had to fix

A rotated file was already re-read from the start, because holding an offset past the new end would lose every transition. But its old entries stayed in the list, so the re-read duplicated them. Entries now carry the file they came from, and a truncation drops that file's entries along with its offset:

Services/Eft/SessionModeTimeline.csthe Source tag earns itself
private readonly record struct Entry(DateTime At, SessionProfileHint Hint, string Source);

if (stream.Length < position)
{
    position = 0;
    _positions[file] = 0;
    _entries.RemoveAll(e => string.Equals(e.Source, file, StringComparison.OrdinalIgnoreCase));
}

RemoveAll is scoped to one file on purpose. A session folder can hold several application logs, and clearing the whole list would discard transitions that were read correctly from a file nothing happened to. Pinned by SessionModeTimelineTests.A_truncated_log_does_not_discard_another_logs_transitions.

03

A calendar nobody chose

The regex had already pinned the timestamp's exact shape. The parse then reinterpreted that shape through the user's Windows locale.

Services/Eft/EftLogPatterns.csTryExtractTimestamp
- if (match.Success && DateTime.TryParse(match.Groups[1].Value, out timestamp))
+ if (match.Success && DateTime.TryParseExact(
+         match.Groups[1].Value, TimestampFormat,
+         CultureInfo.InvariantCulture, DateTimeStyles.None, out timestamp))

DateTime.TryParse with no culture uses CultureInfo.CurrentCulture, and a culture carries a calendar, not just a format. The input string is unambiguous, so nothing here is a formatting mismatch. The parse reads 2026 as a year in the ambient calendar and converts it to Gregorian.

Under Thai (Buddhist) that means 2026 BE, which is Gregorian 1483. Under Persian it means 1405 SH counted the other way, landing on 2647. The arithmetic is the giveaway: those are the calendar offsets, 543 subtracted and 621 added, applied to a number that was never a calendar year in the first place. Under ar-SA (Umm al-Qura) the parse fails outright.

Downstream, this is total

Every timeline entry sorts centuries away from the quest events it is supposed to attribute, so Resolve finds no transition at or before any event and correctly answers null for all of them. Null means "no evidence", and no evidence means the event is dropped. A Thai, Persian, or Arabic Windows install runs the sync, is told nothing was attributable, and records nothing. It is the one defect on this list a user would report, because it fails completely rather than quietly.

The same reasoning applies a second time in LogSyncService.IsWithinCutoff, which parses the session folder's own log_2026.08.12_21-03-11 stamp. That one decides whether a folder is inside the sync window, so an ambient calendar would read every folder as a different century and discard the lot. It parses invariant for the same reason, and its whole design is deliberately generous: an unreadable time, an unfamiliar folder name, or a session that started before the cutoff and ran past it all keep the file, because the function exists to prune work and not to make decisions.

Why TryParseExact and not just a culture argument The format string is the second half of the fix. Passing InvariantCulture to TryParse would fix the calendar and still accept shapes EFT never writes, which is how a corrupted line becomes a plausible timestamp instead of a rejected one. 04

One quest, two rows

The subtlest defect here, and the one the store fake hid. Two key policies that cannot be reconciled met an OR that assumed they never coexist.

Two facts, both true, both established in part 1:

  • A write keys by ProgressKeyOf(task), which is the quest's first non-empty Id.
  • A load keys by normalizedName ?? id taken from the stored row, so a named quest comes back under its NormalizedName.

Part 1's IsRecordedDone asked both keys, which reads like defensive programming and was in fact necessary: an Id-only check reports "not recorded" for a quest that is recorded, so every sync rewrites the same rows and counts them as newly applied. The trouble is what the OR does when both keys are populated at once.

Loading puts the quest in under its name. Any in-memory write then puts it in again under its Id, leaving both. The OR reports whichever it reaches first, and that is the stale one.

Reproduction, from the commit message

Complete a quest. Restart the app, so the row loads back name-keyed. Mis-mark it Failed, which writes an Id-keyed entry beside it. Now click Complete. Nothing happens: the completion cascade asks "is this already Done?", the OR finds the name-keyed entry still saying Done, and refuses to re-complete a quest the user is looking at with a Failed chip on it.

Services/QuestProgressService.csthe collapse
private static void SetQuestRow(
    ImmutableDictionary<string, QuestStatus>.Builder builder,
    string key, string? normalizedName, QuestStatus status)
{
    builder[key] = status;
    if (!string.IsNullOrEmpty(normalizedName) &&
        !string.Equals(normalizedName, key, StringComparison.OrdinalIgnoreCase))
    {
        builder.Remove(normalizedName);
    }
}

Every in-memory write now routes through it, including the ones inside PlanQuestChanges's pending-state loop that used to call SetItem directly. That is what turns the dual-key OR from a hazard back into the safety net it was meant to be: the OR is sound precisely because a quest can no longer occupy both spellings at once. The two helpers are one contract, and reviewing either without the other will not show you the argument.

The same shape, in the Failed branch

PlanQuestChanges's Failed case tested one exact key with RecordedStatus(pending, taskKey). For an off-screen profile, whose rows come back name-keyed, that check never matched, so every sync re-wrote an already-Failed quest and counted it as applied. It now goes through IsRecordedFailed, the dual-key twin of IsRecordedDone. Same for PlanLogEvent's Failed case. Guard: ProgressSnapshotTests.An_already_failed_quest_in_an_off_screen_profile_plans_nothing_on_a_second_sync.

05

The write thrown away

Part 1 defended this behaviour explicitly. The defence was wrong, and knowing why is the point of this chapter.

Part 1's compare-and-swap re-checks the owner inside the loop body, because a profile switch can publish a different snapshot between the read and the swap. Writing this profile's rows onto another's cache would show progress that is not theirs, so the re-check is correct and necessary. What it did next was not:

part 1, ApplyQuestChangesBatchAsyncthe comment that was wrong
// Bailing out here loses the write rather than misfiling it, which the next sync
// recovers from; misfiling it is what nothing recovers from.
if (!string.Equals(ownerId, current.ProfileId, StringComparison.Ordinal))
    return (current, new List<(string Id, string? NormalizedName, QuestStatus Status)>());

Two things are wrong with it. The smaller one is that returning an empty list makes "the profile switched under us" indistinguishable from "nothing needed changing", so the caller reports a successful no-op for a write it lost.

The larger one is the claim that the next sync recovers it. Sync only re-reads sessions inside the configured SettingsService.SyncDaysRange window. Once that session folder ages past the range, the next sync does not look at it, and there is no later run that puts the row back. The write is not deferred. It is gone.

The false choice

The original comment framed this as drop-or-misfile, and drop is genuinely better than misfile. But there was never only two options. At the moment the swap is lost, the code still holds ownerId: it knows exactly which partition these rows belong to. It just cannot publish them to a snapshot that now names someone else. Writing to the database without touching the snapshot is precisely the off-screen path the same method already had for a profile that was never loaded.

Services/QuestProgressService.csApplyForOwnerAsync
// null says "the profile switched under us", which the caller must be able to
// tell apart from an empty row list ("nothing needed changing"): the rows
// still belong to a partition we know the name of, so they get written there
// instead of being dropped.
if (!string.Equals(ownerId, current.ProfileId, StringComparison.Ordinal))
    return (current, null);

...

// changed == null falls through to:
return await ApplyOffScreenAsync(owner, ownerId, plan, logLabel);

That is also why plan is a delegate rather than a precomputed list, and why the parameter documentation insists it be pure. It runs once per compare-and-swap retry and once more on the fallback, each time against a different snapshot, so a plan that captured its inputs would answer for a state that no longer exists.

One more edge the fallback opened

If the user switches to the profile being written while that off-screen write is in flight, the reload reads the store before the rows land, so the snapshot names the right profile and does not hold them. The quests look un-completed until something re-reads. ApplyOffScreenAsync closes it by reloading for the revision the published snapshot carries, so a newer transition arriving in the meantime simply discards this reload and reads the rows itself. Guard: ProgressSnapshotTests.A_profile_that_becomes_loaded_mid_write_ends_up_showing_the_rows.

The refactor that made all this possible is worth noting on its own: ApplyQuestChangesBatchAsync and ApplyLogEventAsync were two near-identical copies of the loaded-versus-off-screen dance. They are now one ApplyForOwnerAsync that differs only in the plan it is handed and the label it logs. Two copies of this logic is two places for exactly the defect above to survive a fix.

06

What the player is told

The PRD makes the per-profile summary the player's only signal, because the per-quest confirmation list is gone. That raises the bar on every number in it.

The count was of rows queued, not rows written

ApplyQuestChangesAsync reported batchChanges.Count, which is what it handed down. The two differ routinely and in both directions: the batch skips rows already recorded, and it adds Failed rows for the mutually exclusive alternatives a completion rules out. ApplyQuestChangesBatchAsync now returns Task<int>, and a profile that received nothing is left out of the map entirely rather than shown as a zero, so the summary cannot name a partition it did not touch. Guards: A_second_apply_of_the_same_changes_reports_nothing_applied and A_completion_that_fails_an_alternative_reports_both_rows.

A partition that threw looked exactly like one that needed no change

Each profile's write is isolated, so one failure does not cost the others their report. The consequence is that a failed partition is simply absent from AppliedCountsByProfile, which is indistinguishable from an untouched one. With a single profile in the run, the dialog read "No quests changed." after losing everything.

The apply step now returns QuestApplyOutcome(AppliedByProfile, FailedProfiles), the dialog keeps its header neutral whenever anything failed, and SyncApplyFailedFormat names the profiles in EN, KO and JA. Guard: LogSyncAttributionTests.A_profile_whose_batch_throws_is_reported_as_failed_and_the_others_still_apply.

Sync and apply disagreed about where the loaded profile's rows come from

Sync planned every profile from a fresh store read. Apply planned the loaded profile from the snapshot and only an off-screen profile from the store. Hand edits publish to the snapshot synchronously and persist fire-and-forget, so the store read can be behind what the user is looking at. Two planners reaching different conclusions from different sources also fed stale rows into alternative-quest collection, which could re-ask an either-or the player had already answered.

Two smaller arithmetic bugs in the same dialog

  • A quest in progress in two profiles was counted twice, because InProgressQuests is ordered output rather than a set. A run-wide InProgressKeys now deduplicates across passes, so "still in progress: N" cannot exceed the number of distinct quests.
  • A quest whose last log event is Started, but which is already recorded Done, fell into no bucket at all: not a change, not in progress, not already current. It now increments AlreadyCurrentCount, which is what stored state already matching the log means, and the numbers add up again.

The partition key can no longer come from a default

QuestChangeInfo.OwnerProfile and AlternativeQuestGroup.OwnerProfile are now required. This is the most mechanical change in the PR and one of the most valuable, because default(AppProfile) is AppProfile.PvpZone: an initializer that simply forgot the field would file the change into the permanent PvP partition, the one that is most expensive to lose and hardest to notice. Making the compiler ask is the only version of this rule that cannot be forgotten.

The pattern worth taking away

Three of the fixes in this chapter are the same move: make the type carry the obligation rather than the reviewer. required on the partition key, a non-optional daysRange parameter so the next caller that omits it fails to compile, and a nullable return that forces the caller to distinguish "switched" from "nothing to do". Prefer these to a comment asking the next person to remember.

07

Ordering and atomicity

Four defects that share a root: state that was consistent because of how the old code happened to be scheduled, not because anything enforced it.

The refactor deleted an accidental lock

LogSyncService raises QuestEventDetected in a tight loop over one tail read and does not await the handler. The old handler ended in a blocking Dispatcher.Invoke, which serialized events by accident. Part 1 replaced it with an async void body, and that accident went with it: event N+1 began planning while event N was still between its read and its write. A Completed followed by a Failed in one tail could then both plan against the same pre-write rows, and whichever landed second won, leaving a quest the game failed recorded as Done.

MainWindow.xaml.csboth properties made explicit
private readonly SemaphoreSlim _questEventGate = new(1, 1);

await _questEventGate.WaitAsync();
try
{
    // On the UI thread, and not with a blocking Invoke: this runs on a thread-pool
    // thread, and QuestProgressService.ProgressChanged (raised inside the call
    // below) has subscribers such as IntegratedItemService that update UI state
    // without marshalling themselves.
    await Dispatcher.InvokeAsync(() => HandleQuestEventAsync(evt)).Task.Unwrap();
}
finally
{
    _questEventGate.Release();
}

.Task.Unwrap() is the detail to check. InvokeAsync of an async lambda completes when the lambda returns its Task, not when that Task finishes, so without the unwrap the gate releases at the first await inside and the serialization is decorative. The teardown path gained a matching QuestEventDetected -=, because a handler that dispatches its whole body onto a shutting-down dispatcher awaits an operation that never runs.

Two fields that were one fact

ProfileService assigned the selection and incremented the revision as separate steps, and callers read them as two properties. Two threads transition concurrently in production (the dispatcher when the user clicks, the log watcher's thread pool when evidence arrives), so they could assign in one order and take revisions in the other. A caller reading the pair could then pair the old profile with the new revision, at which point the staleness guard sees nothing wrong and cheerfully publishes one profile's rows as the answer to another's transition.

Both halves now live under one gate and are read together through CurrentTransition. Two details are deliberate. The gate is static, so it exists even on an instance built by RuntimeHelpers.GetUninitializedObject, which skips field initializers and would otherwise leave every lock throwing on a null (ProfileSwitchingTests builds one that way, and the class is a singleton, so a per-type gate is a per-instance gate in production). And the event is raised outside the lock: subscribers run synchronously and take locks of their own, so holding the gate across the raise is a lock-ordering hazard. The args are built inside, so each subscriber still sees a matched pair.

The timeline was documented as not thread-safe, and then shared

The live path keeps one SessionModeTimeline per session folder across watcher callbacks that run on the thread pool, so a Refresh rebuilding the entry list could overlap a Resolve walking it. The resulting InvalidOperationException then hit the bare catch in the live quest-event path, which swallowed it along with the entire batch of events. The player's only signal was a finished raid that never registered.

Both halves are fixed: the timeline takes its own lock in every public member and Entries hands back a copy, and the catch logs. Putting the guarantee in the class rather than in each caller is the right call here precisely because the failure it prevents is invisible at the call site. Guard: SessionModeTimelineTests.Refresh_and_Resolve_can_run_concurrently_on_one_timeline.

The two services nobody looked at

HideoutProgressService and ItemInventoryService subscribed to ActiveProfileChanged, discarded the event's profile, and re-read ProfileService.Instance inside the async body. That is the exact defect this PR exists to remove from quests, still sitting in two other services. Both now take the profile and revision from the event, resolve the storage id before the first await, and run the same revision guard. Their fire-and-forget saves resolve the profile before the Task.Run body too, so a switch between scheduling and running cannot redirect a row.

Worth asking in review

These two were found by looking for the pattern rather than by a failing test. The question the reviewer should ask is whether the sweep was complete: is there a third subscriber to ActiveProfileChanged, or a fourth Task.Run that reads ActiveProfileId inside its body? ProfileAttributionSourceTests bounds the write-path files by an allowlist, but an allowlist only covers the files it names.

Loading, made survivable

Three smaller lifecycle fixes finish the chapter. The quest and objective loads get separate try blocks, because publishing them together is a statement about atomicity (never one profile's quests beside another's objectives) and not about failing together: an unreadable objective table is no reason to throw away quest rows that read back fine. The publish and notify are themselves wrapped, because the caller reaches this through _ = ReloadForProfileAsync(...) and a throwing subscriber would otherwise fault a Task nobody observes. And the self-healing reload is restored: a provenance-only re-confirmation now reloads if the last load failed or the snapshot names a different profile, which are the two states that used to be curable only by switching profile away and back by hand.

08

What was deleted

Deletions deserve their own pass, because a removed guard and a removed corpse look identical in a diff.

  • SaveProgress and SaveProgressToDbAsync, the legacy whole-snapshot rewrite. Its last caller was ReconcileProgressWithDb, which went with it. Every write now goes through the batch path, which is the one that takes an explicit profile.
  • SyncResult.CompletedQuests and TotalApplied, and SyncResultDialog.AlternativeGroupCount with the out parameter that carried it. All unread once the dialog became a per-profile summary.
  • Two hand-rolled BuildQuestIdLookup copies, one in MainWindow and one in LogSyncService, replaced by the indexes QuestProgressService already builds. This one is not purely a cleanup: the new BuildTaskIndexes indexes every task by id, including a task with no NormalizedName, where the old Initialize filtered to named tasks first. The live handler resolves by id and returns on a miss, so a nameless quest's completion was previously not recorded at all. QuestTaskIndexTests pins the wider set.

The deletion that changes what ships

14 System.Diagnostics.Debug.WriteLine calls became Log.For. That reads as tidying and is not: Debug.WriteLine carries [Conditional("DEBUG")], so the compiler removes those call sites from a Release build. Every diagnostic quoted in this guide, including the discarded-stale-load line and the batch-save confirmations, did not exist in the build users run. A silent defect with no log line is a defect nobody can report usefully.

One thing was deliberately not deleted, and part 1 already covered it: LogSyncService's application*.log glob has never matched a real EFT filename, so its map path is dead. It is still there, with a comment recording the finding, because repairing the glob would only make dead code do unused I/O. Nothing about attribution goes through it, and SessionModeTimeline uses the correct *application*.log pattern.

What did not get fixed, and is not a defect

Rows already stored under the wrong mode by a previous version are still not repaired. The PRD records the reasoning and the release notes should say so plainly. Nothing in this second wave changes that decision; it only makes the number of rows in that category stop growing.
