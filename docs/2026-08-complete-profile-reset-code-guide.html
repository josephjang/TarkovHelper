PR #41 · Code guide

A reset that keeps its promise

With PvP Season, resetting a profile stops being a rare recovery and becomes the routine way a season starts. This guide walks the change that makes the reset complete, atomic, and durable: the background first, then three labs where you drive the actual decision logic, then a gate that checks whether it landed.

Part 3 of the profile series. Part 1 covered attribution (where progress goes); part 2 covered the deep review of that work. Companion to docs/decisions/feature-complete-profile-reset.md (the product decision) and .spec.md (the technical design), resolving SPA-3, SPA-4 and SPA-6.

The whole change in one sentence

"Reset" now means: one SQLite transaction removes everything the chosen profile owns and stamps a watermark in the same commit, a per-profile barrier drains and holds the writes that used to race it, the app's own log import refuses to restore anything from before that watermark, and a localized dialog tells the truth about all of it, including failure.

01

What reset used to mean

Four independent promises, all broken quietly. None of them was a typo; each was a structural choice that stopped being acceptable once resets became routine.

The old Danger Zone button did this, in this order:

MainWindow.BtnResetProgress_Click (before)the whole reset
QuestProgressService.Instance.ResetAllProgress();   // quests + objectives
_hideoutProgressService.ResetAllProgress();         // hideout
// items, profile values, raid history: nothing
MessageBox.Show("진행도가 초기화되었습니다.\nAll progress has been reset.");

And each ResetAllProgress had the same internal shape: clear the in-memory cache first, then block the UI thread while two autocommit deletes run, and swallow whatever goes wrong:

QuestProgressService.ResetAllProgress (before)memory first, failure swallowed
Mutate(current => (current with { Quests = Empty, Objectives = Empty }, 0));  // screen empties NOW
Task.Run(async () =>
{
    try
    {
        await Store.ClearAllQuestProgressAsync(profileId);      // delete 1 (autocommit)
        await Store.ClearAllObjectiveProgressAsync(profileId);  // delete 2 (autocommit)
    }
    catch (Exception ex) { _log.Error($"Reset failed", ex); }   // player never told
}).GetAwaiter().GetResult();

The four broken promises

  1. "All progress" was three tables of six. Item inventory, profile values (level, scav rep, faction, prestige, DSP count) and raid history all survived. ItemInventoryService.ResetAllInventory() existed and had zero callers; DeleteProfileSettingAsync had zero callers, so profile values survived forever.
  2. Success was announced unconditionally. A failure between the two deletes left objectives without their quests; a failure after the memory swap left the screen empty while the database kept every row. The success box showed anyway, and a restart brought the "reset" data back.
  3. Nothing ordered pending writes against the deletes. Batch saves are fire-and-forget, and the inventory flush runs on a 500 ms debounce timer. A write scheduled before the reset could land after it and recreate deleted rows.
  4. Even a perfect reset did not hold. The game retains roughly three days of session logs. The next sync re-imported the removed progress, and attribution (part 1) made this worse: old seasonal events are filed into exactly the profile that was just reset, whatever is selected on screen.

Why seasons make this urgent

A recurring seasonal reset with a partial category list is a standing trap: every category the reset silently skips is data the player believes gone. And the player doing the resetting is, by construction, doing it every season.

02

Ownership defines complete

The PRD's central decision: everything stored under the profile's key goes, everything account-wide survives. The player never needs to know the storage taxonomy to predict the outcome.

user_data.db partitions six tables by ProfileId: QuestProgress, ObjectiveProgress, HideoutProgress, ItemInventory, ProfileSettings, and (new in this change) RaidHistory via its own owner column. The new UserDataDbService.ResetProfileAsync is one connection, one transaction, six deletes and one insert:

UserDataDbService.ResetProfileAsyncthe shape, abbreviated
await using var transaction = await connection.BeginTransactionAsync();
DELETE FROM QuestProgress     WHERE ProfileId = @p;
DELETE FROM ObjectiveProgress WHERE ProfileId = @p;
DELETE FROM HideoutProgress   WHERE ProfileId = @p;
DELETE FROM ItemInventory     WHERE ProfileId = @p;
DELETE FROM ProfileSettings   WHERE ProfileId = @p AND Key NOT IN (survivors);
DELETE FROM RaidHistory       WHERE AppProfileId = @p;   -- NULL never matches
INSERT app.progressResetAt = resetAt (ON CONFLICT update); -- the watermark
await transaction.CommitAsync();  -- exceptions propagate; no catch-and-log

Three deliberate details

  • The survivor list is an allowlist, and deletion is the default. SettingsService.ProfileKeysSurvivingReset names exactly two keys, the game editions (EOD, The Unheard Edition). They are facts about the account, not character progress; wiping them would corrupt quest filtering until the player noticed the unticked box. A future profile key someone forgets to classify is wiped, which is the safe direction for progress-shaped data. A test pins the list to a subset of ProfileSpecificKeys.
  • The watermark is written inside the same transaction, after the settings delete so it is not swept by its own delete. Fence and removal commit atomically: there is no window where the data is gone but the fence is down. Chapter 04 is about what reads it.
  • The old per-table ClearAll* methods are deleted, not kept alongside. There is no second, non-atomic way to reset left in the codebase.

Because every failure path is now one failure path (the transaction throws, the rollback restores everything), the UI can finally say something true on failure: nothing was removed. That sentence is load-bearing in chapter 06.

03

Writes in flight

A perfect transaction is not enough. The app schedules persistence it does not wait for, and nothing ordered those writes against a reset of their profile.

Attribution (part 1) made every write carry the correct profile id. It did not order them against a reset of that profile:

  • QuestProgressService schedules fire-and-forget persistence at four sites (_ = SaveProgressBatchAsync(...), objective batches, and two deferred delete bodies).
  • ItemInventoryService debounces through a 500 ms timer, and its "flush" snapshots the pending set and persists inside Task.Run, so even a flush returns before the rows are durable.
  • EftRaidEventService saves raid rows with Task.Run(() => SaveRaidHistoryAsync(...)).

A batch save scheduled before a reset can therefore insert its rows after the reset's deletes. The fix is a per-profile barrier, and where it lives matters more than what it does:

TrackedUserDataWritesthe two operations
Task Run(string profileId, Func<Task> op)
  // waits out any reset barrier, registers, runs op, logs failure, unregisters
Task<IAsyncDisposable> BeginResetAsync(string profileId)
  // barrier up, awaits every registered write (the drain); dispose lowers it

Structural, not disciplinary

The barrier is acquired inside the persistence helpers, not at their call sites. A future caller of any helper is ordered automatically; there is no call-site convention to erode. This is also why a queue serializing all writes at all times was rejected: it taxes every write forever to solve an ordering problem that exists only around reset. Outside a reset the barrier costs one dictionary lookup and one lock.

The orchestrator, ProfileResetService.ResetAsync(target), then has a fixed order: barrier up and drain, discard the target's pending debounced inventory saves (they describe quantities the transaction is about to delete; flushing them would write rows only to remove them), run the transaction, and only after the commit let each service publish its cleared in-memory state through a HandleProfileReset hook that no-ops when it holds another profile's data. Memory follows durable state, reversing the old order. The whole flow is async end to end: a blocking wait on the dispatcher would deadlock against tracked writes whose continuations return to it.

04

The logs remember

The game keeps several days of session logs, and the app deliberately reads them. Without a fence, the first sync after a reset undoes it.

Attribution files each session's events into the profile that produced them. That is exactly right, and it is exactly the problem here: old seasonal sessions land in the seasonal profile no matter what is selected, so a reset seasonal profile is repopulated by its own history. Deleting the game's logs is not an option (they are not the app's files); documenting the re-import would turn "reset" into "reset until the next sync". So the reset records its moment, and the import paths refuse anything not after it:

two fences, one watermarksync and live
// Sync: per owner group, before planning
var resetAt = await Store.GetProgressResetAtAsync(ownerId);
ownerEvents = ownerEvents.Where(e => e.Timestamp > resetAt.Value).ToList();
result.PreResetEventCount += dropped;   // shown in the sync summary

// Live: inside the tracked write, so check-then-write is atomic vs a reset
return TrackedUserDataWrites.RunAsync(ownerId, async () =>
{
    var resetAt = await Store.GetProgressResetAtAsync(ownerId);
    if (resetAt.HasValue && timestamp <= resetAt.Value) return 0;  // no row, no snapshot change
    return await ApplyForOwnerAsync(owner, ...);
});

Three boundary decisions

  • The boundary is "not after". An event stamped exactly at the reset moment is dropped. A tie means the evidence does not prove the progress happened after the player's decision, and the fence fails toward the decision.
  • Hand entry never passes through either fence. The fence exists to stop the app's own re-import of removed history. A quest the player ticks after the reset is present intent, not history.
  • The live check runs inside the barrier. Checked outside, an event could pass a stale watermark read and write after a newer one committed. Inside, the read and the write are on the same side of any reset.

The accepted hole

Log timestamps are local and carry no offset, so during the one repeated hour per year an event can be judged on the wrong side of a reset that happened inside that hour. Converting to UTC fixes nothing, because the log lines being compared carry no offset either. Same exposure, same acceptance, as attribution.

05

Raids get an owner

SPA-4: raid history identified the in-game character, which says nothing about which app profile the raid belonged to. A complete per-profile reset had nothing safe to delete.

RaidHistory.ProfileId is the EFT character id, and GameMode cannot distinguish PvP Zone from PvP Season (they share game rules by design). So the table gains a second identity column, and its value is decided at exactly one moment:

EftRaidEventServicecapture at creation, from session evidence
_currentRaid = new EftRaidInfo
{
    ProfileId    = raidProfileId,                              // EFT character id (existing)
    AppProfileId = AppProfileIdOf(_currentSessionProfileHint), // "pvp"/"pve"/"season", or null
    ...
};
  • Captured at creation, never at save time. Raid saves run in a deferred task after the raid ended, when the user may have switched profiles. The value is frozen into the raid object when the raid first exists, from the session evidence current at that moment. The ambient selection is never consulted; it is not evidence of where the raid happened.
  • Null means "no evidence", never a default. An unknown or absent session hint yields null, and the reset's delete is WHERE AppProfileId = @p, which NULL never matches. Every legacy row and every unowned row survives every reset, by construction (PRD R9). Guessing owners for legacy records by game mode and date was rejected: game mode cannot distinguish permanent PvP from PvP Season, which is the exact ambiguity that created SPA-4, and a wrong deletion is unrecoverable.
  • The migration is additive and downgrade-safe. An idempotent pragma check adds the nullable column; older builds' INSERT lists explicit columns, so a downgrade keeps working and its rows read back as legacy.

If EFT renames the session-mode token

New raids fall back to a null owner: reset stops removing new raid rows until the pattern is updated. That fails toward preserving data rather than deleting the wrong rows, which is the direction every null in this design fails toward.

06

An honest dialog

SPA-6: the old confirmation was a fixed Korean-plus-English MessageBox that named no profile and listed two categories. The new one is a first-class window because it has structural work to do.

ProfileResetDialog is one window with two states. The confirm state names the captured target profile with its localized label, enumerates every category the reset removes, notes what survives, and warns (without blocking) when a raid appears to be in progress. The result state reports success, or failure with the sentence chapter 02 made true: nothing was removed.

Details that carry weight

  • The target is captured once, when the dialog opens, from ProfileService.Instance.CurrentTransition, and bound into the reset delegate. An automatic profile switch while the dialog is open does not move the reset (PRD R1). Nothing below the capture reads the ambient selection; the source-scan test adds ProfileResetService and TrackedUserDataWrites to its scan list with empty allowlists, so a reintroduced ambient read fails the build.
  • A raid in progress warns, but does not block. Raid detection can be stale or wrong, and the player decides when their season ends, not the raid detector. A reset during a raid is safe: everything after the reset moment is new progress, recorded normally.
  • Every control carries an AutomationId because the e2e harness drives owned WPF windows by title and InvokePattern but cannot drive a native MessageBox at all. ProfileResetE2ETests exists only because the MessageBox does not: it seeds two profiles, resets one through the real dialog, and asserts in the database file that the season partition emptied, the editions and watermark survived, and PvE was untouched. The decline path asserts nothing changed and no watermark went up.
  • The partial reset is gone on purpose. There is no "quests only" option, no backup, no undo. The enumerating confirmation is what prevents surprise; the partial shape was the defect, not a feature to preserve.
