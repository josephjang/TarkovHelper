PR #46 · Code guide, part 7

The setting that the software deleted

Part 6 made the profile settings cache one immutable snapshot behind a revision gate, and all the tests passed. A deep review then found a defect that the player cannot prevent. A settings load cannot read the store, so it publishes the default values of that profile. The drawer then clears the Edge of Darkness checkbox, which sends the same event as a click. The handler writes False to the store, and you cannot get the flag again. Four labs let you operate the echo chain, the fan-out, the edit window, and the bulk read.

This is part 7 of the profile series. It is the deep-review guide for part 6 (2026-08-profile-settings-race-code-guide.html, PR #43). Part 2 has the same relation to part 1, and part 4 to part 3. Two decision documents relate to this guide. This change rewrites the Technical Decisions and the Non-Goals in docs/decisions/fix-profile-settings-race.spec.md. It also adds a note to docs/decisions/feature-complete-profile-reset.spec.md.

The whole change

This change makes five corrections. Each announce asks again if the cache still holds its snapshot. A second counter closes the window in which a load can publish rows that an edit already replaced. The settings drawer marks its own repaints, so the handlers do not read those events as a click. The seven events cause one refresh in each page, and not thirty-five. The legacy import fails for one value, and not for the full run.

01

What part 6 left

This change does not alter the snapshot, the revision gate or the publish gate. The review examined the space between them, and the code that reads the events that they send.

Part 6 removed eight reads that each asked which profile the player selected. One ProfileSettingsSnapshot replaced them. The snapshot holds eight values, the profile that owns them, and the revision of the transition. One reference swap under _publishGate publishes it.

A reload claims its revision at the gate, and then reads the store to one side. It asks again at the gate if its revision is still the newest. If the revision is not the newest, the reload discards its own result.

This is a full answer to one question: which reload owns the cache. It is not an answer to three other questions. The deep review is mostly a list of those three.

  • What occurs after the publish. The gate controls the publish. The gate cannot control the seven events that follow. The subscribers move to the dispatcher and then call this service again. Therefore the gate would cause reentrancy and a deadlock. Refer to chapter 3.
  • What the store contained during the read. The revision gate puts the reloads in sequence. It tells you nothing about an edit that the player made during a reload. Refer to chapter 4.
  • What the subscribers do with the events. The settings drawer writes the values into controls. The change handlers of those controls then write back. Refer to chapter 2. This one destroys data.

Two other changes are important, because they change the code that this guide shows. Part 6 added a fourth copy of ClaimRevision, and all four copies were the same. One helper, RevisionGate.Claim(ref long latest, long revision), replaces them. All four services call it.

The review also applies the THR-1 direction from the part 6 spec, but only in part. The four services share the gate. They do not share the reload flows, because those flows are different in ways that are real. The differences are the notify flags, the half-failures and the debounced saves.

TarkovHelper/Services/RevisionGate.csnew, and the whole of it
internal static void Claim(ref long latest, long revision)
{
    while (true)
    {
        var current = Interlocked.Read(ref latest);
        // Not a plain compare-and-store: two handler threads can read the same
        // current, and the one whose exchange loses re-reads instead of
        // overwriting the winner's newer value.
        if (revision <= current) return;
        if (Interlocked.CompareExchange(ref latest, revision, current) == current) return;
    }
}

The helper is static, and the caller owns the long. A type that owns the counter was the other option. Each service reads _latestRevision directly with Interlocked.Read for its check after the store read. A type would move that read into an accessor, and the code would not be more safe. RevisionGateTests shows that the counter only increases, and it tests two threads that claim at the same time.

02

The write that no person made

A write to CheckBox.IsChecked sends Checked and Unchecked, and a click sends the same two events. The handler could not identify the difference, and one of the two conditions caused a write to the store.

Examine the sequence. A settings load cannot read the store. Therefore it publishes the Defaults of that profile and it sets _lastLoadFailed. This is the part 6 design, and it is correct. If the cache kept the values of the previous profile, the screen would show them with the name of a different profile. In the default snapshot, HasEodEdition is null, and HasEodEditionOrDefault gives false.

The fan-out sends HasEodEditionChanged(false). Then MainWindow.OnEditionChanged moves to the dispatcher and calls UpdateEditionUI. That method writes ChkEodEdition.IsChecked = false, and WPF sends Unchecked. ChkEdition_Changed starts. It finds a checkbox that is clear, and it does the procedure for a player click:

TarkovHelper/MainWindow.xaml.csbefore

{
    ChkEodEdition.IsChecked = _settingsService.HasEodEdition;      // raises Unchecked
    ChkUnheardEdition.IsChecked = _settingsService.HasUnheardEdition;
}

private void ChkEdition_Changed(object sender, RoutedEventArgs e)
{
    if (_isLoading) return;        // only ever true during Window_Loaded

    if (sender == ChkEodEdition)
        _settingsService.HasEodEdition = ChkEodEdition.IsChecked == true;   // stores False
}

The cost

The code sets _isLoading only for the start-up pass in Window_Loaded. But these events also occur much later. They occur at a profile change, at a profile reset, and at the settings self-heal. Thus there is no guard after start-up.

The write goes to the store, and the Edge of Darkness flag of the player is not there any more. The screen is not only incorrect until the next reload. The value is deleted. The application cannot get it again, and the player touched no control.

The correction is a scope, and not a flag that the code sets and clears by hand. This difference is important:

The echo that a flag cannot stop

One echo occurs after the scope closes. The two text boxes in the drawer apply their value at LostFocus. The service can write text into a box while the caret is in that box, and the box can then lose the focus. The guard is down at that moment. Therefore only a comparison can tell you if the value is a player edit or a repaint:

TarkovHelper/MainWindow.xaml.csApplyPlayerLevelFromTextBox, after
if (int.TryParse(TxtPlayerLevel.Text, out var level))
{
    level = Math.Clamp(level, SettingsService.MinPlayerLevel, SettingsService.MaxPlayerLevel);

    // Only a value that DIFFERS from what the service reports is a player edit.
    if (level != _settingsService.PlayerLevel)
        _settingsService.PlayerLevel = level;

// Always repaint: unparsable text ("abc") must not be left in the box, and an
// out-of-range entry ("999") must show the clamped value that was actually applied,
// which the setter raises no event for when the clamp lands on the value it holds.
UpdatePlayerLevelUI();

The repaint that always occurs is the less obvious half. Put 999 in the level box. The clamp makes it 79. The setter finds that the store already holds 79, so it sends no event. Without the repaint, the box continues to show 999, and the player thinks that the application accepted that value.

03

The fan-out outside the gate

The publish is one operation. But the announce is seven calls on a thread, and the dispatcher can stop that thread for a long time. Part 6 asked no question before these calls.

RaiseProfileSettingsChanged receives the snapshot as a parameter. It does not read the field again for each event. Therefore one fan-out cannot mix two profiles. Part 6 is correct here. But part 6 does not ask if the fan-out is still necessary.

This sequence causes the defect. A reload on the thread of the log watcher publishes profile A and starts to announce. The first handler moves to the dispatcher. The dispatcher is already busy with a manual profile change. That change publishes profile B and announces all seven values of B. Then the fan-out of A continues and sends the other values of A.

QuestListPage sets its faction radio button from these events, and not from the snapshot. At the next filter change, the page writes the value of the radio button to the store. Thus the screen of profile B shows the faction of profile A. Then the page saves that faction into profile B.

TarkovHelper/Services/SettingsService.csafter
private void RaiseProfileSettingsChanged(ProfileSettingsSnapshot snapshot)
{
    Announce(() => PlayerLevelChanged?.Invoke(this, snapshot.PlayerLevelOrDefault));
    Announce(() => ScavRepChanged?.Invoke(this, snapshot.ScavRepOrDefault));
    Announce(() => DspDecodeCountChanged?.Invoke(this, snapshot.DspDecodeCountOrDefault));
    Announce(() => PlayerFactionChanged?.Invoke(this, snapshot.PlayerFaction));
    Announce(() => HasEodEditionChanged?.Invoke(this, snapshot.HasEodEditionOrDefault));
    Announce(() => HasUnheardEditionChanged?.Invoke(this, snapshot.HasUnheardEditionOrDefault));
    Announce(() => PrestigeLevelChanged?.Invoke(this, snapshot.PrestigeLevelOrDefault));

    void Announce(Action raise)
    {
        // Reference identity, not profile id: the question is whether THIS snapshot is
        // still the one the cache holds, and two snapshots can name the same profile.
        if (!ReferenceEquals(Volatile.Read(ref _profileSettings), snapshot)) return;
        raise();
    }
}

The code asks this question before each event, and not one time at the start. Each handler can stop this thread while the dispatcher does its work. A profile change that occurs during event k stops event k+1 and all the events after it. A part of a fan-out is safe, because the snapshot that replaced this one publishes and announces all seven of its own values.

What this guide does not claim

One window is still open, and the spec says the same. A publish can occur between the last check and the start of the handler. This side cannot close that window. To close it, the pages must read the snapshot, and they must not use the last event that they received. That is a larger change than this one. The test SettingsSetterContractTests.A_switch_landing_mid_fan_out_stops_the_rest_of_it holds the part that is closed.

04

Two counters, opposite sequences

A generation counter tells a load that an edit is complete. It cannot tell the load that an edit is in operation. In that window, the load publishes again the value that the player replaced.

Part 6 has _editGeneration. An edit increases it. A load reads this counter before it reads the store. If the counter is different at the publish, the load reads the store again. Thus the load does not replace a number that the player typed.

The review asked where the code must increase the counter, before or after the store write. The answer is that neither position is sufficient.

The code increases the counter before the store write. Therefore a load that started its read cannot publish rows that are older than the edit. But this leaves the opposite hole. A load can read the counter after the increase, and then read rows before the write is complete.

At the publish, the counter is the same, so the load publishes the old rows. The snapshot then holds pre-edit rows with the correct profile id, and the code records no failure. If you move the increase after the write, the hole moves to the other side.

Two counters close the two directions, but only if each side touches them in the opposite sequence. This is the full argument, and it is easy to make an error here.

The edit increases _editsInFlight first, and decreases it last. Thus the counter is more than zero for all the time in which a load cannot read the row. The load reads _editGeneration first, and _editsInFlight second. Thus an edit that starts after these reads must also increase the generation after them. One signal or the other tells the load to read the store again.

Examine the second half of the condition. This swap can only lose an edit to the profile that the code publishes. A load that moves the cache to a different profile must replace the values that are there. The edit stays in the profile that received the write.

When the load has no more attempts

MaxLoadAttempts is 3. If an edit occurs at each attempt, the load keeps the snapshot that holds the edits. This is better than a snapshot with rows that are older than the last edit.

But in part 6 this condition published nothing and announced nothing. One half of that behaviour is incorrect. HandleProfileReset is a plain Action. Its contract is that the cache is correct and announced when the action is complete. Thus a quiet return left old values in the settings panel after the reset removed them.

05

What a store can give back

ProfileSettings is a plain SQLite table, and a player can edit it by hand. Also, the legacy JSON import wrote its numbers with no check for many years. The one bulk read receives all of these values.

The setters always clamp. Thus no value that the application writes can be out of the range. That was the argument against a clamp at the read. The review found three errors in that argument. First, a player can edit a row by hand. Second, the legacy app_settings.json import applied no clamp.

Third, an old build read its own scav rep incorrectly in a locale with a comma decimal mark. ProfileSettingsSnapshot.From now clamps each value that has a range.

These ranges are necessary. The values go to the quest filter, where QuestProgressService compares them with the conditions of each task.

  • A stored level of 9999 is more than the level condition of each quest. Thus the full list shows as unlocked.
  • The code compares the DSP decode count exactly to select a Make Amends branch. A row that is out of the range matches no branch, and it locks all of them.
  • A scav rep with no clamp goes directly to the Fence karma filter.

The comparer is a part of the read

The bulk read replaced eight SELECT statements, one for each key. The table has no COLLATE NOCASE, so each of those statements returned only the exact key. A dictionary that ignores the case does not do the same:

TarkovHelper/Services/UserDataDbService.csLoadProfileSettings
// ProfileSettings has no COLLATE NOCASE, so (ProfileId, Key) treats "app.playerLevel"
// and "app.PlayerLevel" as two legal rows. A case-insensitive dictionary would collapse
// the pair last-row-wins, letting row order decide the value and giving a hand-edited
// row an effect it never used to have.
var result = new Dictionary<string, string>(StringComparer.Ordinal);

while (reader.Read())
    result[reader.GetString(0)] = reader.GetString(1);   // indexer: last row wins

The faction is the one value that the code makes uniform, and it has no clamp. The read makes it lower case, and not only the write. QuestListPage.LoadFactionSelection compares the value as ordinal text. An old build could write the row as "USEC", which matches no radio button. Therefore the player sees no faction. But the quest filter ignores the case, so it continues to hide the quests of the other faction.

06

Seven events, one refresh

One profile change sent seven events. MainWindow told the quest list to refresh for five of them. The pages also received the same events directly.

Five settings handlers in MainWindow called QuestListPage at the end. The page also received the same events directly. Thus one profile change ran the full quest procedure seven times, and it did this for pages that the player could not see. This change removes the five calls. Each page receives the events and builds its content one time. This changes the timing of the user interface, and the spec records that with the correction.

The coalescer collects the seven events into one refresh. This makes the direct subscription sufficiently fast. It has two decisions that you must know:

TarkovHelper/Services/RefreshCoalescer.csnew
public static RefreshCoalescer OnDispatcher(DispatcherObject owner, Action refresh)
{
    var dispatcher = owner.Dispatcher;
    return new RefreshCoalescer(
        refresh,
        // BeginInvoke, not InvokeAsync: both queue the callback, but the
        // DispatcherOperation InvokeAsync returns CARRIES the callback's exception
        // instead of rethrowing it, so discarding that operation (as a
        // fire-and-forget schedule must) swallows the failure silently.
        action => dispatcher.BeginInvoke(action, DispatcherPriority.Background));
}

private void Run()
{
    // Cleared BEFORE the refresh, not after: a change landing WHILE the refresh runs
    // books a second pass instead of being swallowed by the pass that had already
    // read the old state.
    Interlocked.Exchange(ref _pending, 0);
    _refresh();
}

The schedule rule is in one place only, and this is necessary. Dispatcher.Invoke runs the callback immediately when the caller is already on the user-interface thread. The callback then clears the flag before the other events arrive, and it collects nothing. The Background priority lets all the events arrive first. The test RefreshCoalescerSchedulingTests.OnDispatcher_reports_a_refresh_that_throws holds the BeginInvoke decision with a true dispatcher, because you cannot see the difference in another way.

This chapter closes one more failure path. The rebuild method in ItemsPage is an async void method at the top of the dispatcher stack. No code above it can catch an exception, so an exception stops the application. A try block now catches the exception and writes it to the log.

07

The other corrections

Four smaller findings have the same shape. At each one, two parts of the code must agree, but no mechanism makes them agree.

The import that stopped after a write

MigrateAppSettingsAsync wrote nine values in one try block, and it declared its counter in the same block. If the database was locked at value six, the method stopped and reported zero. But five rows were already in the database.

MigrateFromConfigFolderAsync deletes the JSON files only when the total is more than zero. Thus a partial import kept the files, and the automatic migration started again at each launch. The counter is now outside the try block. Each value has its own guard, so one failure stops only that value.

Two readers of one file

SettingsService.MigrateFromJsonIfNeeded and ConfigMigrationService.MigrateAppSettingsAsync both read the legacy app_settings.json file. They answer different questions, so the code needs both of them. But they must write the same row for a given JSON value, and they were different for five values.

The start-up reader stored the faction in the case of the file. It applied no clamp to the sync range. It clamped the scav rep but did not round it, so it could write 2.37, which no setter can make.

LegacyAppSettingsValues now holds the value half. Each function is pure and operates on one value. Thus the two readers keep their own rules for the table, the partition, the count and the failure report. The test ConfigMigrationProfileAttributionTests.Both_legacy_readers_turn_one_file_into_the_same_profile_rows makes them agree by machine, and not by memory.

The spin button that removed the import

ItemInventoryService delays its saves. AdjustFirQuantity writes the sum of the cache value and the change as an absolute quantity. A save that waits holds a quantity from before the import. Thus one operation of the spin button after an import wrote the old total over the imported rows. The flush now occurs before the first write, and never after it. The code loads the cache again after the last write.

The status from two profiles

QuestProgressService.GetStatus already carried a ProgressSnapshot through the full prerequisite walk. But its six condition tests each read SettingsService.Instance for their own value. A publish between two of these tests mixed the editions of one profile with the level of another profile. This is the same defect that the snapshot type prevents, and it was in the largest consumer of that type. Both snapshots are now parameters, and each recursive step carries the same two snapshots.
