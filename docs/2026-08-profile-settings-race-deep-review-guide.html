PR #46 · Code guide, part 7

The setting that erased itself

Part 6 made the profile settings cache one immutable snapshot behind a revision gate, and the tests passed. A deep review then found that the worst remaining defect needed no player action at all: a settings load that could not reach the store published that profile's defaults, the unchecked box that followed raised the same event a click raises, and the echo wrote False over the player's stored Edge of Darkness flag permanently. Four labs let you drive the echo chain, the fan-out that ran outside the publish gate, the edit window one counter could not describe, and the row set a hand-edited database can hand back.

Part 7 of the profile series, and the deep-review companion to part 6 (2026-08-profile-settings-race-code-guide.html, PR #43), the way part 2 follows part 1 and part 4 follows part 3. Companion to docs/decisions/fix-profile-settings-race.spec.md, whose Technical Decisions and Non-Goals this change rewrites in place, and to the retirement note it adds to docs/decisions/feature-complete-profile-reset.spec.md.

The whole change in one sentence

Every announce re-checks that the snapshot it is announcing is still the one the cache holds, a second counter closes the window in which a load could republish rows an edit had already replaced, the settings drawer marks its own repaints so their events cannot be mistaken for a player's click, the seven-event burst collapses into one refresh per page instead of thirty-five, and the legacy import fails per value rather than per run.

01

What part 6 left standing

The snapshot, the revision gate and the publish gate all survive this change unaltered. What the review audited is the space between them, and everything downstream of the events they raise.

Part 6 replaced eight per-key reads against an ambient "which profile is selected?" with one ProfileSettingsSnapshot: eight values, the profile they belong to, and the revision of the transition they were loaded for, published by a single reference swap under _publishGate. A reload claims its revision through the gate, reads the store off to the side, re-checks under the gate that it is still the latest, and discards itself if it is not.

That is a complete answer to one question: which reload owns the cache. It is not an answer to three others, and the deep review is largely a list of those three.

  • What happens after the publish. The publish is gated. The seven changed events raised from it are not, and cannot be: the subscribers marshal onto the dispatcher and call back into this service, so holding the gate across them would invite reentrancy and a dispatcher deadlock. Chapter 3.
  • What the store looked like while the rows were read. The revision gate orders reloads against each other. It says nothing about an edit the player typed in the middle of one. Chapter 4.
  • What the subscribers do with the events. The settings drawer writes them into controls whose own change handlers write back. Chapter 2, and it is the one that destroys data.

Two structural cleanups ride along and are worth naming here because they change how the rest of the guide reads. ClaimRevision had reached four byte-identical copies once part 6 added its own; it is now one RevisionGate.Claim(ref long latest, long revision), called by all four services. And the review takes the THR-1 direction the part 6 spec recorded, but only the part of it that applies: share the gate, not the reload flows, whose differences (notify flags, half-failures, debounced saves) are real.

TarkovHelper/Services/RevisionGate.csnew, and the whole of it
internal static void Claim(ref long latest, long revision)
{
    while (true)
    {
        var current = Interlocked.Read(ref latest);
        // Not a plain compare-and-store: two handler threads can read the same
        // current, and the one whose exchange loses re-reads instead of
        // overwriting the winner's newer value.
        if (revision <= current) return;
        if (Interlocked.CompareExchange(ref latest, revision, current) == current) return;
    }
}

It stays a static helper over a caller-owned long rather than a type owning the counter, because each service's post-read check reads _latestRevision directly through Interlocked.Read. Hiding the field would push that half through an accessor for no added safety. RevisionGateTests pins the monotonicity, including the concurrent case.

02

The write nobody made

Assigning CheckBox.IsChecked raises Checked and Unchecked exactly as a click does. The handler could not tell the two apart, and one of the two paths wrote to the store.

Follow the chain. A settings load cannot reach the store, so it publishes that profile's Defaults and records _lastLoadFailed. That is the part 6 design and it is right: keeping the previous profile's values would show one profile's editions under another profile's name. Defaults means HasEodEdition is null, which HasEodEditionOrDefault answers as false.

The fan-out raises HasEodEditionChanged(false). MainWindow.OnEditionChanged marshals onto the dispatcher and calls UpdateEditionUI, which assigns ChkEodEdition.IsChecked = false. WPF raises Unchecked. ChkEdition_Changed runs, sees a checkbox that is not checked, and does what it does for a player click:

TarkovHelper/MainWindow.xaml.csbefore
private void UpdateEditionUI()
{
    ChkEodEdition.IsChecked = _settingsService.HasEodEdition;      // raises Unchecked
    ChkUnheardEdition.IsChecked = _settingsService.HasUnheardEdition;
}

private void ChkEdition_Changed(object sender, RoutedEventArgs e)
{
    if (_isLoading) return;        // only ever true during Window_Loaded

    if (sender == ChkEodEdition)
        _settingsService.HasEodEdition = ChkEodEdition.IsChecked == true;   // stores False
}

The cost

_isLoading is raised only for the startup pass in Window_Loaded. These events also arrive long afterwards: a profile switch, a profile reset, the settings self-heal. So outside startup the guard is simply absent, the write lands, and the player's Edge of Darkness flag is gone from the store. Not shown wrong until the next reload: gone. Nothing in the app can recover it, and the player did not touch anything.

The fix is a scope, not a flag set and cleared by hand, and the distinction is the whole point:

TarkovHelper/MainWindow.xaml.csafter
private SettingsEchoSuppression SuppressSettingsEcho() => new(this);

private readonly struct SettingsEchoSuppression : IDisposable
{
    private readonly MainWindow _window;
    private readonly bool _wasUpdating;

    public SettingsEchoSuppression(MainWindow window)
    {
        _window = window;
        _wasUpdating = window._isUpdatingSettingsUI;   // remembered, not assumed false
        window._isUpdatingSettingsUI = true;
    }

    // RESTORES rather than clears, so a nested update cannot lower its caller's guard.
    public void Dispose() => _window._isUpdatingSettingsUI = _wasUpdating;
}

private void UpdateEditionUI()
{
    using var echoGuard = SuppressSettingsEcho();

    ChkEodEdition.IsChecked = _settingsService.HasEodEdition;
    ChkUnheardEdition.IsChecked = _settingsService.HasUnheardEdition;
}

private void ChkEdition_Changed(object sender, RoutedEventArgs e)
{
    if (_isLoading || _isUpdatingSettingsUI) return;
    ...
}

All five repaint methods open the scope (UpdatePlayerLevelUI, UpdateScavRepUI, UpdateDspDecodeCountUI, UpdateEditionUI, UpdatePrestigeLevelUI), so a control added to any of them is covered without anyone remembering to. RefreshCoalescerSchedulingTests.Settings_repaint_methods_suppress_the_echo pins that by reflection over the method list rather than by naming the five it knows about today.

The echo a flag cannot cover

One echo arrives after the scope has closed. The two drawer text boxes commit on LostFocus, and the box can be losing focus over text the service itself wrote into it while the caret sat there. By then the guard is down, so equality is the only thing that can tell a player edit from a repaint:

TarkovHelper/MainWindow.xaml.csApplyPlayerLevelFromTextBox, after
if (int.TryParse(TxtPlayerLevel.Text, out var level))
{
    level = Math.Clamp(level, SettingsService.MinPlayerLevel, SettingsService.MaxPlayerLevel);

    // Only a value that DIFFERS from what the service reports is a player edit.
    if (level != _settingsService.PlayerLevel)
        _settingsService.PlayerLevel = level;
}

// Always repaint: unparsable text ("abc") must not be left in the box, and an
// out-of-range entry ("999") must show the clamped value that was actually applied,
// which the setter raises no event for when the clamp lands on the value it holds.
UpdatePlayerLevelUI();

The unconditional repaint is the subtler half. Type 999 into the level box: the clamp turns it into 79, the setter finds 79 already stored and raises nothing, and without the repaint the box would keep showing 999 as though it had been accepted.

03

The fan-out outside the gate

Publication is atomic. Announcement is seven separate calls on a thread that can be parked for as long as the dispatcher takes, and part 6 asked nothing at all before making them.

RaiseProfileSettingsChanged takes the snapshot as a parameter rather than re-reading the field per event, so no single fan-out can mix two profiles. Part 6 got that right. What it did not ask is whether the fan-out should still be happening.

The sequence that breaks it: a reload on the log watcher's thread publishes profile A and starts announcing. Its first handler marshals onto the dispatcher, which is already running a manual profile switch inline. That switch publishes profile B and announces all seven of B's values. Then A's fan-out resumes and delivers the rest of A's. QuestListPage takes its faction radio from these events rather than from the snapshot, and on the next filter change it persists what the radio says, so B's screen ends up showing and then saving A's faction.

TarkovHelper/Services/SettingsService.csafter
private void RaiseProfileSettingsChanged(ProfileSettingsSnapshot snapshot)
{
    Announce(() => PlayerLevelChanged?.Invoke(this, snapshot.PlayerLevelOrDefault));
    Announce(() => ScavRepChanged?.Invoke(this, snapshot.ScavRepOrDefault));
    Announce(() => DspDecodeCountChanged?.Invoke(this, snapshot.DspDecodeCountOrDefault));
    Announce(() => PlayerFactionChanged?.Invoke(this, snapshot.PlayerFaction));
    Announce(() => HasEodEditionChanged?.Invoke(this, snapshot.HasEodEditionOrDefault));
    Announce(() => HasUnheardEditionChanged?.Invoke(this, snapshot.HasUnheardEditionOrDefault));
    Announce(() => PrestigeLevelChanged?.Invoke(this, snapshot.PrestigeLevelOrDefault));

    void Announce(Action raise)
    {
        // Reference identity, not profile id: the question is whether THIS snapshot is
        // still the one the cache holds, and two snapshots can name the same profile.
        if (!ReferenceEquals(Volatile.Read(ref _profileSettings), snapshot)) return;
        raise();
    }
}

Re-asked before every event, not once up front, because each handler can block this thread for as long as the dispatcher takes to run it: a switch that lands while event k is being delivered still stops events k+1 onwards. A partial fan-out is safe by construction, since whatever superseded this snapshot publishes and announces all seven of its own values.

What the guide does not claim

One window stays open and the spec says so in the same terms: a publish landing between the last check and the handler actually running is not closable from this side. Closing it for good means the pages reading the snapshot rather than trusting whichever event reached them last, which is a larger change than this one. SettingsSetterContractTests.A_switch_landing_mid_fan_out_stops_the_rest_of_it pins what is closed.

04

Two counters, opposite orders

A generation counter tells a load that an edit happened. It cannot tell it that an edit is happening, and the difference is a window in which the load republishes the value the player just replaced.

Part 6 already had _editGeneration: an edit bumps it, and a load that captured it before its store read and finds it moved at publish time reads again rather than reverting a number the player typed. The review's question was where exactly the bump sits relative to the write, and the answer is that no single placement works.

The bump happens before the store write, so that a load whose read is already in flight cannot publish rows that predate the edit. That leaves the mirror hole: a load can capture the already bumped counter, read rows the write has not committed yet, find the counter unmoved at publish time, and republish pre-edit rows under the right profile id with no failure recorded. Moving the bump after the write only moves the hole the other way.

TarkovHelper/Services/SettingsService.csthe edit side, after
// Raised first and lowered last, so this edit counts as in flight for the whole
// span in which its row may be unreadable to a load.
Interlocked.Increment(ref _editsInFlight);
try
{
    Interlocked.Increment(ref _editGeneration);   // before either half lands
    SaveProfileSetting(origin.ProfileId, key, value);
    outcome = TryPublish(origin, next, update, out supersedingProfileId);
}
finally
{
    Interlocked.Decrement(ref _editsInFlight);
}
TarkovHelper/Services/SettingsService.csthe load side, after
// Both captured BEFORE the read, and in this order.
var generation = Volatile.Read(ref _editGeneration);
var editsInFlight = Volatile.Read(ref _editsInFlight);

... one bulk read, off to the side ...

lock (_publishGate)
{
    if (live != null)
    {
        if (!isStillWanted(live)) return LoadPublishOutcome.Superseded;

        if ((Volatile.Read(ref _editGeneration) != generation || editsInFlight != 0) &&
            string.Equals(live.ProfileId, snapshot.ProfileId, StringComparison.Ordinal))
            return LoadPublishOutcome.OvertakenByEdit;
    }
    ...
}

Two counters close both directions provided each is touched in the opposite order on the two sides, which is the entire argument and is easy to get backwards. The edit raises _editsInFlight first and lowers it last, so it is non-zero for the whole span in which its row may be unreadable. The load captures _editGeneration first and _editsInFlight second, so an edit that began after the capture necessarily bumps the generation after the capture too. Either signal makes the load read again.

Note also the second half of the condition: only an edit to the profile being published can be lost by this swap. A load moving the cache to a different profile is meant to replace what is there, and the edit stays in the profile it was written to.

And when the re-reads run out

MaxLoadAttempts is 3. If edits keep landing on every attempt, the load gives the edits the last word and keeps the edited snapshot, which is strictly better than replacing it with rows that predate the last edit. But part 6's give-up branch returned without publishing or notifying, and one half of that promise is unconditional: HandleProfileReset runs as a plain Action whose contract is that the cache is current and announced when it returns. Returning quietly left the settings panel showing values the reset had wiped.

TarkovHelper/Services/SettingsService.csthe give-up branch
default:
    _log.Warning($"Settings load for {profileId} kept being overtaken by edits ...");
    return;
    // The LIVE snapshot, not the rows just read: it is the one every getter answers
    // from, so it is the honest thing to announce.
    if (notify) RaiseProfileSettingsChanged(Volatile.Read(ref _profileSettings));
    return;

05

What a store can hand back

ProfileSettings is a plain SQLite table a player can hand edit, and the legacy JSON import carried its numbers through unchecked for years. The single bulk read is the one place all of that funnels through.

The setters have always clamped, so no value the app itself wrote can be out of range. That was the argument for not clamping on the way in, and it is wrong in three ways the review enumerated: a hand-edited row, a legacy app_settings.json import that clamped nothing, and an older build that could mis-read its own comma-decimal scav rep under another locale. ProfileSettingsSnapshot.From now clamps every bounded value it parses.

These are not cosmetic bounds. The values fan out into quest filtering, where QuestProgressService compares them against task requirements:

  • a stored level of 9999 answers every quest's level requirement, so the whole list reads as unlocked;
  • the Make Amends branches are selected by an exact match against the DSP decode count, so an out-of-range row matches no branch at all and silently locks every one of them;
  • an unbounded scav rep reaches Fence karma filtering directly.

The comparer is part of the read

The bulk read replaced eight per-key SELECTs, and a per-key SELECT against a table with no COLLATE NOCASE returns only the exact key. A case-insensitive dictionary would not reproduce that:

TarkovHelper/Services/UserDataDbService.csLoadProfileSettings
// ProfileSettings has no COLLATE NOCASE, so (ProfileId, Key) treats "app.playerLevel"
// and "app.PlayerLevel" as two legal rows. A case-insensitive dictionary would collapse
// the pair last-row-wins, letting row order decide the value and giving a hand-edited
// row an effect it never used to have.
var result = new Dictionary<string, string>(StringComparer.Ordinal);

while (reader.Read())
    result[reader.GetString(0)] = reader.GetString(1);   // indexer: last row wins

The faction is the one value normalised rather than clamped. It is lower cased on the way in, not merely on the way out, because QuestListPage.LoadFactionSelection compares ordinally: a row an older build wrote as "USEC" matches neither radio button, so the player sees no faction selected while quest filtering, which compares case-insensitively, still hides the other faction's quests.

06

Seven events, one refresh

One profile switch raised seven events. MainWindow pushed a quest list refresh from five of them, and the pages were subscribed as well.

Five of MainWindow's settings handlers ended with a push into QuestListPage, on top of the page's own subscription to the same events. One profile switch therefore ran the full quest pass seven times, off-tab included. The pushes are gone; the pages subscribe directly and rebuild once. That is a UI-timing change riding along with a correctness fix, which the spec flags rather than hides.

Collapsing the burst is what makes "subscribe directly" cheap, and the coalescer that does it has two decisions worth reading:

TarkovHelper/Services/RefreshCoalescer.csnew
public static RefreshCoalescer OnDispatcher(DispatcherObject owner, Action refresh)
{
    var dispatcher = owner.Dispatcher;
    return new RefreshCoalescer(
        refresh,
        // BeginInvoke, not InvokeAsync: both queue the callback, but the
        // DispatcherOperation InvokeAsync returns CARRIES the callback's exception
        // instead of rethrowing it, so discarding that operation (as a
        // fire-and-forget schedule must) swallows the failure silently.
        action => dispatcher.BeginInvoke(action, DispatcherPriority.Background));
}

private void Run()
{
    // Cleared BEFORE the refresh, not after: a change landing WHILE the refresh runs
    // books a second pass instead of being swallowed by the pass that had already
    // read the old state.
    Interlocked.Exchange(ref _pending, 0);
    _refresh();
}

The scheduling rule is written down in exactly one place, and it has to be: a callback that runs inline, which is what Dispatcher.Invoke does when it is already on the UI thread, clears the pending flag before the rest of the burst arrives and so coalesces nothing at all. Background priority is what makes the burst land first. RefreshCoalescerSchedulingTests.OnDispatcher_reports_a_refresh_that_throws pins the BeginInvoke choice against a real dispatcher, which is the only way to observe the difference.

One more failure path closes here. ItemsPage's rebuild is an async void sitting at the top of the dispatcher stack, where a throw has nothing above it to catch it and takes the process down. It is now wrapped so a throw is logged instead.

07

The rest of the sweep

Four smaller findings that share one shape: a boundary where two pieces of code had to agree and nothing made them.

The import that aborted after committing

MigrateAppSettingsAsync wrote nine values inside one try and declared its counter inside it too. A locked database on value six aborted the run and reported zero for the five rows that had already committed. MigrateFromConfigFolderAsync deletes the imported JSON files only when the total is non-zero, so a partial import left the file behind to re-trigger the auto migration on every launch. The counter is now hoisted out of the try, and each value is guarded individually so one failure costs only itself.

Two readers of one file

SettingsService.MigrateFromJsonIfNeeded and ConfigMigrationService.MigrateAppSettingsAsync both read legacy app_settings.json, and they answer different questions, so there will always be two. What they must not differ in is what a given JSON value becomes as a row, and they had drifted on five values. The startup reader stored the faction in the file's own casing, clamped no sync range at all, and clamped the scav rep without rounding it, so it could write a 2.37 no setter could ever produce. LegacyAppSettingsValues is now the shared value half, deliberately pure functions over one value each so the two readers keep their own policies for which table, which partition, whether to count it, and how to report a failure. ConfigMigrationProfileAttributionTests.Both_legacy_readers_turn_one_file_into_the_same_profile_rows is the test that makes the agreement mechanical rather than remembered.

The spinner that undid the import

ItemInventoryService debounces its saves, and AdjustFirQuantity re-persists cached + delta absolutely. A pending save holds a quantity captured before the import, so one spinner nudge after an import wrote the stale total back over the imported rows. The flush now happens before the first write and never after it, and the cache is reloaded after the last one.

The status assembled from two profiles

QuestProgressService.GetStatus already carried an explicit ProgressSnapshot through the whole prerequisite walk. Its six requirement gates each re-entered SettingsService.Instance for their own value, so a publish between two of them mixed one profile's editions with another's level: the exact tearing the snapshot type exists to make unobservable, reappearing in its largest consumer. Both snapshots are now parameters, and every recursive step carries the same pair.

The review deferred two things, and both are now GitHub issues named from the code that defers them rather than only from a spec: extracting the EFT install locator and dropping the MapSettings facade, and removing the dead ShowLevelLockedQuests setting (issue 45).
