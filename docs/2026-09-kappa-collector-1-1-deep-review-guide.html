PR #62 · Code guide

The answer was there, and it came from the wrong place

Part 2 of the Kappa and Collector guides. Part 1 (docs/2026-09-kappa-collector-1-1-code-guide.html) is the design of the change in PR #60. This part is the deep review of that design. It fixed 33 findings, refuted 2 in the re-audit and 12 at verification, and left no decision open.

The defects share one shape. A surface answered a question from something NEAR the truth: the rows beside the number, one half of a requirement, a walk that carried its own target, a task set from the publish before. Every fix gives the question one place to be answered from. The decisions are in docs/decisions/feature-kappa-collector-1-1.spec.md, which this PR extends with TD15 to TD22.

The whole change

A deep review of the Kappa gauge and the Collector page. It found seven readings taken from the wrong source, four rules written more than once, and one service nothing called at all.

01

A reading from the wrong place

What part 1 built, and the shape every defect in this review has.

Part 1 gave the Collector page an unlock panel and made every Kappa count one number. It did that with a render pass: one capture of the recorded progress and the profile settings, threaded through everything one repaint shows. The pass is what stops a profile switch from mixing two profiles on one screen.

The review asked a narrow question of every number the change added. Where does this reading come from? Six times the answer was a source that is usually the same as the truth, and occasionally not.

The readingCame fromWhich is right until

None of these is a crash. Each produces a number that looks like an answer. That is what makes them expensive to find and cheap to miss: a wrong count reads exactly like a right one, and the app never says which source it used.

The shape they share

A test over the reading passes. A test over the source passes. Nothing tests that the reading came from the source it should have. The two are only tied together by whoever wrote the line.

02

The gauge that counted the rows

Part 1 moved the count into the pass, and then read it from the rows beside it.

Part 1 made the Kappa gauge agree with the status chips next to it. It did that by counting from the statuses cached on the row view models, which is what the chips count from. That is one source for two numbers, and it is correct whenever the rows are there.

The rows are not always there. The page subscribes to its services in its constructor, and its first load sits behind an await. A service event arriving in that window runs ApplyFilters over an empty row list. Every flagged quest was then absent from the list, so none of them counted. The gauge read a confident 0/13 for a profile that had recorded twelve of them.

TarkovHelper/Pages/QuestListPage.xaml.csUpdateKappaGauge, before
-   var doneInThisPass = _allQuestViewModels
-       .Where(vm => vm.Status == QuestStatus.Done && !string.IsNullOrEmpty(vm.Task.NormalizedName))
-       .Select(vm => vm.Task.NormalizedName!)
-       .ToHashSet(StringComparer.OrdinalIgnoreCase);
    // An empty row list is not a profile with nothing done.

The fix stores the pass instead of reading its output. CaptureRowPass is the only capture the two producers of row statuses use, so the stored pass cannot fall behind the rows. The gauge counts within it, and the count covers every flagged quest whether or not a row carries it.

TarkovHelper/Pages/QuestListPage.xaml.csUpdateKappaGauge, after
+   if (_rowPass is not { } pass || pass.KappaProgress() is not { } kappa)
+   {
+       TxtKappaGauge.Text = string.Empty;
+       KappaGaugeBar.Width = 0;
+       return;
+   }
+   var (completed, total, percentage) = kappa;

No reading is not a zero reading

Part 1 painted 0/0 when the quest graph was not built. That is the exact sentence the guard exists to avoid: a player reads it as "nothing is flagged". The pass now answers null for "no reading", and every Kappa surface paints nothing at all rather than a number it does not have. The precondition had been spelled four ways across two pages, and one of the four substituted the zero.

03

Half a requirement

The highest-value finding of the run, and the angles all missed it.

An item row carries two numbers: how many units the quests in scope want, and how many of those have to be Found In Raid. The two differ whenever one quest wants the item in raid and another wants it plain. The Collector page aggregates exactly that, and 22 items in the published data are mixed this way.

The rule asked only about the Found In Raid half. Owning the raid-found units marked the row Fulfilled, whatever the plain remainder said. The same expression drove the progress bar to 100, struck the item name through, dimmed the row and counted it in the stats line. A player was told an item was done while a quest still wanted one more.

TarkovHelper/Pages/CollectorViewModels.csthe rule, before
if (TotalFIRCount > 0)
{
    // FIR is required
-   if (OwnedFirQuantity >= TotalFIRCount)
-       return ItemFulfillmentStatus.Fulfilled;
    // TotalCount is never consulted on this branch.
}

The fix is one rule in the model layer, asked by all three surfaces that had a copy. Both halves have to be met. The raid-found units cover the raid-found half, and the units left over cover the remainder. A raid-found unit counts toward the remainder, because a raid-found item is still an item. A plain unit never fills a raid-found slot.

TarkovHelper/Models/ItemInventory.csItemFulfillment, after
+   public static bool IsFulfilled(int ownedFir, int ownedNonFir, int requiredTotal, int requiredFir) =>
+       Clamp(ownedFir) >= Math.Max(requiredFir, 0)
+       && Clamp(ownedFir) + Clamp(ownedNonFir) >= RequiredUnits(requiredTotal, requiredFir);

The review found this in the gap sweep, after all ten angles had run. No angle asked it, because no line of the change touched the expression: part 1 moved the rule between files and left it as it was. The sweep asks what the angles did not, and this is what it was for.

04

A walk that lied by name

Part 1 fixed the caller. The review fixed the walk.

GetAllPrerequisites appended the quest it was asked about as its last entry. Part 1 found what that cost. A "quest started" log event handed the whole answer to a planner that marks every entry Done. So every quest the live sync saw a player start was recorded as finished. Part 1 dropped the target at that one call site.

The review called that the wrong altitude. A caller compensating for a walk's name is a repair that the next caller does not inherit, and there were four other callers. The member is now two members. GetPrerequisiteClosure includes the target and says so in its name. GetAllPrerequisites is the same walk with the target dropped, which is what the name always promised.

TarkovHelper/Services/QuestGraphService.csthe two members
+   public List<TarkovTask> GetPrerequisiteClosure(string questNormalizedName)
    // prerequisites earliest first, the target last

+   public List<TarkovTask> GetAllPrerequisites(string questNormalizedName)
+       => GetPrerequisiteClosure(questNormalizedName)
+           .Where(t => !string.Equals(
+               t.NormalizedName, questNormalizedName, StringComparison.OrdinalIgnoreCase))
+           .ToList();

One caller wanted the inclusion all along. LogSyncService.CollectAlternativeQuestGroups forms a selection group from every entry with mutually exclusive siblings. A logged quest with siblings of its own reaches a group only by appearing in its own walk. That call site now reads the closure, and says why in a comment. Part 1's lab D drives both consumers.

Two dead walkers went with it. QuestProgressService.GetPrerequisiteChain was a third copy of the same traversal with no caller, and QuestGraphService.GetOptimalPath was reachable only from the service chapter 7 deletes.

05

The task set nobody replaced

The app updates its database every hour, and two services never heard about it.

A data publish lands in the background. Each database service reloads its own tables and announces it. Two services do not, because they are handed their tasks rather than reading them: the progress service and the quest graph. Nothing handed them the new set.

So the quest list, the chips, the detail pane and the Kappa denominator all stayed on the previous publish. They waited for the next restart. The item table beside them was fresh. On the Collector page the two could be seen to disagree: a requirement whose item had left the new item table was skipped from the list, while the quest that wanted it still counted it.

TarkovHelper/MainWindow.xaml.csOnQuestDataRefreshed
Dispatcher.Invoke(() =>
{
    var tasks = QuestDbService.Instance.AllQuests.ToList();
    // An empty reload is a failed load, not a publish that removed every quest.
    if (tasks.Count > 0)
    {
+       QuestProgressService.Instance.PublishTasks(tasks);
+       QuestGraphService.Instance.Initialize(tasks);
    }

    BuildLoyaltyGroup();
});

Why PublishTasks and not Initialize

Initialize publishes the task set and then loads the recorded progress for it. A publish changes which quests exist. It never changes which rows the player recorded, and the progress snapshot is keyed by id and name rather than by task instance. Calling Initialize here would block the dispatcher on a user-database read and re-run a "which profile is selected" read meant for startup. PublishTasks is the indexing half on its own.

The handler runs inline on the dispatcher, and the three pages queue their own reloads. So the republish always completes before any page repaints, whatever order the subscribers run in. Hideout modules stay out on purpose, and chapter 8 says why.

06

The selection a reload dropped

A defect a player meets every time progress changes, and no test could see.

The Collector page remembered the selected row as a view model instance. Every reload builds new instances, so the remembered one belonged to the previous list. Worse, assigning a new ItemsSource makes the list clear its selection and raise the changed event with nothing selected. The page read that as the user deselecting, and wiped the remembered name as well.

So the detail pane collapsed to "Select an item" on every progress change, every language switch and every database refresh. The name is the identity that survives a reload, and the row is now re-found by it. The handler stays suppressed while the page is the one changing the control.

TarkovHelper/Pages/CollectorPage.xaml.csSetItemsSourcePreservingSelection
+   var wasInitializing = _isInitializing;
+   _isInitializing = true;
+   try
+   {
+       LstItems.ItemsSource = rows;
+       _selectedItem = FindSelectedRow(_selectedItemNormalizedName, rows);
+       LstItems.SelectedItem = _selectedItem;
+   }
+   finally { _isInitializing = wasInitializing; }

Three reloads that dropped their own work

The same page posted three reloads as Dispatcher.Invoke(async () => ...). That binds to the overload taking a function returning a task, which returns at the body's first await and drops the task carrying the rest. Any exception in it went with the task. The reloads are synchronous now, so there is no await to return at. The one path that must be posted uses BeginInvoke, whose operation reports its exception.

07

One place per question

Four rules that were written more than once, and a service written for nobody.

Part 1 left four copies of a status adapter across two pages, and two copies of a trader name resolver. The pass now answers both. RenderPass carries the quest graph beside the snapshots. It exposes the status, the Kappa count and the Kappa list. A surface holding a pass cannot reach past it, because the graph is not a member of it.

A test keeps it that way. RenderPassStatusGuardTests fails when any file under Pages/ other than the pass itself names GetStatus. The map page is the one exemption, and it is named in the test.

The Collector page's scope rules moved to a service. The transitive walk, the three status exclusions, the currency rule and the raid-found aggregation were private members of a control the unit suite cannot construct. Nothing anywhere ran them. They are Services/CollectorScope.cs now, taking their two service questions as delegates, and 20 tests run them.

The Found In Raid axis became a value

Every quantity read, write and handler existed twice, once per half, in the service and in both item pages. The service carried two 20-line setters that differed in one field name. A FirKind parameter replaced them. The legacy names stay as one-line delegations, so nothing outside had to change at once.

The two item row view models turned out to be the same class typed twice, about ninety lines each. They share a base now. And ItemRequirementService, 352 lines and five types, had no reachable caller at all: the review deleted the dead chain inside it first, then found that nothing called what was left. It is gone, after a sweep across all four projects that included reflection and name-of references.

08

What stayed open

Two findings refuted with proof, one gap left on purpose, and the tests that could not be run red.

Two findings did not survive the re-audit. One proposed making the graph's Kappa members return null instead of throwing when the graph is not built. That would overwrite a recorded decision: An_uninitialized_graph_says_so_rather_than_counting_nothing asserts the throw. It also removes no guard, since each call site becomes a null check in the same place. The defect behind it was real, and chapter 2's null policy fixed it without touching the service.

The second proposed collapsing the Collector page's quest lookup. Its target no longer existed, and both remaining forms are worse. One puts the literal quest name back in the page. The other routes through a precondition that throws, ahead of a guard the page needs to return null.

Hideout modules still need a restart

The republish in chapter 5 carries quests only. The hideout database service reloads on its own subscription and announces it asynchronously. Republishing modules from the quest refresh would race that reload, and could publish the old list. The hideout progress service also has no progress-free half to call. A publish that changes a module is still invisible until restart. Closing it needs its own handler and the same split, and that is recorded in two documents and in the handler's comment.

Two Items page cleanups were deferred

The page still has two detail-pane writers and two copies of a status switch. They were deferred deliberately and filed as josephjang/TarkovHelper#61, as one issue rather than two: collapsing the writers deletes one of the switch copies, so two issues would mean two pull requests editing the same members. The issue is cross-referenced from four sites in the file.

One honesty note about the tests. Several of the Step 3 tests could not be run red against the unfixed tree, because the members they assert did not compile there. Those were verified by mutation instead: dropping the exclusion, the currency rule, the raid-found condition and the built-yet guard each failed the intended test. That is stated rather than reported as a red run. Two comment-only fixes have no failing assertion by nature, which is also stated.
