PR #67 · Code guide

Two refresh paths that each did the wrong amount of work

Part 2 of the guides for the quest recommendations removal. Part 1 (2026-09-remove-quest-recommendations-code-guide.html) explains PR #65, which removes the panel. This part explains the deep review of that pull request, and the fixes that PR #67 stacks on it.

The review found nine defects. Two changed behaviour: one refresh path ran its work twice, and one ran too little of it. The rest were comments and records that stated something nothing checks. The decisions are D4 and D5 in 2026-09-22-remove-quest-recommendations.md.

The whole change

MainWindow stops a second quest-list pass after each progress write. The two data reloads share one sequence, so the detail pane redraws after every reload. Comments and records now state only what is true and checked.

01

Reasons nothing checks

The shape most of the findings share, and how the review ended.

Part 1 rewrote several comments that had used the panel as their reason. A rewrite needs a new reason, and the easy new reason is a list: these callers, these events, these files. A list in a comment is true on the day someone writes it. Nothing fails when the code moves on.

The review found this shape four times. It also found two refresh paths where the code itself had copies that drifted apart. That is the same defect in code instead of prose: two places state one fact, and only one of them is updated.

How the review ended

The review ran on the deep-review-node engine. The engine blocked before its final report on a defect of its own. An answered question went stale when another answer edited a shared file, and no command could clear it.

The author chose to finish by hand. Seven fixes came from the engine. DESIGN-2 and ALTITUDE-2 were completed from its checkpoint. The final checks that the engine did not run were run by hand, and PR #67 lists them.

02

The pass that ran twice

EFFICIENCY-1 and decision D4: a refresh that the write already does.

MainWindow applied a quest event from the game log, then called RefreshDisplay on the quest page. After the in-progress quest dialog, it completed each prerequisite, then called RefreshDisplay again. Both calls ran the full sequence: statuses, filters, the detail pane.

But each write already announces itself. ApplyForOwnerAsync and CompleteQuest both raise ProgressChanged when rows change on screen. The page subscribes to that event and runs the same sequence. So every log event ran the pass twice.

TarkovHelper/MainWindow.xaml.csHandleQuestEventAsync
await progressService.ApplyLogEventAsync(task, evt.EventType, owner, evt.Timestamp);
-_questListPage?.RefreshDisplay();// ApplyForOwnerAsync already raised ProgressChanged -> OnProgressChanged

The review removed both calls. RefreshDisplay stays as a public entry point that still delegates to the one sequence, so the rule from part 1 holds. The proposal records the change as D4, because R3 named RefreshDisplay as a refresh path.

03

The reload that forgot the pane

DESIGN-2 and decision D5: two copies of one sequence, and the step one lost.

The page reloads its data on two paths. OnDatabaseRefreshed runs after a data publish. ReloadDataAsync runs when MainWindow reloads the quest list after the data check, a progress reset, a log-sync apply or a data migration. Those four raise no ProgressChanged.

The two paths were hand-written copies, and they had drifted. The publish path ended with UpdateDetailPanel. The other path did not. So after a progress reset, an open detail pane kept showing the quest as it was before the reset.

TarkovHelper/Pages/QuestListPage.xaml.csafter
+private void ReloadAllForDataChange()+{+    LoadQuests();+    PopulateTraderFilter();+    PopulateMapFilter();+    ApplyFilters();+    UpdateDetailPanel();+}
public async Task ReloadDataAsync()
{
    await LoadItemDataAsync();
+   ReloadAllForDataChange();}

Both paths now fetch the item lookup their own way and call one shared sequence. The old ReloadDataAsync also ran RefreshQuestDisplayNames, which did nothing: LoadQuests builds every row with its localized names already.

The pane now redraws after those four reloads, which it did not do before. That goes past R3's "exactly as before", so the proposal records it as D5. The author chose this option over a pane-only fix, which would keep two copies.

04

The margin that was always there

SWEEP-2: a false reason not to check, and the check it replaced.

PR #65 did not launch the app to look at the Quests tab. The reason it gave was false: "the panel was Collapsed until it was filled, so the default layout does not change". Only the inner Expander started collapsed. The panel itself always held its Auto row and a 12 px bottom margin.

So the removal moves the list up for every user. The proposal accepts that shift, but no test measures spacing. The grid guard reads row indices, and the E2E test checks only that the expander is gone.

The author chose a manual check. A build of the branch ran maximized on a fresh config. The gap from the chip row to the list measured 40 physical px at about 250% scale, which is about 16 DIP. That is the status row's padding plus its margin, with no empty band. The proposal's Risks record the result.

05

Comments and records

State what a guard pins, not a list that can go out of date.

RenderPass said the live status overload stays "for callers outside Pages/". Two lines earlier it exempted the map page, which is inside Pages/. It now names the map page and says the callers outside Pages/ are not listed, because no guard looks there.

TraderLoyaltyPanel listed three events that drive it. MainWindow names different ones. It now names the two MainWindow methods that call it, and a new test fails if a third caller appears.

ALTITUDE-2 found a <see cref> to a GetStatus overload that no longer exists. The compiler did not warn, because no project turns on doc-comment diagnostics. The cref is fixed. Turning the diagnostics on is issue #66, and the csproj points at it.

The records got three corrections: a supersede note that misquoted R7, the 294 and 296 prerequisite counts, which count different sets, and a comma splice in D2. One commit subject was 73 characters. It was reworded before landing, and the tree did not change.

What stayed open

Three findings the review refuted, and what the fixes left in place.

RefutedClaimWhy it does not hold
DUPLICATION-1the removal guards pin the same names twicethey pin different names; the reflection theory checks RecommendationType, which the scan list does not contain
ALTITUDE-3nothing limits the live status callers outside Pages/those callers are intended; the guard covers Pages/ because that is where the tearing risk is
DESIGN-3a file summary lists only some regionsthe list ends in "etc.", as the sibling file's summary does

RefreshDisplay now has no caller. It stays as the page's public on-demand entry point, and a test pins that it delegates to the shared sequence. A later change that finds no use for it can delete it with that test.

The engine did not run its own final checks, because it blocked first. Those checks were run by hand on the fix branch: both builds, the unit suite and the E2E suite. PR #67 lists the results. The engine defects go to the engine's own maintainers.
