PR #48 · Code guide

The data an old build can still read

Today every install downloads every data publish. The app checks nothing about what arrives, and it installs the bytes it received. This change gives each build an endpoint of its own, and it checks a download before the swap. Three labs let you operate the verify gate, the pointer that reports a stopped channel, and the publish that must write two addresses.

Two decision documents relate to this change, and both are new in this PR. docs/decisions/feature-versioned-data-channel.md holds the product decisions. docs/decisions/feature-versioned-data-channel.spec.md holds the technical design. The change is phase 2 of docs/decisions/feature-eft-1-1-roadmap.md.

The whole change

One property in the csproj names the data format this build reads. That property selects the bundled database and the endpoint the app polls. The endpoint publishes a manifest with a digest, and the app checks a download against it before the swap. A pointer at data/index.json tells a build that the project moved past it.

01

What updates today

The mechanism this change replaces is small. It is two URLs, one token, and one string comparison. Read it first, because each part of the new design answers something here.

DatabaseUpdateService holds two constants. Both point at raw main, at the two files under TarkovHelper/Assets/. Every install in the field holds those same two strings, because they are compiled in.

TarkovHelper/Services/DatabaseUpdateService.csbefore
internal const string VERSION_URL = "https://raw.githubusercontent.com/josephjang/TarkovHelper/refs/heads/main/TarkovHelper/Assets/db_version.txt";
internal const string DATABASE_URL = "https://raw.githubusercontent.com/josephjang/TarkovHelper/refs/heads/main/TarkovHelper/Assets/tarkov_data.db";
private const int UPDATE_INTERVAL_MS = 5 * 60 * 1000; // 5분

The check is four steps. Read the remote token. Compare it with the local token. If the two differ, download the database. Then write the new token into the local file.

Three properties of that comparison carry into the new design, so give them a moment. The token is opaque. The code compares it for equality, and it never puts two tokens in order. This is what makes a rollback work: the project publishes older content under a new token, and every install follows it like any other publish.

The same two files are also the build seed. TarkovHelper.csproj copies them into the output. The bundled token is what stops a fresh install from downloading the full 6.9 MB database on its first check. A failed fetch is safe: the code logs a warning and returns, and it changes no local file.

The timer starts with a due time of 0, so the first check runs at once. After that it repeats every five minutes.

02

The three gaps

One of these gaps can damage every install at the same time. One installs wrong data quietly. One lets an app tell the user something that is not true.

Every install receives every publish

There is no gate of any kind. A publish reaches an install from 2025 and an install from today within minutes. That is correct while the database only grows, because an old build ignores a table it does not know.

It stops being correct at the first publish that changes what a field means. Such a publish would reach every old install and make it show wrong data. Nothing can undo that selectively, because the code that reads the data is already on the disk of every user.

The 1.1 quest data refresh is the plausible first publish of that kind, and it is the next phase of the roadmap. This is why the roadmap moved the mechanism into a phase of its own. A mechanism of this shape only protects the builds that ship after it. The moment the need arrives is the moment it is too late.

Nothing checks what arrived

Raw GitHub caches each file on its own schedule. A check can therefore read a fresh token beside a database that the cache still holds from before. The old code installs those bytes and then writes the fresh token into the local file.

The cost

After that write, the install believes it holds the new version. Every later check compares equal and does nothing. The wrong database stays until the next publish, and the app never retries. A download that the network cut short installs the same way.

A stopped channel cannot say so

An install whose endpoint stops receiving publishes reports that its data is up to date. That answer stays the same forever while the data ages. The user has no signal that an app update is the way back to current data.

For a tracker this is the worst of the three answers. A user reads quest and item availability from the app and acts on it. Silence reads as agreement.

03

Four names, three integers

The design puts three integers and one string into the channel. Three of them could each be called a version. Read the four names before the design, because the design is hard to judge without them.

data format not a number The contract a build must satisfy to read the database. It covers the tables, the meaning of each field, and the values a field may hold.
dataFormatVersion 1 Which data format. It rises only when forward compatibility breaks. It names the directory, and the app compiles it in.
schemaVersion 1 The shape of one JSON document in the channel, and nothing else.
version 1.0.10 Which publish the data is. An opaque token, compared for equality only, exactly as it works today.

One question decides whether the data format version rises: would the previously released build, reading this data with its existing code, show the user something wrong? If the answer is yes, the number rises. If an old build simply ignores the change, the number stays.

New tables, new columns, new rows and new values inside a documented range are all free. A field whose meaning changed is not free, and neither is a field whose permitted range narrowed.

Why the name is not "schema version"

Schema versioning as practised compares structure. Avro, JSON Schema and the Confluent Schema Registry all work that way. A changed field meaning leaves the structure alone. A structural check would therefore pass, and the users would still see wrong data.

The word is also taken already in this repository, by the _schema_meta table and by the DDL. The name here follows Apache Iceberg, whose format-version is defined to rise when older readers would no longer read newer tables correctly. That is the same concept under the same name.

The term for the promise is forward compatibility, in the sense the Confluent documentation uses: a consumer on the old contract can read data written under the new one. That is this project exactly, because the readers nobody can fix are the installs already on disk.

04

Versioned URLs

Two other mechanisms could gate a publish. The roadmap left the choice open, and this PR settles it. The reasons are worth more than the answer, because the same reasons decide the shape of the documents.

The channel is one directory per data format version, at a fixed place on raw main. The index sits above them and names the version the project publishes right now.

repository layoutnew in this PR
data/
  index.json                 // the data format version published right now
  v1/                        // the endpoint for data format version 1
    manifest.json            // what this endpoint serves
    tarkov_data.db
    db_version.txt           // the legacy token, and the seed bookmark

TarkovHelper/Assets/         // the address pre-channel builds poll
  tarkov_data.db             // byte identical to data/v1
  db_version.txt

TarkovHelper/Assets/ stays in the repository because the builds already in the field hardcode those two URLs. Nobody can repoint them. That pair becomes the second address of data format version 1. The two addresses must hold the same bytes for as long as version 1 is live.

Why not a minimum app version marker

The rejected design puts a number beside the data that says which app versions may install it. Both designs protect only the builds that ship after them, so reach is not the difference. The failure modes are.

  • It gates on the wrong key. The compatibility key is the data format, and the app version is a different thing. An app release that touches no data would strand people for no reason.
  • It forces order onto a token that has none today. The whole field compares that token for equality, and rollback by republish depends on that.
  • It cannot work alone. Pre-channel builds ignore any marker. After a break, the older builds that do read the marker would stop receiving even compatible corrections, unless one endpoint per version already existed.

The third point is the one that settles it. The marker design turns into versioned URLs plus a parser. Versioned URLs put the version where the reader already looks, and they make a freeze physical: a superseded endpoint is a directory that stops changing.

Why a pointer, and not a marker in the old endpoint

The first design had each publish write a frozen line into every endpoint it left behind. Builds polling those endpoints would then read it and know.

That design edits documents the rest of the design calls finished. It also leaves a step that a person can forget, at exactly the moment that person is busy with a release. data/index.json replaces it. The publish rewrites the index every run, so the announcement cannot be forgotten, because nobody performs it.

The invariant this buys

The index is the only mutable part of the channel. Once a data format version is superseded, its directory is never written again. A build left on it keeps serving the last data that build can read.

Why JSON, and why the digest travels inside it

An earlier shape carried the version and the freeze directive as lines in db_version.txt. That name was already wrong the moment the file held anything besides a version. Every mature channel names the document for its role and carries a payload digest inside it. Look at electron-builder latest.yml, Squirrel RELEASES, APT Release, and the Docker and TUF manifests.

Putting the digest in the same document as the version is what makes the pair atomic. Chapter 2 described the skew that per-file caching allows. A separate hash file would not help, because a cache can hold that one stale just as easily.

Why version 1 gets a directory now

The channel could have waited. Builds would keep polling the Assets URLs, and data/v2/ would appear at the first real break. That plan avoids the mirror, and it costs more than it saves.

It means the mechanism runs for the first time during the emergency publish. The seed wiring, the two-target publish flow and the endpoint contract would all execute for the first time under pressure. Creating data/v1/ now makes every routine publish exercise the exact path the breaking one will use. Git stores blobs by content, so the mirror costs close to nothing.

05

One property, three consumers

A build has to agree with itself about which data format it reads. The bundled database, the polled URL and the number the app claims must be one decision, and not three.

The csproj carries the number. The seed items read it, and an AssemblyMetadata item carries it to runtime code. Nothing else names it.

TarkovHelper/TarkovHelper.csprojafter
<TarkovDataFormatVersion>1</TarkovDataFormatVersion>

<!-- Surfaces the property to runtime code. -->
<AssemblyMetadata Include="TarkovDataFormatVersion" Value="$(TarkovDataFormatVersion)" />

<!-- ... marks the elided <CopyToOutputDirectory>PreserveNewest</CopyToOutputDirectory> -->
<None Update="Assets\tarkov_data.db">...</None>
<None Update="Assets\db_version.txt">...</None>
<None Remove="Assets\tarkov_data.db" />
<None Remove="Assets\db_version.txt" />
<None Include="..\data\v$(TarkovDataFormatVersion)\tarkov_data.db" Link="Assets\tarkov_data.db">...</None>
<None Include="..\data\v$(TarkovDataFormatVersion)\db_version.txt" Link="Assets\db_version.txt">...</None>

The two Remove lines are the part that is easy to drop. Without them the SDK default items and the linked channel items both target Assets\ in the output. Two items would write one output path, and MSBuild ordering would decide the winner. DataChannelTests.The_assets_pair_is_removed_from_the_default_glob fails if either line goes away.

Link keeps the output layout the same. Runtime paths, the release package and the e2e expectations all still find Assets\tarkov_data.db. Only the source of that file moved.

Four tests hold this wiring together. Runtime_data_format_matches_the_csproj_property reads the csproj and compares it with the runtime value. The last one is worth a sentence of its own. If the index lived inside a format directory, a superseded build could only ever read the copy in the directory that stopped being maintained. That is precisely the state it needs to detect.

06

Verify before you install

Three checks stand between the bytes that arrived and the working database. Each one can be absent, and the rules for an absent check are as deliberate as the rules for a failed one.

The manifest is what the endpoint promises. It names the version it serves, and it describes the file beside it.

data/v1/manifest.jsoncommitted in this PR
{
  "schemaVersion": 1,
  "dataFormatVersion": 1,
  "version": "1.0.10",
  "database": {
    "file": "tarkov_data.db",
    "digest": "sha256:1fdb928c9e1c7912a491244bfd1b4dc5607aaa7c6dd6b4ec0eda5986e91313c7",
    "size": 6889472
  }
}

database.file is data and not a constant. A test proves the app fetches the name the manifest gives. That leaves room for a version stamped filename later, with no change to a reader.

Optional to the reader, mandatory in the repository

The digest and the size are optional for the app. An absent field, an unparseable one, or one that names an algorithm this build cannot check all mean the same thing: install, and write a log line. Refusing would turn a future hash upgrade into a breaking change for every build in the field. That is the outcome this whole channel exists to avoid.

Inside the repository they are mandatory. DataChannelMirrorTests.The_committed_manifest_describes_the_committed_database fails if either goes missing. So the fields can only disappear on purpose.

Why the digest names its algorithm

The value is sha256:<hex>, following OCI and Sigstore. The prefix is what lets a build that only knows sha256 tell "a digest I cannot check" apart from "no digest at all". Without the prefix the two look the same, and verification switches itself off with nothing in the log.

DatabaseUpdateService.VerifyDownloadafter
if (payload.Size is { } expectedSize)
{
    var actualSize = new FileInfo(tempPath).Length;
    if (actualSize != expectedSize) return false;   // discards the temp file
}

if (string.IsNullOrWhiteSpace(payload.Digest)) return true;

var separator = payload.Digest.IndexOf(':');
var algorithm = separator > 0 ? payload.Digest[..separator] : null;
var expectedHash = separator > 0 ? payload.Digest[(separator + 1)..] : null;

// An algorithm this build does not implement is a publish from the future,
// not a bad download: warn and install, the same way an absent digest installs.
if (!string.Equals(algorithm, "sha256", StringComparison.OrdinalIgnoreCase)
    || string.IsNullOrWhiteSpace(expectedHash))
{
    _log.Warning(...);
    return true;
}

// Hex case is not part of the contract.
return actualHash.Equals(expectedHash, StringComparison.OrdinalIgnoreCase);

The payload speaks for itself

The manifest is the publisher describing the file. The third check is the file describing itself. The published database carries its data format version in SQLite user_version, the 32 bit slot SQLite reserves for the application and never reads.

This catches a case the manifest cannot. A manifest can be internally consistent and still describe the wrong file: a directory populated by hand, a copy from the wrong build, a half finished bump.

}
catch (Exception ex)
{
    // The bytes already matched the manifest's hash, so the file is what the
    // publisher meant to serve. Rejecting a verified download over an

What a refusal leaves behind

A failed check deletes the temp file and returns false. The caller then returns "Failed to download database" and never reaches UpdateLocalVersionAsync.

The bookmark is the part that matters most. Say the local file advanced to the new token while the wrong bytes sat on the disk. Every later check would then compare equal and do nothing. Leaving the bookmark alone is what makes the next check retry.

07

Left behind

A build reads one number from the index and draws its own conclusion. What it does with that conclusion is one word in the title bar, and the argument for that one word took two rejected designs.

Every check starts with the index, before the manifest. The comparison is strictly greater: a higher published version means this build receives nothing further. An index that cannot be read leaves the last known state alone.

DatabaseUpdateService.RefreshSupersededStateAsyncafter
DataChannelIndex? index;
try
{
    index = ParseIndex(await _httpClient.GetStringAsync(_indexUrl));
}
catch (Exception ex)
{
    _log.Warning($"Failed to get channel index: {ex.Message}");
    return;                       // IsSuperseded keeps its value
}

if (index == null)
{
    _log.Warning($"Channel index at {_indexUrl} is unreadable; keeping the last known state");
    return;

IsSuperseded = index.CurrentDataFormatVersion > DataFormatVersion;

The early return is deliberate. A build that stopped receiving data has more failing checks by nature, and a network blip must not turn the notice off and on again. A_failed_index_fetch_does_not_clear_a_known_supersession holds that.

Being left behind ends future publishes. It does not take away data the install never received. The check continues to the manifest, and it installs anything on this build's own endpoint that the install has not caught up to yet.

Two refusals that never reach the user

Two other conditions stop a check, and both are publishing errors rather than user problems. A manifest whose schemaVersion is above MAX_SUPPORTED_SCHEMA_VERSION is a document shape this build was never taught to read. A manifest whose dataFormatVersion is not this build's pin describes a payload that does not belong at this address.

Both log an error and change nothing. Neither shows the user a message, and neither fetches the database. The next publish fixes both, and telling a user to update the app would be wrong advice.

The notice is the button that was already there

A newer data format can only ship together with the build that pins it. So whenever a build is left behind, a newer app exists, and the update button is already on screen. Adding a second notice beside it would split one situation into two things to read. It would also leave the user's only action in the quieter of the two.

The pill escalates instead. The label stops naming a version number and names the consequence. The tone moves from success green to warning, with dark text, because white on amber is unreadable at that size.

08

One publish, two addresses

While data format version 1 is live, two addresses must hold the same bytes. The publish tool in TarkovDBEditor is what keeps that true, and it must never create a format directory by itself.

The tool does not carry a version constant. A second pin could drift away from the first one, and this whole phase exists to make that class of mistake impossible. The repository layout describes itself instead: the live version is the highest data/v<N> directory present.

TarkovDBEditor/Services/DataPublishService.csnew
public int GetLiveDataFormatVersion()
{
    if (!Directory.Exists(_dataChannelPath)) return 0;

    var highest = 0;
    foreach (var dir in Directory.GetDirectories(_dataChannelPath, "v*"))
    {
        var name = Path.GetFileName(dir);
        if (int.TryParse(name.AsSpan(1), NumberStyles.None, CultureInfo.InvariantCulture, out var format)
            && format > highest)
        {
            highest = format;
        }
    }

    return highest;
}

The parse is what makes this correct. Sorting the names as text puts v9 above v10, so a publish would write the endpoint that was frozen and leave the live one alone. The_live_format_is_the_highest_channel_directory writes v1, v2, v9 and v10 and asserts 10. The parse also drops vNext, v and v2beta, which the next test asserts.

A zero is an error and not a fallback. A repository with no data/ directory fails the comparison with a message that names data/v<N>. Falling back to the Assets only layout would publish to an address that no current build polls.

The stamp goes on before anything is hashed

CompareAsync writes PRAGMA user_version into the source database before it compares, hashes or copies anything. Both endpoints then receive one stamped file, which is the only way the two can end byte identical.

A source that SQLite cannot open fails the publish there. Stamping could have skipped quietly instead. A file that is not a database should never reach the channel. Nothing else in the tool was checking that what it ships is one.

A drifted mirror is a change, not only a complaint

If a commit ever reaches one format-1 endpoint and not the other, raw main serves different bytes at the two addresses. The guard test in CI catches that. Catching it is not enough on its own.

What the first design left

With no database change, HasAnyChanges was false, so the Publish button stayed disabled. The CI guard was red and the tool offered no way to fix it. Copying files by hand was the only way out.

DataPublishService.ComparisonResultafter
public bool MirrorNeedsRepair => MirrorsToAssets && !MirrorInSync;

public bool HasAnyChanges => DbChanged || MapConfigsChanged ||
public bool HasAnyChanges => DbChanged || MirrorNeedsRepair || MapConfigsChanged ||
    MapSvgAdded > 0 || MapSvgUpdated > 0 || ...

The mirror is compared on both files. A drift in the database alone and a drift in the version stamp alone are each enough to make the publish button live again. Two tests cover the two directions, and a third asserts that a pair already in sync has nothing to publish. Without that third test the first two would prove nothing.

The order of the writes

The database goes first, then the manifest, then the version stamps, then the index. An interrupted publish then leaves an old version pointing at data that is merely newer. It never leaves a new version, or a new hash, pointing at data that never arrived.

One further rule lives outside the code. A publish commit carries every endpoint file it wrote, so raw main never serves a half published mirror. The mirror guard in CI is the tripwire for a commit that breaks that rule.

The guard that reads the database itself

DataFormatDriftTests snapshots the published database into DataFormatBaseline.v1.json: every table, and the declared type of every column. A run fails when a table or a column disappears, or when a column changes type. Additions are free and need no baseline change.

The first run writes the baseline and then fails on purpose. A baseline that appeared quietly would let a run that deleted it pass against whatever the database happens to hold that day.

What the guard cannot see

Nothing in the file says what a value means. A field whose meaning changed, or whose permitted range narrowed, passes this test. Those stay a human judgement against the question in chapter 3, and a green run is not evidence that forward compatibility holds.

The interval

Data polling moves from five minutes to one hour, and the app update check moves from three minutes to the same hour. Five minutes was 288 checks a day against a payload that changes a few times per game patch. It also sits below the cache window of the service that serves it, so the extra checks could not learn anything new.

The check at startup is unchanged and immediate, and it is the one that finds things. The cost is recorded rather than hidden: Settings still checks for app updates only, so restarting the app is the way to force a data check. That is deferred to the next settings pass.

DataChannelMirrorTests holds the byte-identical mirror, the committed manifest, the stamp and the index. DataChannelEndpointServingTests drives the real service against a loopback server and holds the update, the three checks and the refusals.

DataPublishChannelTests drives real publishes against throwaway trees and holds the live format resolution, the mirror repair and the frozen endpoints. DataFormatDriftTests holds the database against its baseline. UpdateServiceTests and LocalizationHeaderStringsTests hold the feed URLs and the three languages.

One check is deferred until this lands on main, because the endpoints only exist then. Fetch all four raw URLs and compare the mirrored pair byte for byte. Confirm that the previously released build still reports its data up to date. Confirm that a build from this branch fetches data/v1/ and reports up to date. The spec records this in its Verification section.
