PR #65 · Code guide

A list that no longer says why, taken off the Quests tab

This guide is a short curriculum for one removal. It starts with what the Recommended Quests panel did and why its ranking stopped making sense under the EFT 1.1 data. Then it shows what the change deletes, what it keeps, and how the tests hold the result.

The decision is 2026-09-22-remove-quest-recommendations.md, a Unified change proposal. The 1.1 data context is the subject of 2026-09-kappa-collector-1-1-code-guide.html and the quest data refresh guides before it.

The whole change

The Quests tab loses its Recommended Quests panel. The service, the view model, the setting and the strings behind the panel go with it. Nothing else on the tab changes, and no published data changes.

01

Five buckets and a tie

What the panel did, in the terms of the code this change deletes.

QuestRecommendationService.GetRecommendations looked at every Active quest. For each one, AnalyzeQuest made five checks in a fixed order. The first check that matched gave the quest its bucket and its priority. A quest that matched no check got no recommendation.

Check, in orderMatches whenPriority
Ready to completethe quest needs items, and the tracked inventory holds all of them100 + 20 for Kappa + 5 per follow-up
Item hand-in onlythe objectives are item hand-ins, and at least half the items are owned50 + 40 x owned share + 10 for Kappa
Kappa prioritythe quest is required for Kappa70 + 5 per follow-up
Unlocks manythe quest leads to 2 or more quests60 + 10 per follow-up
Easy questthe quest needs no items40, flat

The panel showed the first five after one sort. The sort compares priority first. It then puts ready quests and hand-in quests first. Nothing after that separates two quests with the same numbers.

TarkovHelper/Services/QuestRecommendationService.csdeleted
return recommendations
    .OrderByDescending(r => r.Priority)
    .ThenByDescending(r => r.Type == RecommendationType.ReadyToComplete)
    .ThenByDescending(r => r.Type == RecommendationType.ItemHandInOnly)
    .Take(maxResults)
    .ToList();

LINQ OrderBy is a stable sort. When two quests tie on every key, they keep the order they had in the input. The input was AllTasks, which loads in name order. So a tie is settled by the alphabet.

Two inputs need the user

The first two buckets read the tracked inventory. The inventory is what the user types on the Items tab. When the user types nothing, every count is zero, and those two buckets never match. That was true before 1.1 as well.

02

What 1.1 took from the inputs

The weights did not go wrong. The values they multiply stopped telling quests apart.

The design of 2025-12 assumed long prerequisite chains and a Kappa flag on half of all quests. EFT 1.1 replaced most chains with player level and trader loyalty gates. The proposal measured the inputs of the score in both databases, and this guide repeats its numbers without a new measurement.

Input the score readsv2026.7.0 data1.1.0 data

Put the two chapters together. A fresh profile tracks no items, so the first two buckets are empty. A few Kappa quests and a few quests with many follow-ups fill the top places. After them come the quests at a flat 40. On a fresh profile there are 81 to 125 of them, by level.

The last places of the five are therefore the first names of the alphabet. The proposal records that output: Acquaintance, All This Filth..., Belka and Strelka, and so on.

The cost

The panel still looked like advice. Nothing on it could tell a 1.1 player why this quest, and not one of the other hundred, was on the list. The expander was collapsed by default, so most users saw only a count badge that always said 5.

03

Remove, not re-score

Decision D1, and what the change does not try to do.

The proposal looked at a new set of weights. It could drop the Kappa bonus, raise the unlock threshold, or rank the easy bucket by level. It rejected all of them for one reason: new weights still multiply the same inputs.

With 294 of 488 quests free of prerequisites, the position of a quest in the graph no longer separates it from the others. Thirteen Kappa quests cannot carry a priority scheme. A 1.1 player asks other questions. What does the next level unlock? Which Active quests share the map of the next raid? Which hand-ins does the stash already cover?

Those questions need their own product decision, so they get their own proposal. This change makes room for that proposal and assumes nothing about its shape. If it wants a scoring service, it starts from its own inputs.

What stays as it is

The filters, the status chips, the progression sort and the follow-ups in the detail pane do not change. TarkovTask.LeadsTo, QuestGraphService and ItemInventoryService fed the score, and they keep their other users. These are the tools a player uses now to choose the next quest.

R2 names seven strings. The region held three more: ItemsOwned, ItemsNeeded and UnlocksQuests. The same 2025-12 commit added them for the panel, and nothing ever read them. The goal of no dead code covers them, so the change deletes the region whole. PR A lists this as a correction to the plan.

The page markup loses the panel element and its row. The grid had four rows. It now has three, and the main content moves up from row 3 to row 2.

Why delete the row, when an empty Auto row takes no height? An empty row is a slot with no owner. The next edit can put an element in it by mistake, and nothing would look wrong. R1 asks for the row to be gone, and a test counts the rows against the children.

The components namespace prefix goes too. The panel was its only user in this file.

05

One sequence, one step shorter

Requirement R3: every refresh path keeps the rest of its steps.

Four paths called UpdateRecommendations. They were the page load, the shared state-change sequence, the database-refresh handler and RefreshDisplay. Each path loses that one call and nothing else.

TarkovHelper/Pages/QuestListPage.xaml.csRefreshAllForStateChange
private void RefreshAllForStateChange()
{
    RefreshQuestStatuses();
    ApplyFilters();
    UpdateDetailPanel();
-   UpdateRecommendations();}

RefreshDisplay did not change. It still delegates to the shared sequence. This matters because an earlier change closed a shortcut here: a second, shorter copy of the sequence (feature-quest-chip-only-status-filter.spec.md). The proposal lists a new copy as a risk of this change.

TarkovHelper/Pages/QuestListPage.xaml.csRefreshDisplay, unchanged
public void RefreshDisplay() => RefreshAllForStateChange();

The comment above RefreshDisplay used the panel as its reason. It said that a shorter copy once left the panel stale after a level edit. The rule stays, so the comment now gives a reason that is still true. A completed quest unlocks its follow-up quests. That moves rows, chip counts and the detail pane together, and a second copy is where one path loses a step.

06

The row that stays behind

Decision D2 and requirement R9, and a correction to D2.

Older builds saved the state of the expander as the row questList.recommendationsExpanded in user_data.db. This build does not read the row, and it does not delete it. The settings table is a key and value store, and an unknown key does no harm.

The proposal rejected a cleanup on the next load. That code would run once for each user and then stay in every later build with no purpose. The row costs nothing and means nothing.

TarkovHelper/Services/Settings/QuestListSettings.csLoadSettings
if (SettingsValue.TryParseDouble(_userDataDb.GetSetting(KeyDetailPanelWidth), out var width))
    _detailPanelWidth = Math.Clamp(width, MinDetailPanelWidth, MaxDetailPanelWidth);
-if (bool.TryParse(_userDataDb.GetSetting(KeyRecommendationsExpanded), out var recommendationsExpanded))-    _recommendationsExpanded = recommendationsExpanded;_settingsLoaded = true;

A correction to the proposal

D2 first said that the complete profile reset clears the row. It does not. QuestListSettings keeps its keys in the app-wide UserSettings table. UserDataDbService.ResetProfileAsync deletes only the rows of the profile in ProfileSettings.

So the row survives a reset, like every other questList.* key. D2 stands on its other two reasons. This pull request corrects the text of D2 in the proposal.

07

How the removal is pinned

A removal has no defect to reproduce. The tests pin what must stay gone and what must stay.

The page cannot be built in the unit suite, because its markup needs the resources of the app. So QuestRecommendationsRemovalTests reads the source and reflects over the assembly. Its cases were written before the removal and run against the old tree first.

CasePinsOld tree
The_recommendation_types_are_goneR2, five typesfailed

The_expander_setting_is_goneR2, the setting propertyfailed

The two R3 cases passed on the old tree, and that is correct. They pin steps that must survive, so they must pass before and after. The other cases failed on the old tree for the expected reason, which shows that they are not empty. That run is evidence, not a reproduced defect.

The source scan exempts two test files. Each one names the panel to prove that it is absent. The E2E case also failed on the old tree, so its element name is real.

Some tests went with the feature. LocalizationHeaderStringsTests no longer pins the Kappa priority text or the text of the service (R5). The E2E case that clicked a recommendation is deleted with its entry point (R4). The other navigation tests stay.

The documents that specified the panel get a Superseded in part note (R8). The archived 2025-12 PRD gets one too (D3). A reader who finds those documents learns that the panel is gone, and why, without a search of the history.
