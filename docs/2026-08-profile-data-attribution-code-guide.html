PR #38 · Code guide

Progress that knows where it came from

This change stops the app filing quest progress under whichever profile happens to be on screen. Read it as a curriculum rather than a diff: the background first, the defect second, then three labs where you drive the actual decision logic before the gate at the bottom checks whether it landed.

Companion to docs/decisions/fix-profile-data-attribution.md (the product decision) and .spec.md (the technical design). Those record what was decided; this one exists to make the reasoning transferable.

The whole change in one sentence

Every write used to ask ProfileService.ActiveProfileId which partition it belonged to. That question has the right answer for exactly one of the four ways data arrives, so the answer now travels with the data: log events carry the game mode of the session that produced them, and hand edits carry the profile whose rows were on screen.

01

What EFT writes down

You cannot judge the attribution logic without knowing what evidence exists on disk. It is less than you would hope and more than the old code used.

Escape from Tarkov writes one folder per play session. Each folder holds several logs, and this change cares about exactly two of them.

%EFT%/Logs/one session folder
log_2026.08.11_07-00-00_1.1.0.46657/
  2026-08-11_07-00-00 1.1.0.46657 application.log        <- Session mode lines live here
  2026-08-11_07-00-00 1.1.0.46657 push-notifications_000.log  <- quest events live here
  2026-08-11_07-00-00 1.1.0.46657 network-connection.log

The application log announces which mode the client switched into. One line, repeated whenever the player visits the profile screen:

application.logthe only evidence of game mode
2026-08-11 07:00:12.431 1|1.1.0.46657|Info|application|Session mode: PvpSeason

The push-notifications log carries quest events as JSON blocks. Note what it does not contain: any mention of the game mode.

push-notifications_000.logtype 12 = completed
{
  "type": "new_message",
  "dialogId": "54cb57776803fa99248b456e",
  "message": {
    "type": 12,
    "templateId": "5936d90786f7742b1420ba5b successMessageText",
    "dt": 1786528812                 <- unix seconds, the only time we get
  }
}

Three facts that shape the whole design

  1. A sync reads every retained folder. The parser enumerates with SearchOption.AllDirectories, so one run spans days of play across all three modes. There is no such thing as "the profile this sync belongs to".
  2. A folder is not single-mode. Measured on one machine, one folder switched mode four times inside five minutes. Attribution per folder would still misfile; it has to be per timestamp.
  3. Both timestamps are local, and neither carries an offset. The mode line is a local-time string; the quest event is a unix dt converted with .LocalDateTime. They compare directly, which is convenient and leaves a one-hour-per-year hole at a daylight-saving fall-back. The spec records that rather than solving it.
02

The wrong question

The old code was not buggy in the usual sense. Every line did what it said. It simply asked the wrong source for the answer.

Progress is partitioned by profile: pvp, pve, season. Every write needs a partition key, and every write got it the same way:

QuestProgressService.cs (before)the shape repeated on every write path
await _userDataDb.SaveQuestProgressBatchAsync(
    changedQuests, ProfileService.Instance.ActiveProfileId);

ActiveProfileId answers what is the user looking at right now. Count the ways progress arrives and how often that is the right answer:

  • Hand entry (the user ticks a quest): correct. The user is looking at the profile they mean.
  • Syncing from logs: wrong, always. The logs span every mode; the screen shows one.
  • A live raid event: wrong whenever the player has switched the view to compare another mode.
  • The moment after an automatic switch: wrong for a window. The global moves before the cache does.

Why this was expensive

The permanent PvP profile accumulates progress over the life of an account. Entries mixed into it are the hardest to notice and the most costly to lose, and nothing in the app recorded which entries were wrong. The failure was silent by construction.

The fourth case deserves a closer look

SetActiveProfile assigns the global and raises its event synchronously, from the log watcher's thread pool. Subscribers answer with a fire-and-forget reload and return immediately. In the gap, ActiveProfileId names the new profile while the cache still holds the old one's rows, so a quest ticked in that window is written to a profile whose data was never displayed, and then vanishes from the screen when the reload lands. The player sees nothing recorded; the wrong profile gained an entry.

Two things are worth provoking before you move on. Drag the handle to the far left, before 09:00:00: there is no transition at or before that instant, so Resolve returns null. That is not a failure to handle: it is the honest answer, and the apply step drops the event and counts it. Then flip the strategy to per folder and drag again: a single answer for the whole folder is wrong for three of the four spans.

Services/Eft/SessionModeTimeline.csthe resolution rule
internal AppProfile? Resolve(DateTime at)
{
    SessionProfileHint hint = SessionProfileHint.Unknown;
    var found = false;

    foreach (var entry in _entries)
    {
        if (entry.At > at) break;   // entries are chronological
        hint = entry.Hint;
        found = true;
    }

    if (!found) return null;        // before the first marker: no evidence

    return ProfileService.TryResolveDetectedProfile(hint, out var profile) ? profile : null;
}

Read the null carefully

null means "no evidence", never "use the default". The app has already shipped one defect of exactly that shape, where a value that could not distinguish permanent PvP from seasonal play was used to pick storage and merged the two. Guessing here would reproduce the damage this change exists to stop.

03

Evidence on the event

Once the timeline exists, the fix is to stamp each event with its answer at the moment the answer is cheapest to compute.

Models/QuestLogEvent.csthe new field
/// Null means "no evidence" and never a default: an event from before the
/// first mode marker in its folder has nothing saying where it belongs.
public AppProfile? OwnerProfile { get; set; }

Why the stamp happens during parsing

The obvious alternative is to attribute later, at apply time, from SourceFile. Parsing wins for two reasons, and only the first is about performance:

  • At parse time the parser still knows which folder it is walking, so it builds one timeline per folder. At apply time the events are already flattened and each one would have to find its folder again.
  • Every consumer of a QuestLogEvent, present or future, receives an attributed event rather than having to remember to resolve one. The live raid path gets this for free, which is how requirement R4 is satisfied without a second mechanism.

The part that is easy to miss in review

Attribution alone is not enough. Sync also asks is this quest already recorded? and that question used to be answered from the in-memory cache, which holds at most one profile. Once a run spans three, the cache names the wrong profile for every group but one.

Services/LogSyncService.csone pass per owning profile
foreach (var group in attributed.GroupBy(e => e.OwnerProfile!.Value))
{
    var owner = group.Key;
    // That profile's OWN stored rows, read from the store. The loaded cache
    // would be the right answer for at most one group in the whole run.
    var storedProgress = await _store.LoadQuestProgressAsync(
        ProfileService.GetProfileId(owner));

    RunProfilePass(owner, group.ToList(), storedProgress, run);
}

This is also where the already up to date count in the summary comes from, and why IQuestProgressStore had to be extracted: the sync path needs to read a profile it is not displaying.

04

Cache and key as one value

The second half of the change. Log attribution closes a deterministic defect; this closes a timing one.

Before: two independent pieces of state. A mutable dictionary of rows here, and "whatever ProfileService currently reports" there. Nothing kept them in step, so a reader could observe one without the other.

Services/ProgressSnapshot.csthe new state
internal sealed record ProgressSnapshot(
    string ProfileId,
    long Revision,
    ImmutableDictionary<string, QuestStatus> Quests,
    ImmutableDictionary<string, bool> Objectives);

Binding them into one immutable value makes the split window impossible to observe. A reader captures the field once and sees rows and profile that belong together. A writer derives the next snapshot from the one it read, publishes it with compare-and-swap, and persists under that snapshot's ProfileId.

Services/QuestProgressService.csthe single write shape
var (published, changedQuests) = Mutate(current =>
{
    var rows = RowsOf(computePlan(current));
    return rows.Count == 0
        ? (current, rows)
        : (current with { Quests = WithRows(current.Quests, rows) }, rows);
});

// The partition comes from the snapshot the change was derived from,
// not from whatever the selection has become by the time this runs.
_ = SaveProgressBatchAsync(changedQuests, published.ProfileId);

Two transitions in flight

Reloads are asynchronous, so two switches in quick succession start two loads that can finish in either order. ProfileService gained a monotonic TransitionRevision that travels on the event; a load that finishes after a newer one was requested discards its result instead of publishing rows the user has already navigated away from.

Why compare-and-swap, when a plain assignment would do

Mutations are, in practice, confined to the dispatcher today. Nothing enforces that, and a lost update from a second writer would be silent. The retry loop makes the guarantee independent of a property no test checks, and it will almost never spin.

Code

The beat that matters is the third. Under Before, the edit reads a global that has already moved and a cache that has not, so the two disagree and the row lands in PvE, a profile whose data the player has never seen. Under After there is only one thing to read, and it is still the season snapshot, so the row goes where the player meant it to.

05

What else moved, and why

Four consequences that are easy to wave through in a diff this size, and are worth a moment each.

The per-quest review step is gone

The sync dialog used to list every change with a checkbox. That step existed because the player was the last defence against wrong attribution. Once attribution comes from the logs, it asks the player to confirm a judgment they have no better information about than the app does, over a list that now spans several profiles. It is replaced by a per-profile summary, which the PRD states as a requirement, not a nicety, precisely because a bad sync is now harder to walk back. The one prompt that survives is the one no evidence can settle: which of two mutually exclusive prerequisites the player actually took.

The cascade stopped using derived status

CascadeLookups.Status is now the recorded-only view rather than GetStatus. The two are interchangeable here: the core consults Status solely through gates testing == Done and == Failed, and GetStatus reports either of those exactly when progress records it. The payoff is that it keeps SettingsService (player level, faction, editions, all profile-scoped) out of a planner that now has to run for a profile that is not the selected one.

A dead code path was left dead, on purpose

LogSyncService's map watcher filters on application*.log. EFT names those files <date>_<time>_<version> application.log, so a pattern anchored at "application" has never matched anything. That whole path is dead: MapDetected and FindLastMapFromLogs have no subscribers anywhere, and live map detection is LogMapWatcherService's job. Repairing the glob would only make dead code do unused I/O, so it was left as-is with a comment recording the finding. SessionModeTimeline uses the correct pattern.

A deadlock the unit tests could not have found

Folding the quest and objective loads into one ReloadForProfileAsync gave the startup path a ProgressChanged it never used to raise. Initialize runs that load with Task.Run(...).GetAwaiter() .GetResult(), blocking the dispatcher, while subscribers marshal their refresh back to it. Unconditional hang, on every launch.

Services/QuestProgressService.csload-bearing argument
// notify: false is load-bearing, not an optimization. This call blocks the
// dispatcher thread on GetResult(), and ProgressChanged subscribers marshal
// their refresh back to the dispatcher.
Task.Run(async () => await ReloadForProfileAsync(profile, revision, notify: false))
    .GetAwaiter().GetResult();

The lesson worth keeping

The end-to-end test is what caught it, because the deadlock needs a real dispatcher. A change that touches thread affinity earns an e2e test even when the unit coverage looks complete.
