PR #51 · Code guide

The pipeline that stops instead of publishing quietly

Part 2 of the quest pipeline guides. Part 1 (docs/2026-08-quest-data-1-1-refresh-code-guide.html) is the design of the rebuild in PR #50. This part is the deep review of that design. Every defect here shares one shape. The run does the wrong thing, and each guard reports success.

The decisions are recorded in docs/decisions/feature-quest-data-1-1-refresh.md and in its specification docs/decisions/feature-quest-data-1-1-refresh.spec.md. This PR extends the specification. It records no new product decision.

The whole change

A deep review of the rebuilt quest pipeline. It found guards that pass over wrong answers. It closes each one where the answer is still correctable.

01

A guard that says yes

What part 1 built, and why a defect in a guard is worse than an ordinary defect.

Part 1 moved quest identity off the wiki page address and onto the game record id. It added a carry-over, so a renamed quest keeps the row key its recorded progress is filed under. It put guards around the write: a match rate, a delete budget, a seasonal marker canary, and a set of publish constraints.

The guards are what this review reads. A published database is a one way contract. Installs poll every five minutes, download what the endpoint holds, and apply it without checking it. Nothing recalls a bad publish. A quest whose row key changes loses every recorded completion in every install at once.

So the only useful question about a guard is what it answers over a wrong result. Several of them answered "pass". Each one is a chapter below, and each fix lands where the invariant can still be enforced.

The shape they share

None of these defects produces an error, a red count, or an empty table. Each one produces a plausible number. The delete budget reads 100 percent and refuses a run that deletes nothing. The match rate reads 0 percent and passes a run that orphans 48 quests. A freshness check reads green over data from before the patch.

02

The budget that counted keys

A guard that would have refused the first regeneration it was written for.

Every child table write refuses to lose more than 80 percent of the table in one run. The published QuestRequirements table holds 794 prerequisite edges. Part 1 measured that loss over each row's computed key.

A row key is not what a row is about. The key of a prerequisite edge covers its GroupId. Every published non-Collector row carries a GroupId of 1 or more from the old wiki parser, and the new pipeline emits 0. Collector's 248 rows use an older concatenation scheme entirely.

So on the first 1.1 run not one published key appears in the new set. The budget reads 794 of 794 gone, 100 percent, and refuses the run. That run deletes no prerequisite edge for that reason at all. It re-keys them.

-   IEnumerable<string> newIds,
+   IEnumerable<string> existingIdentities,
+   IEnumerable<string> newIdentities,

    Action<string>? progress)
{

    var existingCount = lost.Count;
    if (existingCount < MinRowsForDeleteBudget)
        return;

    lost.ExceptWith(newIdentities);
    var share = (double)lost.Count / existingCount;

+       // The gap between the two numbers is what makes a re-key visible.

            + $"({share:P1}); {rowsToDelete} rows deleted by key");

    }

    throw new InvalidOperationException(/* names the share and the limit */);

A prerequisite edge is now its (QuestId, RequiredQuestId) pair. A loyalty gate is its (QuestId, TraderId) pair. Items and Traders pass the record id, which is already upstream's own identity.

Measured that way against data/v1/tarkov_data.db and the live task set, the first 1.1 run loses 596 of 794 pairs. That is 75.1 percent against an 80 percent ceiling. The margin is real and thin, and the code comment says so with the numbers.

The ceiling stays loose on purpose. Patch 1.1 replaces the wiki's chains with the game's, and it takes the Kappa flag off all but 13 quests. Collector's synthesized list falls from 248 rows to 12. A tighter ceiling refuses the run this pipeline was rebuilt for.

03

Asking by the thing that rotates

The resolver exists because patch 1.1 moves titles. One of its steps looked a quest up by title.

One wiki page can have several game records behind it. ChooseAmong decides which record the page takes, by a fixed order of evidence. Step 3 is "the record the user's recorded progress has already been matching".

Part 1 found that record by the page title. The index it asked also answered for the title a row's key was minted from. Two failures follow from that, and neither leaves a mark in the published data.

  • A renamed page finds nothing. The lookup asks for the new title, and the previous row carries the old one. Step 3 falls through, step 4 takes the newest record, and the page mints a fresh key.
  • A page whose title changed owner finds the wrong row. Patch 1.1 handed eight titles to a different quest. The lookup answers with the old owner's row, and files one quest's recorded progress against another.

The fix is not only the new expression. The title index is deleted. What remains is ByExactName, which answers for a row's own name and never for the title a key was minted from. Only the seasonal pages use it, because those pages have no game record to match on.

Step 1 changed for a related reason. It recognises a BEAR record and a USEC record behind one page, and part 1 took whichever id sorted first. Each page of a chain is decided on its own, so that rule could take BEAR for Part 1 and USEC for Part 2.

Part 2's prerequisite would then name a BEAR record the refresh never imported. BuildRequirements drops a prerequisite it cannot resolve, and it does so without a word. The app would then offer Part 2 to a player who has not started Part 1. The side is now pinned to BEAR, which is what all four published faction pages resolve to today.

Step 1 also stopped requiring the pair to be the whole candidate set. A stale third record must not turn a shared page into a one faction quest. The row would then carry a Faction value that hides the quest from half the installs.

04

Blind to the rows it measured

A carry-over guard whose denominator excluded exactly the rows that cannot be carried.

AssertMatchRateHeld refuses a run that would lose the game record of more than 5 percent of published quests. It measured that over the rows that already carry an external id.

A row with no external id cannot be carried at all. Nothing in a run ties its new title to it. Those rows are the ones a refresh orphans, and they were the ones the guard could not see. They were absent from the numerator and from the denominator.

The refresh separately refuses to start when more than 10 percent of previous quests carry no external id. Ten percent of 488 published quests is 48 rows. So up to 48 quests could lose their row key at a measured loss of 0 percent.

The list itself comes from the resolver, which already builds it for the run log. The error names the first ten rows. A run that loses quests now says which quests, rather than reporting a share nobody can act on.

05

A receipt written too early

An ETag is a claim that a file on this machine holds a named upstream revision.

The client reads the game rules from json.tarkov.dev. It stores the ETag of each file it fetched, so the next run may be told 304 and keep what it has. Part 1 recorded those ETags as soon as the response parsed.

Parsing is not the last step that can fail. The caller still has to write the parsed models to a cache file. If that write fails, the ETag store names a revision no file on the machine holds.

The next run then sends If-None-Match, upstream answers 304, and the run keeps the very copy the failure was meant to replace. It also re-stamps the file's write time, so the seven day staleness guard reads green. The refresh publishes a pre-patch task set and reports success.

+ return Fetched(quests, group);

Not calling CommitETags costs one unconditional fetch. It never costs correctness. That is the safe direction for a caller to get wrong, and the reason the decision sits with the caller rather than inside the client.

06

Never reading the file that ships

Four guards that certified something other than the thing they were guarding.

The constraints read the build, not the file

The publish constraints state what every installed build can read: the requirement type vocabulary, the faction vocabulary, one row per prerequisite, a non-empty normalized name that matches the row key. Part 1 checked them over the rows a refresh had just built in memory.

The build phase is not the only way a row reaches the file. A hand edit in the editor's grid writes straight to the database. So does a backfill run, and so does any correction made after a refresh. The generic UPDATE can rewrite Quests.Name and leave NormalizedName behind.

The rules moved to PublishConstraints, which holds one declaration and two readers. One reader takes the rows a refresh built. The other opens a candidate database file read only. The publish path now runs them three times. It runs them in the comparison, and again against the file it is about to copy. It runs them a third time over the endpoint copy, before that copy is mirrored into Assets.

The file reader feature detects every column, the same way the app does. A database published before Quests.NormalizedName existed is checked the way the app reads it, from the name, rather than refused for lacking the column. data/v1/tarkov_data.db is in that older shape and passes the gate as published, which PublishConstraintTests asserts against the file itself.

A catch that admitted 320 pages

The crawl excludes event, seasonal and legacy categories. The loop that reads them caught every exception and moved on, with the comment "the category may not exist".

MediaWiki answers a missing category with an empty member list and a 200, so the catch never covered that case. What it covered was a timeout. One timed out request turned the whole exclusion list into nothing.

Historical content alone holds 320 pages inside Category:Quests, and 35 of them still have a live tarkov.dev record. Those 35 would publish as real quests. The read now fails the crawl, and the message says what continuing would publish.

A canary that only sang at zero

The seasonal marker guard fired when no page matched. A wiki edit that rewords 17 of the 18 KORD BREACH pages leaves one matching, and the guard stays quiet. The other 17 are held back and deleted with their objectives and prerequisites.

None of those pages carries an external id, so no other guard can see them. The measure is now a share of the pages that mention a seasonal mode, and the limit is 25 percent.

A flag older than the text it described

IsSeasonal was stored in the page cache beside the page text. It was assigned only where content is fetched, and the crawl skips content for every page whose revision is unchanged.

So a cache written before the marker existed answered false forever, while the refresh read the page text and imported the quest. The field is deleted. Both readers now derive the flag from PageContent through ExtractIsSeasonal, which is the only arrangement in which they cannot disagree.

The cache also kept every page it had ever seen. A page the quest list no longer names stayed in it and kept publishing as a live quest. PruneCacheTo drops those entries, and it refuses to prune to an empty crawl.

07

One prerequisite, two statuses

Fourteen 1.1 prerequisites name more than one satisfying status. A row carries one.

A prerequisite row is keyed by the (quest, prerequisite, group) triple. Two rows for one status pair would collide on that key rather than express an alternative. So both statuses have to fit on one row.

Ten of the fourteen are "active or complete". Accept is satisfied by an active prerequisite and by a completed one, so those ten collapse onto Accept with nothing left over and nothing lost.

The other four are "complete or failed", and no single type covers that. Part 1 collapsed them onto Complete. Two of the four ship as working OR groups in the published database today, so the collapse regresses behaviour that players have right now.

TarkovDBEditor/Services/RefreshDataService.csMapRequirementStatuses
// The most permissive type wins RequirementType, and only a status it does not
// already satisfy reaches AltRequirementType.
var named = statuses.Select(s => MapRequirementStatus(s, questTitle)).Distinct().ToList();
var primary = named.Max();

var leftover = named.Where(s => !Satisfies(primary, s)).Distinct().ToList();
if (leftover.Count > 1)
    throw new InvalidOperationException(/* a widened vocabulary needs a column */);

return new MappedRequirement(
    primary.ToString(),
    leftover.Count == 1 ? leftover[0].ToString() : null);

// Accept subsumes Complete, and nothing else subsumes anything but itself.
private static bool Satisfies(RequirementStatus type, RequirementStatus other) =>
    type == other || (type == RequirementStatus.Accept && other == RequirementStatus.Complete);

Both mechanisms ship. AltRequirementType is an additive column that carries the second status, and a build that reads it is satisfied by either. It reaches nothing until an app release reads it.

The other half reaches the field now. ExpandExclusiveAlternatives writes the same fact as an OR group: this prerequisite, or the quest whose completion fails it, both at Complete. Every installed build has understood OR groups since before this change.

Which quest is the other branch comes from upstream's own fail conditions, not from a transcription. The expansion is refused, and reported, whenever the group would not be readable as written.

Why the writer refuses a second row

The installed reader keys incoming prerequisite rows by TaskId alone and drops every later row naming the same prerequisite, GroupId and all. So two rows for one pair publish as one row, and which one survives is the row order. An OR group can lose a branch and become a group that nothing satisfies. PublishConstraints refuses that shape whatever produced it.

08

One rule, four spellings

The normalized name is the key recorded progress is filed under. Four places spelled it, and they disagreed.

The app derives a quest's normalized name in SQL when the column is absent. It derives it in C# when the column exists but a row's value is NULL. The editor writes the stored column from a third spelling. The two end to end test suites carried a fourth.

The SQL is the rule, because it is what produced the values that recorded progress is filed under today. It replaces spaces with dashes, drops the ASCII apostrophe and the period, and lowers A to Z.

It lowers nothing else. The bundled SQLite is built without ICU, so its LOWER leaves every non-ASCII letter alone. The C# twin called ToLowerInvariant, and it also stripped the comma, the question mark, the exclamation mark, the colon and the quote.

TarkovHelper/Services/QuestDbService.csGenerateNormalizedName
- return name.ToLowerInvariant()
-     .Replace(" ", "-").Replace("'", "").Replace("'", "").Replace(".", "")
-     .Replace(",", "").Replace("?", "").Replace("!", "").Replace(":", "").Replace("\"", "");
+ var result = new StringBuilder(name.Length);
+ foreach (var c in name)
+ {
+     switch (c)
+     {
+         case ' ': result.Append('-'); break;
+         case '\'': case '.': break;
+         default: result.Append(c is >= 'A' and <= 'Z' ? (char)(c + ('a' - 'A')) : c); break;
+     }
+ }
+ return result.ToString();

A row whose stored value is NULL was therefore keyed under a name nothing else computes. Nothing throws and nothing shows red. The completion simply stops appearing.

QuestNameNormalizationParityTests holds the three spellings together. One of its tests has SQLite evaluate the app's own expression over every published quest name and compares the result with the C# fallback. That test cannot be fooled by a shared misunderstanding of what SQLite does.

Tests that proved nothing

Several existing tests were shown to be inert before they were tightened. Each of these mutations left the whole suite green: renaming PageCollision.ChosenTaskId, nulling the match overrides file, and restoring the swallowed catch of chapter 6.

The fourth spelling of the name rule lived in the end to end suites. Both carried a local copy that used ToLowerInvariant, which lowers 1,146 BMP code points that the app's SQL leaves alone.

The consequence is worse than a wrong assertion. Both suites take the first carried rename they are offered, and a title with a cased non-ASCII letter reads as one. A single false positive displaces every real case, and the suite goes green having driven an ordinary quest. The copy is gone, and E2EFixtureGuardTests pins the reader that replaced it.

Read this file closely

During the review a fixer ran git checkout -- on RefreshDataService.cs and destroyed about 1,560 lines of uncommitted work. The file was reconstructed by replaying the recorded edits. It was verified structurally, behaviourally and by its metrics. Behavioural equivalence can be claimed. Byte equality cannot, because no copy from before the loss exists to compare against.
